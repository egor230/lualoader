# ПАУЗА СКРИПТОВ В GTA VC: ХРОНИКА МГНОВЕННОГО ВЫЛЕТА

> Дата: **22.09.2026** | Плагин `lualoader.asi` (Lua 5.4.9), игра GTA VC (**gta-vc.exe, PE32 x86**), Wine/Linux.
> **ВАЖНО: игра запущена как 32-битный `gta-vc.exe` (base 0x00400000), а НЕ reVC.exe (тот 64-битный, base 0x140000000).**
> Все адреса краша ниже привязаны к образу `gta-vc.exe` и system-области 32-битного процесса.

---

## 1. СИМПТОМ

Нажатие **Ctrl** (пауза/отключение всех Lua-скриптов) → мгновенный вылет. В
`lualoader/trace.txt` последняя строка — «ПАУЗА: …», дальше обрыв. Повторялось
во всех трёх итерациях фиксов.

---

## 2. ЧТО ЕСТЬ В АРХИТЕКТУРЕ (со слов автора кода, подтверждено исходником)

- 5 Lua-скриптов, каждый в отдельной **Lua VM** (`luaL_newstate`) + отдельный **`std::thread`** (`pump_owner`);
  т.е. каждый скрипт = свой thread + свой lua_State.
- `create_newthread()` из Луа плодит **дополнительную Lua VM + дополнительный C++ thread** (`luaL_newstate` + `std::thread(...).detach()`), с задержкой 301мс.
- Корутины: есть `L1` (вторая корутина через `lua_newthread(L)`), но `pump_owner` запускает `lua_resume(L1,...)` и `lua_resume(L,...)` из **своего** C++ thread.
- Игровые API (`Command<COMMAND_*>`, 504+ функций) дёргаются **напрямую из C++ worker-потоков** параллельно игровому потоку.
- Пауза по Ctrl = `scripts_disabled=true` + `pause_scripts()` (барьер по `active_pump_threads`) + (в прошлых версиях) запись в игровую память `ScriptSpace[OnAMissionFlag]=false` и `AddMessageJumpQ`.
- Остановка: yield-корутины через `lua_yield` из hook (была попытка), позже — «скрипт сам доезжает до своего `wait()` и паркуется». teardown — асинхронный, отдельный поток, закрывает чужие lua_State.

---

## 3. ДИАГНОСТИЧЕСКИЙ МЕХАНИЗМ (РЕАЛИЗОВАН)

В `plugin.cpp`:
- `AddVectoredExceptionHandler(1, lua_vectored_filter)` — FIRST handler, ловит **до** SEH reVC;
- `SetUnhandledExceptionFilter(lua_crash_filter)` — старый резерв;
- `std::set_terminate(lua_terminate_handler)`; `atexit(lua_atexit_handler)`;
- запись в `lualoader/trace.txt` прямым WinAPI без CRT (CreateFileA/WriteFile).
Формат: `C++| VECTORED: code=0x... addr=0x... thread=NNN`, `CRASH:`, `STD::TERMINATE`, `ATEXIT`.

## 4. ПОСЛЕДНИЙ КРАШ — ТОЧНАЯ НАХОДКА (трейс 09:32, последние строки)

```
8231: C++| VECTORED: code=0xC0000005 addr=0x004630EE thread=280   ← АВАРИЯ В КОДЕ ИГРЫ (главный поток!)
8232: C++| ПАУЗА: барьер — жду выход из активной зоны (активных=0)
8234: VECTORED: code=0xC0000005 addr=0x7725EFDD thread=452        ← 3+ AV в system-области, worker-потоки 452/448/460
8235: C++| ПАУЗА: барьер — все pump-потоки припаркованы (активных=0)
8237: C++| ПАУЗА: запрос (thread=468), скрипты замораживаются (yield-пауза без teardown)
8238: VECTORED: code=0xC0000005 addr=0x7725EFDD thread=460
8239: VECTORED: code=0xC0000005 addr=0x7725EFDD thread=448
8240: VECTORED: code=0xC0000005 addr=0x7725EFDD thread=452
```

Ранее в той же сессии (стр. ≈8146): `VECTORED: code=0xC0000005 addr=0x7BCD72F0 thread=284` и
`code=0xE06D7363` («MS» C++ exception) на игровом потоке **сразу после** применения паузы.

### Интерпретация

1. **`0x004630EE` = внутри образа `gta-vc.exe`** (PE32, imagebase `0x400000`, .text),
   файловый офсет `0x62CEE`. Дизассемблер:

```asm
4630ec:	89 c2           	mov    edx,eax
4630ee:	8a 82 ac 03 00 00  mov    al,BYTE PTR [edx+0x3ac]   ← AV: чтение [edx+0x3AC] по висячему/нулевому edx
4630f4:	88 44 24 0c      	mov    BYTE PTR [esp+0xc],al
```

   Т.е. **сама игра** в главном потоке разыменовала `edx+0x3AC`, где `edx` = результат предыдущего
   `call 0x451cb0` — это указатель на какой-то игровой объект (похоже, пед/авто), который стал
   **невалидным** (освобождён/перезаписан из worker-потока). Офсет `+0x3AC` — поле флагов/stay-was-attacked
   (перекликается с `set_ped_stay_when_attacked`!).

2. `0x7725EFDD`, `0x7BCD72F0` — **system-область** 32-битного процесса (ntdll/kerel32/winex11), массовые
   AV сразу на 3+ worker-потоках при падении игрового потока.

3. **Дата-пункт:** краш происходит **в КОДЕ ИГРЫ**, а не в `lualoader`. Значит `gta-vc.exe`
   доходит до строки чтения `[edx+0x3AC]` с испорченным `edx`. Это симптом **повреждения игровой
   памяти, вызванного НАМИ** — из worker-потоков параллельно с игровым потоком.

## 5. ПРИЧИНА (ГЛАВНЫЙ ВЫВОД)

**Data race между игровым потоком и C++ worker-потоками Lua** на игровых объектах:
- Lua-скрипты дергают `Command<COMMAND_*>`: `set_ped_stay_when_attacked`,
  `set_current_weapon_ped`, `is_ped_in_car`, `exitcar`, `create_spec_ped`, `mission_watch`,
  `setflagmission` — все пишут поля `CPed`/машины/флаги.
- **Игровой поток** каждый кадр читает те же структуры (AI, коллизии, рендер).
- Нет никакой блокировки: `active_pump_threads`/барьер защищают только «момент паузы»,
  но не «вообще всю игру». Порча накапливается и детонирует в произвольной точке
  (часто — в момент паузы, т.к. в паузу скрипты паркуются на давно сломанных структурах).

Совпадает с выводом сервиса: главный риск — не пауза как таковая, а **500+ параллельных
`Command<>` из чужих потоков**. Точка `0x4630EE` чтения `[edx+0x3AC]` — прямая «дыра»:
`set_ped_stay_when_attacked` пишет ровно эту зону (stay-флаг).

## 7. РЕКОМЕНДАЦИЯ СЕРВИСА (полный текст в диалоге; суть)

**Правильная схема потоков:**
1. **Один Lua-VM на скрипт** (`luaL_newstate`), доп. корутины — только `lua_newthread(L)`
   (общий registry/allocator), **НЕ** `luaL_newstate`.
2. **Один C++ thread-owner на каждый главный скрипт** (`pump_owner`).
3. **Ctrl:** только `scripts_disabled.store(true)`. Никакого `lua_close`/`lua_yield` из чужих
   потоков. Скрипт сам доезжает до своего `wait()`, внутри: `if (scripts_disabled.load()) return lua_yield(L,0);`
   → owner получает управление и **сам закрывает свой lua_State** (см. идея `owner_selfclose`).
4. **Не трогать `teardown_all`**, пока не найдена точка.
5. **Проверять код возврата `lua_resume()`** (LUA_ERRRUN/ERRMEM) — сейчас НЕ проверяется.
6. Не пытаться «всем скриптом» снять ET-флаги и синхронно остановить; дать скриптам **самим**
   завершиться через wait().

## 8. НЕ РЕШЕНО / ОТКРЫТО

1. Настоящая причина падения игрового потока — порча объекта игры (вероятно `CPed`, поле
   `+0x3AC`) из worker-потоков через `Command<>`/peds. **Недавние правильные адреса:
   `0x4630EE` (игра), `0x7725EFDD`/`0x7BCD72F0` (system, worker-потоки).**
2. Существует ли риск «повреждения до паузы»? Судя по адресу — ДА, повреждение идёт
   непрерывно во время работы миссии (стр. 8146, 8231 — все в момент миссии «Свинья»).
3. Проверить, что именно пишут 504 `Command<>` из worker-потоков, и где нет синхронизации.

## 9. СЛЕДУЮЩИЕ ШАГИ (план)

1. **Гипотеза подтверждается дизассемблером** — это главный прогресс. Зафиксировать и
   двигаться в сторону сериализации игровых API либо полной переработки (автор/сервис).
2. Вариант А (минимальный хирургический): запретить worker-потокам вызывать `Command<>`,

   который держит игровой поток на время игрового цикла).
3. Вариант Б (сервис): один owner на скрипт, корутины через `lua_newthread`,
   Ctrl=только `scripts_disabled`, закрытие своего lua_State своим потоком.
