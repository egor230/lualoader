## 1. Что нужно знать перед стартом

- Плагин **lualoader.asi** загружает ВСЕ `.lua`-файлы из `lualoader/`
  при запуске игры. Каждый файл — отдельный Lua-скрипт, у каждого своё
  состояние Lua-машины (`lua_State*`).
- Игра — **GTA Vice City** (steam 1.1 EN). Плагин мингается из Linux
  кросс-компилятором i686-w64-mingw32.
- Миссии в этом lualoader — это НЕ штатные миссии игры (не через
  `CTheScripts`). Это Lua-скрипты, которые отслеживают флаг «идёт миссия»
  (`Getflagmission()`/`setflagmission(true/false)`) и сами выполняют логику.
- Скрипты автозагружаются в порядке папки. Отладка — через `lualoader/log.txt`
  (ошибки) и `lualoader/trace.txt` (альтернативный трассер, пишем сами).

### 1.1 Терминология пользователя

| Фраза | Значит |
|---|---|
| «исходники», «funcs.h» | `lualoader-src/funcs.h` — ВСЕ Lua-функции (реализации+прототипы, ~24500 строк) |
| «plugin.cpp» | `lualoader-src/plugin.cpp` — регистрация функций (`lua_register`), загрузка скриптов |
| «установка», «скрипты» | `lualoader/` — только `.lua` файлы + log.txt |
| «собери» | `cd lualoader-src && ./build.sh` → `ГОТОВО: ../lualoader.asi` |
| «Lua-скрипт/миссия» | `.lua` файл в `lualoader/` |

Координаты в API — всегда **три отдельных числа X, Y, Z**.
Указатели на пед/авто/игрока — светлые userdata из функций поиска/создания.

## 2. Каркас миссии (обязательный скелет)

Эталон — реальный рабочий файл `lualoader/misson party.lua`. Скелет:

```lua
require("lualoader/mod")                 -- обёртки и фиксы (обязательно)

function main()
while true do wait() player = findplayer()   -- ВНЕШНИЙ цикл: ждём вход в маркер
 if Star_mission_marker(9, 118.0, -825.9, 10.5)  -- маркер: подъезд НА МАШИНЕ
 then showtext(" patry", 500, 1)                 -- имя миссии на экран
  setcord(player, 118.0, -825.9, 10.5) setangle(player, 54.0)
  bike = Createcar("MODEL_FREEWAY", 123.8, -810.9, 10.5)  -- стартовый транспорт
  setangle(bike, 320)
  fade(1, 2900)                                  -- проявление (из тьмы)
  blip = createmarker(1, 2, 95.4, -1136.2, 10.5) -- маркер цели на карте
  setsizemarker(blip, 3)
  sp = create_sphere(95.4, -1136.2, 10.5, 3.0)   -- сфера (зона срабатывания)
  printmessage("~r~Текст задания", 3000, 1)

  while true == getflagmission() do wait()        -- ОСНОВНОЙ цикл миссии
   -- ЭТАП 0 -> 1: игрок дошёл пешком до точки
   if ped_in_point_in_radius(player, 95.4, -1136.2, 10.5, 2.0,2.0,2.0)
      and not is_ped_in_car(player) and step == nil
    then remove_blip(blip) remove_sphere(sp)
         -- ... катсцена/создание целей ...
         step = 1
   end
   -- ЭТАП 1 -> 2: новая точка
   if step == 1 and ped_in_point_in_radius(player, -251.2, -1360.8, 8.1, 2.0,2.0,2.0)
      and not is_ped_in_car(player)
    then step = 2
         ped1 = Createped("IGMERC", -241.7, -1360.3, 8.1)  -- создать педа
         -- ... новые маркеры/сферы/враги ...
   end
   -- ЭТАП 2 (финал)
   if step == 2 then
    if ped_in_point_in_radius(player, 100.7,-1477.6,10.1, 2.0,2.0,2.0)
       and ped_in_point_in_radius(ped1, 100.7,-1477.6,10.1, 2.0,2.0,2.0)
     then remove_ped(ped1) miss(1000)              -- УСПЕХ: деньги + «passed»
          step = nil break
    end
    if getpedhealth(ped1) == 0 then                 -- ПРОВАЛ
       printmessage("dead", 3000, 1) end_mission("mission failed!")
       step = nil break
    end
   end
  end
  -- после выхода из основного цикла флаг уже снят (miss/end_mission)
 end
end
end
```

### 2.1 Почему миссия начинается с заезда НА МАШИНЕ (важно)

- Триггер — `Star_mission_marker(тип, x, y, z)` во **внешнем** цикле
  `while true do wait() end`.
- Он срабатывает, когда игрок **подъезжает к значку на машине**.
  `Star_mission_marker` (`mod.lua`) сам ставит флаг миссии, принудительно
  высаживает игрока (`exitcar`), убирает его машину (`remove_car`) и только
  потом возвращает `true` — после чего начинается тело миссии.
- Как только игрок вышел из машины — **значок исчезает**.
- Зачем именно так:
  1. Сразу видно, что миссия написана на **Lua** — не спутать с миссиями
     игрового движка.
  2. Она **не мешает** другим (оригинальным, движковым) миссиям: свой маркер,
     свои опкоды, своя очистка.
  3. **Безопасно для сохранений** — состояние миссии поднимается и снимается
     аккуратно, сейв не портится.
- Итог: каждая Lua-миссия = «значок, к которому подъезжаешь на машине» →
  высадка → основной цикл.

### 2.2 Правила каркаса (выстраданы опытом)

1. **`wait()` без аргумента** — минимум один на каждый проход цикла.
   Без него игра может зависнуть/вылететь: цикл закрутится без отдачи кадра.
2. **Флаг миссии** держим поднятым (`setflagmission(true)`) ВЕСЬ цикл
   `while true == Getflagmission()`; снимаем после выхода.
3. **Никогда не удаляй объекты миссии прямо в момент, когда цикл крутится
   по тому же условию** — сначала поменяй `step`, следующей итерацией
   удаляй. Удаление «в тот же кадр, когда что-то проверяем» — частая
   причина вылетов.
4. Переводы текста в `printmessage`/`showtext` — через тильду-коды
   (`~r~` красный и т.д.). Кириллица может не отобразиться (старый VC).

## 3. Пошаговый подход к написанию миссии

Этот рецепт — «как надо». В финальной главе (раздел 8) — что реально
происходит, если рецепт нарушить.

### Шаг 0. Определи сюжет и этапы (step-машину)

Разбей миссию на **дискретные этапы**: `step=nil → step=1 → step=2 → финал`.
На каждом этапе — свой входной триггер (точка/радиус/здоровье/таймер) и
свои действия (создание/удаление объектов). Один этап завершает другой.

### Шаг 1. Стартовый триггер (Star_mission_marker)

```lua
if Star_mission_marker(9, 118.0, -825.9, 10.5) then
```
Срабатывает, когда игрок входит в зону на карте. Стоит сразу:
- поставить игрока (`setcord` + `setangle`),
- создать стартовый транспорт и маркер цели,
- `fade` (затемнение/проявление),
- поднять флаг миссии.

### Шаг 2. Главный цикл с конечным автоматом

Внутри `while true == Getflagmission() do wait()` проверяем `if step == N`
и условия для перехода `step = N+1`. Ключевое — каждый переход сначала
чистит старьё, потом создаёт новое, и только сам `step` в конце.

### Шаг 3. Условия успеха и провала

- Успех: `miss(сумма)` + `printmessage` проходного текста + удалить всё +
  `break`.
- Провал: `end_mission("mission failed!")` (`miss` не даёт), удалить всё,
  `break`.

### Шаг 4. Обязательная очистка

После `break` (успех ИЛИ провал) — **удалить все созданные маркеры, сферы,
пикапы, педов, авто** (`remove_blip`, `remove_sphere`, `remove_ped`,
`remove_car`…). Всё, что не удалишь вручную, висит в map-ах плагина и будет
удалено при `destroy()` при перезагрузке скрипта — см. раздел 6.

### Шаг 5. Тест и диагностика

1. Пройти миссию медленно, смотреть `lualoader/trace.txt` (трассер, см. 7.2).
2. Смотреть `lualoader/log.txt` после каждого вылета.
3. Правило: **каждое изменение C++ (`funcs.h`/`plugin.cpp`)** →
   `./build.sh` → «готово» только после сборки. Изменение `.lua` —
   сборка не нужна, только перезапуск игры.

## 4. Какие API используются в миссиях (шпаргалка)

Полный список всех 1506 функций — в `LUA_API_СПРАВОЧНИК.md`. Ниже —
ядро, используемое почти в любой миссии:

### 4.1 Игрок и триггеры
- `findplayer()` → указатель игрока.
- `Star_mission_marker(тип, x, y, z)` → флаг «игрок на стартовом маркере».
- `setcord(player, x, y, z)`, `setangle(player, угол)` — поставить/довернуть.
- `ped_frozen(0|1)` — заморозить/разморозить игрока (катсцены).
- `fade(0 или 1, время)` — затемнение/проявление.
- `set_widescreen(true|false)`, `set_camera_position`, `camera_at_point`,
  `restore_camera()` — раскадровка катсцены.
- `is_ped_in_car(player)` → флаг «в машине».

### 4.2 Транспорт
- `Createcar("MODEL_ИМЯ", x, y, z)` → указатель авто (макрос по имени).
- `setangle(car, угол)`, `setcarcoordes(car, x, y, z)`.
- `putincar(ped, car)` — посадить педа/игрока в авто.
- `ped_car_as_driver/ped_car_as_passenger(ped, car)` — пед водитель/пассажир.
- `exitcar(ped)` — выйти из авто.
- `setcarspeed`, `setdrivingstyle`, `setcarstrong` — ИИ авто.
- `car_in_point_in_radius(car, x, y, z, r)` → флаг.
- `getcarcoordinates_on_y(car, смещ)` → x,y,z (позиция со смещением).

### 4.3 Маркеры/сферы (радар)
- `createmarker(тип, размер, x, y, z)` → id маркера; `setsizemarker(id, s)`.
- `create_marker_car(car)` / `create_marker_actor(ped)` → маркер на сущность.
- `remove_blip(id)` — удалить маркер (чистит и map плагина).
- `removemarker(id)` — то же через `COMMAND_REMOVE_BLIP`.
- `create_sphere(x, y, z, r)` → id сферы; `remove_sphere(id)`.
- `createblip(тип, x, y, z)` → обычный blip.

### 4.4 Педы
- `Createped("ИМЯ_МОДЕЛИ", x, y, z)` → указатель педа. Принимает И спец-акторов
  (`IGMERC`, `IGPHIL` …): пол — по `type_specpeds_list`, базовый пед того же
  пола, сверху — скин спец-актора (раздел 5.1, починено 16.09.2026).
- `create_spec_ped("IG...", x, y, z)` → старая функция спец-персонажа. СМОТРИ
  РАЗДЕЛ 5.1 — создаёт клона Томми (модель 0); для миссий используй `Createped`.
- `ped_in_point_in_radius(ped, x, y, z, rx, ry, rz)` → флаг.
- `getpedhealth(ped)` → число; `setpedhealth(ped, n)`.
- `follow_the_leader(ped)` → пед следует за лидером (в модах — за игроком).
- `clean_leader(ped)` — убрать из «следования».
- `ped_save_pos_attack(ped, флаг)` — атака позиции.
- `ped_walk_to_point(ped, x, y, z)`, `ped_run_to_point(...)`,
  `ped_sprint_to_point(...)` — движение к точке.
- `getcoordinates_on_y(ped/set)`, `getpedcoordinates_on_y(ped, смещ)`.
- `remove_ped(ped)`, `kill_ped(ped)`, `Giveweaponped(ped, патроны, "тип")`.
- `foel(модель, цель, оружие, x, y, z)` → враг, возвращает `ped, маркер`.
- `is_ped_in_car(ped)`, `incar(ped)` → флаг + авто.

### 4.5 Деньги/миссии
- `givemoney(n)`, `miss(n)` — начислить (успех). `miss` помечает проход.
- `end_mission("текст")` — провал/конец миссии.
- **`Getflagmission()` → флаг** (большая буква = C++: при каждом вызове
  поднимает сторож «погиб/арестован → миссия провалена», см.
  `ЗАМЕТКУ_О_МИССИЯХ.md`); `setflagmission(true|false)` — прямая установка.

## 5. ГЛАВНЫЕ ОШИБКИ (по убыванию коварности)

### 5.1 Спец-персонажи: клоны Томми — ПОЧИНЕНО в `Createped` (2026-09-16)

**Симптом (было):** `Createped("IGMERC", …)` / `create_spec_ped("IGMERC", …)`
создавали «второго Томми», а не Мерседес/нужного персонажа.

**Причина:** имени спец-актора нет в `name_peds_list`, `find_in_map` возвращал
`model = 0`, и `CREATE_CHAR` создавал педа с моделью 0 = Томми. Дальше шёл
`UNDRESS_CHAR`/`DRESS_CHAR` — механизм **скинов** (переодевания), но скин
спец-актора не ложился поверх чужой основы: базовый пед должен быть **того же
пола**, что и спец-актор.

**Решение (funcs.h, `Createped`):** если имени нет в `name_peds_list`, но оно
есть в `type_specpeds_list` — это спец-актор, и функция сама делает три шага:
1. **пол** — из `type_specpeds_list` (`4` = мужской, `5` = женский:
   IGMERC/IGMERC2/IGCANDY/STRIPA… — женщины, IGPHIL/IGGONZ/IGDIAZ… — мужчины);
2. **базовый пед нужного пола** — женский `WFYST`, мужской `HMYBE` (обычные
   модели из `name_peds_list`, с загрузкой и `MARK_MODEL_AS_NO_LONGER_NEEDED`);
3. **скин спец-актора** — `UNDRESS_CHAR(ped, имя)` + `DRESS_CHAR(ped)`.

Никакой загрузки спец-модели в слоты — только пол + базовый пед + скин.

```lua
ped1 = Createped("IGMERC", x, y, z)   -- теперь девушка с кожей Мерседес
```

**Старая `create_spec_ped`** оставлена как есть (всё ещё создаёт клона Томми:
модель 0) — в миссиях её НЕ использовать, спец-акторы всегда через `Createped`.
Фолбэк-обёртка `create_spec_ped` в `mod.lua` нужна только для старых скриптов,
вызывающих её по имени; новые миссии зовут `Createped` напрямую.

### 5.2 «Второй Томми» — симптом, повторённый дважды

Было две версии бага:
1. mиссия вызывала `create_spec_ped("IGMERC", …)` напрямую → Томми-клон.
2. Полуфикс: фолбэк стоял ПОСЛЕ `Createped(name)` и на `if base` — не
   срабатывал (база валидна). Девушка так и оставалась Томми.

Урок: при «не та модель» проверять не только имя модели в миссии, но и
порядок fallback-в-коде пула моделей. Паттерн «проверь маппинг до создания»
надёжнее паттерна «создай и проверь, что получилось».

**Итог (2026-09-16):** обе версии закрыты — `Createped` сам распознаёт
спец-акторов и создаёт педа правильного пола под скин (раздел 5.1).

### 5.3 Вылет «на последней точке клуба» — UB в удалениях (erase во время итерации)

**Симптом:** миссия доезжает до финальной точки (клуб), вызывается
`remove_blip`/`remove_sphere`/`remove_ped` — и вылет.

**Причины (все найдены и исправлены):**

1. **`remove_blip`** в `funcs.h` стирал элемент из `markeron` ВНУТРИ цикла
   `for (auto it = markeron.begin(); it != markeron.end(); ++it)`:
   ```cpp
   if (L == it->second && blip == it->first) {
       markeron.erase(blip);   // ← erase во время итерации!
   }
   ```
   После `erase` итератор `it` инвалидирован, следующий `++it` — UB → краш.
   **Фикс:** `auto it = markeron.find(blip); if (it != end()) { …; markeron.erase(it); }`.

2. **`removemarker`**, **`remove_sphere`**, **`remove_pickup`** вызывали
   команду движка, но НЕ удаляли запись из своей map (`markeron`/`spheres`/
   `pickupsids`). В map оставалась висячая запись → при `destroy()` объект
   удалялся повторно (двойное `REMOVE_*` по уже удалённому id) → краш.
   **Фикс:** в каждой `remove_*` добавлено `map.find(x) + map.erase(it)`
   с проверкой `L == it->second`.

3. **`remove_car`/`remove_obj`/`remove_ped`** — элемент физически удален, а
   запись в `mapcars`/`mapobjs`/`mappeds` осталась. Позже `destroy()` зовёт
   `GetPedRef/GetVehicleRef/GetObjectRef` по висячему указателю → краш.
   **Фикс:** стирание из map сразу после команды удаления.

4. **`destroy()`** — ТЕ ЖЕ паттерны `erase`
   внутри `for (…; ++it)` во ВСЕХ 6 циклах (markeron, spheres, pickupsids,
   firesids, mappeds, mapcars, mapobjs). **Фикс:** все циклы переписаны на
   безопасный `it = map.erase(it);`/`else ++it;`. (Прежний дубль `all_destroy()`
   удалён как мёртвый код — он нигде не вызывался и не регистрировался.)

**Общий вывод (главный урок всех сессии):**
> Никогда не стирай элемент из std::map во время обхода той же map.
> Для «удали все записи конкретного скрипта » используй
> `for (auto it = m.begin(); it != m.end();) { …; it = m.erase(it); }`,
> а для «удали одну» — `find` + `erase(it)`.

### 5.4 NULL-указатели: движок удалил педа/авто, а Lua продолжает им пользоваться

**Симптом:** вылет при входе на маркер миссии / при обращении к педу, который
уже пропал с карты (когда игрок вышел из машины, движок УБРАЛ транспорт из
пула).

**Причина:** Lua-функции (`getpedhealth`, `ped_walk_to_point`, `giveweaponped`,
`kill_ped_on_foot`, `ped_in_point_in_radius`, `getpedcoordinates_on_y`,
`getcarcoordinates_on_x/y`, `follow_the_leader`, `ped_sprint_to_point`,
`clean_leader`, `ped_save_pos_attack`, `create_marker_actor`, `exitcar` и др.)
брали указатель из пула, получали NULL и обращались к `NULL->…` → segfault.
`try/catch` в C++ ловит только `throw "…"`, а не segfault, поэтому лог молчит.

**Фикс (системный):** во ВСЕХ «опасных» функциях добавлена проверка
`if (ped == NULL / car == NULL) return 0;` (или `push false` для проверок)
в начале блоков с `LUA_TLIGHTUSERDATA`. Список защищённых функций —
в разделе 9.

**Правило для автора миссий:** перед использованием педа/авто, которого
долго проверяли (`getpedhealth`), всегда держать в цикле проверку
`ispers(ped)`/`isvehicle(ped)`; не хранить указатель навсегда — получать
его один раз на цикл (`player = findplayer()`), но объекты миссии
обновлять тоже.

### 5.5 `set_skin` (переодевание) без подгрузки модели скина

**Симптом:** игрок переодевается, скин не применяется / миссия ведёт себя
странно.

**Причина:** `set_skin` в C++ шлёт `UNDRESS_CHAR` со строкой имени модели
скина, но не выполняет предзадержку загрузки (RequestModel + Load). Скин из
`name_peds_list` не был подгружен.

**Фикс (mod.lua):** перед вызовом `native_set_skin` загружаем id скина:
```lua
local skin_models = { PLAYER9 = 4 }
function set_skin(ped, name)
	if skin_models[name] then
		loadmodel(id); load_requested_models()
		while not availablemodel(id) and n < 200 do wait(50); load_requested_models() end
	end
	return native_set_skin(ped, name)
end
```
Пример в миссии: `set_skin(player, "PLAYER9")` на этапе «магазин одежды».

### 5.6 Миссия «зависает на чёрном экране» — непереход между fade-этапами

**Симптом:** `fade(0, msec)` затемняет, игрок телепортируется, но экран
остаётся чёрным.

**Причина:** разрыв между `fade(0)` (затемнение) и `fade(1)` (проявление) —
в середине был `set_camera_position`/`camera_at_point`, которые требуют, чтобы
прошёл `wait()`. Плюс `ped_frozen(0)` при уже замороженном педе.

**Фикс/паттерн:** всегда после `fade(0, t)` ставить `wait(t + запас)` перед
`fade(1)`. Телепортация и работа с камерой — только в чёрном кадре.

### 5.7 `follow_the_leader` требует 2 аргумента, а в миссии 1

**Симптом:** Lua-ошибка «bad argument» или вылет при попытке педа следовать.

**Причина:** C++ `follow_the_leader(ped, leader)` принимает 2 педа, а старая
миссия звала `follow_the_leader(ped1)` однин аргумент.

**Фикс (mod.lua):** обёртка `function follow_the_leader(ped) return
native_follow_the_leader(ped, findplayer()) end` (см. раздел 9).

**Вывод:** при адаптации старых миссий проверять сигнатуры функций, а не
полагаться на «работало раньше».

### 5.8 `destroy()` и перезагрузка скрипта

**Когда вызывается:** `destroy(L)` на `reload` (Ctrl+Backspace) и
`final_scripts()` (выход). Это «когда мы выходим из цикла миссии — удаляется
всё, что мы создали».

**До фикса** все 6 циклов erase-в-итерации → краш именно в момент выхода.
После фикса (5.3/п.4) — просто чистится корректно.

**Правило:** миссия сама обязана чистить свои объекты до `break`, а не
рассчитывать на `destroy()` — но и `destroy()` не должен падать.

### 5.10 ABI-краш `CVector` — вылет на `SetObjective(OBJ, pos)` (ПОЧИНЕНО 17.09.2026)

**Симптом.** Миссия молча вылетает на ровном месте (нет Lua-ошибки), чаще
всего в конце. В `lualoader/trace.txt` последние строки — что-то вроде
`ped_walk_to_point: ... setobjective (x, y, z)`, но строки «после setobjective»
НЕТ. В игре — резкий выход на рабочий стол без внятного сообщения.

**Причина (фундаментальная, не про Lua).** SDK собирается компилятором
**clang/MinGW**. У класса `CVector` был *пользовательский* копирующий
конструктор `CVector(const CVector& src)`, поэтому clang считал тип
**нетривиальным** и передавал его в C++-функции **по скрытой ссылке
(указателем)**, а не 12 байтами по значению.

Игра же (`gta-vc.exe`) ждёт `CVector` **по значению**: функция `0x521840`
читает x, y, z прямо со стека (`[esp+0x24]`, `[esp+0x2c]`, `[esp+0x30]`) и
делает `ret 0x10` (чистит 16 байт). SDK до фикса присылал указатель
(`flds (%edx)`), а чистилось 8 байт вместо 16 → **мусорные координаты +
порча стека** → мгновенный вылет.

**Доказательства (машинные, не «на глаз»).**
- Дизасм игры: только `python3` + `pefile` + `capstone` (Ubuntu `objdump`
  не понимает `gta-vc.exe` — «file format not recognized»). `0x521840` = приём
  `CVector` по значению, `ret 0x10`.
- Дизасм толкателя в `CPed.o` до фикса: `push %esi; sub $0xc,%esp; ...
  flds (%edx); ... push %esp; push %eax; call *%esi` — это передача
  **указателя**.
- После фикса толкатель стал чистым `mov $0x521840,%eax; jmp *%eax`.

**Почему это не проявлялось раньше.** Апстрим plugin-sdk собирают на MSVC,
где ABI другой (пользовательский copy-ctor не ломает передачу). Баг вскрылся
именно нашей сборкой на clang/MinGW (миграция SDK 15.09.2026, в игре тогда не
тестировалась).

**Фикс (уже применён, 17.09.2026).**
1. `Plugin-SDK/shared/game/CVector.h`, строка с конструктором →
   `CVector(const CVector& src) = default;`
2. `Plugin-SDK/shared/game/CVectorImplementation.h` — удалить внешнее
   определение `inline CVector::CVector(const CVector& src){...}`.
3. Пересобрать `libPlugin_VC.a` (зависимости через `.d`-файлы в
   `output/mingw/obj/Plugin_VC/Release/`), затем `./build.sh`.
4. Проверка: толкатель `CPed::SetObjective(eObjective, CVector)` должен быть
   чистым `jmp` (без `push %esp`/`sub $0xc`).

**Проверка, что это между тобой и вылетом:**
```
# в ассемблере толкателя не должно быть push %esp перед call *%esi
i686-w64-mingw32-objdump -dr <CPed.o> | grep -A20 '<_ZN4CPed12SetObjectiveE...>'
```

**Что лечится этим фиксом.** Все 12 мест `SetObjective(OBJ, pos)` с `CVector` по
значению (актуальный список даёт `grep -n "SetObjective(OBJECTIVE_[A-Z_]*, pos)" funcs.h`;
на 18.09.2026 это 2455, 2478, 2501, 16463, 16481, 16604, 16657, 16675, 16693,
16711, 16822, 17321 — строки плывут при правках, сверять по факту), а также
`CPed::SetSeek(CVector, float)` (0x4FC740) и любые другие вызовы с `CVector`
**по значению**. Перегрузки `(eObjective, CVector const&)` и `(eObjective,
void*)` НЕ ломались (передача по ссылке/указателю).

**Бэкапы (если понадобится сравнить/откатить):**
`shared/game/CVector.h.orig-presdk-abifix`,
`shared/game/CVectorImplementation.h.orig-presdk-abifix`,
`output/lib/libPlugin_VC.a.orig-presdk-abifix`.

> ⛔ **НИКОГДА не откатывать этот фикс.** Если в SDK снова появится
> `CVector(const CVector& src);` без `= default` — это гарантированный
> вылет на всех `SetObjective(OBJ, pos)`. При каждом обновлении SDK
> переносить патч и перепроверять толкатель.

### 5.11 Миссия «не идёт дальше» на `Createcar` — гонка detached-потока (ПОЧИНЕНО 17.09.2026)

**Симптом.** Скрипт замирает (часто на этапе создания машины, напр. на
пристани), игра при этом жива. В `trace.txt` есть `Createcar: <MODEL>` (обёртка
в `mod.lua` печатает ДО вызова C++), но НЕТ `Createcar: ok` и нет следующего
кода. Баг **нестабильный** — в других прогонах те же машины создаются нормально.

**Две причины (обе в связке `Createcar`/`load_model_before_avalible`):**
1. `load_model_before_avalible` крутит `while (!Command<HAS_MODEL_LOADED>)` —
   при неудачной загрузке модели это **вечный цикл** (скрипт стоит, игра жива).
2. `Createcar` запускал **detached `std::thread(expectations, ...)`**, который
   ждал `car->IsVisible()` и вызывал `Command<MARK_MODEL_AS_NO_LONGER_NEEDED>`
   из **неглавного потока**. `Command<>` внутри использует общий
   `static CRunningScript` (`ScriptCommands.h`, `CallCommandById`) → **гонка**
   с главным потоком скрипта → порча движка скриптов → зависание/вылет.
   Это и есть известные «потоки без mutex» из отчёта миграции SDK.

**Фикс (17.09.2026):**
- Detached-поток убран. `COMMAND_MARK_MODEL_AS_NO_LONGER_NEEDED` вызывается
  **сразу после** `COMMAND_CREATE_CAR` на главном потоке. Это канон SCM:
  `029B request_model` → `038B load_requested_models` → `00A5 create_car` →
  `0249 release_model`. Так делает сама Rockstar.
- В `load_model_before_avalible` добавлены трейсы входа/выхода и прогресс
  каждые ~3000 мс — теперь в `trace.txt` видно, на какой модели застряли.
- (23.09.2026) Функция усовершенствована **без смены семантики** (по-прежнему
  блокирует, пока `HAS_MODEL_LOADED` не станет true):
  - **Имя модели в трейсах**: обратный поиск id→name из `car_model_list`,
    `name_peds_list`, `name_weapon_list` (кэш строится при первом вызове).
    Теперь в `trace.txt` вместо «id=269» видно «id=269 (chnsaw)» — сразу понятно,
    чья загрузка застряла.
  - **Пинок стриминга**: каждые ~1000 мс повторный `LOAD_ALL_MODELS_NOW(false)`;
    если модель не встала из-за затора/сбойного состояния стриминга (симптом
    «ЖДЁМ модель 40+ сек» в трейсе после teardown) — принудительная дозагрузка
    добивает модель. Трейс прогресса по-прежнему каждые ~3000 мс.

> ⛔ **НИКОГДА не вызывать игровые `Command<...>` из фоновых потоков.**
> Любая работа с движком — только на главном потоке скрипта. Если нужно
> «сделать что-то после появления объекта» — пиши в очередь (под mutex) и
> разбирай очередь в `wait()` на главном потоке.

> **Сторож миссии и API флага (см. `ЗАМЕТКА_О_МИССИЯХ.md`).** Функции с
> большой буквы (`Getflagmission`/`Setflagmission`/`Start_mission`) переносятся
> на **C++**. Сторож (проверка «погиб/арестован») должен быть **ровно один**:
> при запуске нового сторож старый уничтожается, поэтому потоки не
> пересекаются и конфликта нет.

### 5.12 `GetHeading()` теперь в РАДИАНАХ (ломает все углы) — исправлено

SDK v1004 возвращает у `CPlaceable::GetHeading()` **радианы**, а Lua-скрипты
и опкод `COMMAND_SET_CAR_HEADING` ждут **градусы** 0..360. Из-за этого углы
педов/машин уезжали. Фикс: умножение на `57.295779f` (`180/PI`) в четырёх
местах `funcs.h` (`getpedangle`, `getcarangle`, `getobjangle`, `putincar`).

> **Урок:** после обновления SDK проверяй не только компиляцию, но и
> **семантику** — единицы измерения, порядок аргументов, ABI. То, что
> «собралось», ещё не значит «работает как раньше».

## 6. Что происходит «под капотом» при выходе из миссии

1. Миссия делает `break` из `while true == Getflagmission()`.
2. Управление возвращается в `main()` — внешний `while true` продолжает
   крутиться; миссию можно в любой момент запустить заново (снова на маркере).
3. Созданные объекты, которые мы НЕ удалили вручную, живут в map-ах плагина
   (`markeron`, `spheres`, `mappeds`, `mapcars`, `mapobjs`, `pickupsids`,
   `firesids`) и НЕ удаляются сами по себе — до `destroy()`/`reload`.
4. `destroy(L)` вызывается на `reload` (Ctrl+Backspace) и при завершении
   игры; именно тогда «удаляется всё созданное». До фикса — падало (UB).
5. Поэтому: **культура миссии = всегда чистить за собой**. Иначе:
   - объекты копится между перезапусками (найдутся дубли); 
   - `destroy()` падал (было) / риск двойного удаления (после фикса нет,
     но лишние записи в map загрязняют память).

## 7. Диагностика и отладка

### 7.1 log.txt (штатный лог плагина)

`lualoader/log.txt`:
- строки `loaded <имя>.lua` — какой скрипт загрузился;
- тексты ошибок `throw "..."` из C++-функций (например «bad argument…», 
  «create_spec_ped: CREATE_CHAR вернул NULL»);
- **НЕ видит segfault** — если вылетел без записи в log, это было NULL- 
  обращение или UB (см. 5.3/5.4).

### 7.2 Свой трассер (ma_trace → log.txt) — лучший друг

В `mod.lua` есть `ma_trace(msg)` — пишет строку в `lualoader/log.txt`
(с 2026-09 миграция на единый журнал; с 19.10 trace.txt ЗАПРЕЩЁН — не создавать!).
Применяется на «тонких» местах:

```lua
function ma_trace(msg)   -- фактический код mod.lua:1092 (уже на log.txt)
	local ok, fh = pcall(io.open, "lualoader\\log.txt", "a")
	if ok and fh then fh:write(msg .. "\n"); fh:close() end
end
```

Паттерн диагностики: оборачиваем подозрительные функции, чтобы увидеть,
какая САМАЯ ПЛОХАЯ сработала перед вылетом:

```lua
local ortgetpedhealth = getpedhealth
function getpedhealth(ped)
	local h = ortgetpedhealth(ped)
	ma_trace("getpedhealth: " .. tostring(ped) .. " = " .. tostring(h))
	return h
end
```

Последняя строка в log.txt = место вылета (но помни: NULL-краши иногда
не успевают записать следующую строку — используй трассеры в `foel`,
`follow_the_leader`, `ped_in_point_in_radius`, `remove_*` и т.д.).

### 7.3 «Молчит и лог, и трейс» → это UB/NULL (раздел 5)

Если trace оборвался, а log пуст — почти наверняка:
- обращение к NULL-пед/авто без guard (5.4), или
- erase во время итерации (5.3).
Это два самых частых класса вылетов lualoader-миссий.

### 7.4 Пересборка и проверка

```bash
cd "/mnt/807EB5FA7EB5E954/games/old GTA Vice City/lualoader-src" && ./build.sh
```
- Успех = строка `ГОТОВО: ../lualoader.asi (размер)`.
- Предупреждения `duplicate section .rdata$...` из libstdc++ — штатные.
- Ошибки сборки = `error:` / `undefined reference` — искать их.
- Только `.lua` → `luajit -bl script.lua` (синтаксис) — играть не обязательно.

## 8. Истории ошибок из реальной сессии (хроника миссии «party»)

1. **«В автомобиль садится тommy, а не Mercedes»** → root cause:

3. **Вылет «на последней точке»** в trace от `create_sphere ok` → root cause:
   UB в удалениях (раздел 5.3). Починено переписыванием erase-циклов.
4. **Синтаксис mod.lua** — однажды после ручной правки файла трейсер с
   трассировкой сломался (опечатка). Проверка `luajit -bl` обязательна.
5. **Молчаливый вылет в конце миссии** (17.09.2026) → root cause: ABI `CVector`
   (раздел 5.10). Симптом обманчив — похоже на «пришёл не туда», на деле
   порча стека в `SetObjective(OBJ, pos)`. Лечится `= default` у copy-ctor.
6. **«Стою на пристани, миссия не идёт дальше»** (17.09.2026) → root cause:
   детач-поток `expectations` дёргал `Command<>` из неглавного потока + вечный
   цикл загрузки модели (раздел 5.11). Симптом нестабилен: в одних прогонах
   те же машины создаются, в других — стоп на `Createcar: MODEL_INFERNUS`
   без `ok`. Лечится `release_model` сразу после `create_car` на главном потоке.

## 10. Чек-лист «можно сдавать миссию»

- [ ] миссия = `main()` + `while true do wait()` + `Star_mission_marker`.
- [ ] флаг `setflagmission(true)` поднят, в цикле `== Getflagmission() == true`.
- [ ] каждый проход цикла начинается с `wait()`.
- [ ] этапы через `step`; переходы не удаляют то, что ещё читается в том же
      кадре (сначала смена step, потом удаление прошлого этапа).
- [ ] спец-персонажи создаются через `Createped("IG…", x, y, z)` — пол и скин
      C++ берёт на себя (5.1, починено 16.09.2026); `create_spec_ped` не звать.
- [ ] все обращения к пед/авто под `ispers`/`isvehicle` или NULL-guard (5.4).
- [ ] после `break` — полная очистка своих объектов через `remove_*` (5.9).
- [ ] `trace.txt` прошёл до финальной точки, лог без ошибок (7.1/7.2).
- [ ] (для C++-правок) `./build.sh` → `ГОТОВО: ../lualoader.asi`.
- [ ] (для .lua-правок) `luajit -bl` без ошибок.

## 11. Финальное резюме (что важно запомнить)

1. Миссия на lualoader — это конечный автомат на step-ах внутри
   `while true == Getflagmission()`.
2. Пять классов проблем (по убыванию):
   **UB в удалениях > NULL-указатели > спец-персонажи/скины (починено в
   `Createped`) > сигнатуры функций > fade/камера**.
3. Никогда не erase-в-итерации; всегда чистить свои map.
4. Спец-акторы — только через `Createped` (пол → базовый пед → скин);
   `create_spec_ped` оставлен для старых скриптов и создаёт клона Томми.
5. Всё, что может быть NULL, — проверяй. Движок удаляет сущности без спроса.
6. Трассируй тонкие места (trace.txt), читай log.txt, помни что segfault
   не пишется в лог.
7. Сборка после каждых C++-правок; синтаксис после каждых .lua-правок.

Итог 17.09.2026: к списку классов проблем добавились
**ABI-несовместимость (5.10)** и **гонки потоков (5.11)** — оба коварны тем,
что Lua-код выглядит правильным, а падает/висит движок. Лечатся один раз в
C++/SDK, но требуют машинной проверки (дизасм), а не «на глаз».

## 12. ПРАВИЛА БЕЗОПАСНОСТИ — как НЕ сломать то, что работает

> Прочитай ПЕРЕД любой правкой. Цена нарушения — часы на поиск и сломанная
> миссия.

1. **Бэкап до правки.** Трогаешь SDK или `funcs.h` — сначала
   `cp file file.orig-<что-и-зачем>`. Пример имён:
   `CVector.h.orig-presdk-abifix`.
2. **Патч `CVector` ABI (5.10) — неприкосновенен.** Не откатывать, не
   «упрощать». При обновлении SDK — переносить заново и перепроверять
   толкатель дизасмом.
3. **«Работает — не трогай».** Не переписывай рабочие функции ради красоты,
   стиля или «а вдруг так лучше». Меняешь только то, что доказанно сломано.
4. **Игровые вызовы — только из главного потока.** Никаких `std::thread`,
   дёргающих `Command<>` (5.11). Нужен отложенный эффект — очередь под mutex,
   разбор в `wait()`.
5. **Каждая C++-правка → `./build.sh`.** Успех — строка
   `ГОТОВО: ../lualoader.asi (6,1M)`, 0 ошибок. «duplicate section … has
   different size» — известный безвредный шум MinGW.
6. **Каждая правка `.lua` → `luajit -bl файл.lua`** (проверка синтаксиса).
7. **Проверяй в игре и читай trace.** Последняя строка `trace.txt` — где
   остановилось; `log.txt` — ошибки Lua; сегфолт в лог не пишется.
8. **Фикс доказывай машинно.** Дизасм (objdump/pefile+capstone), а не
   «вроде заработало». После обновления SDK прогоняй миссию целиком.
9. **Проверяй семантику после обновления SDK**, а не только компиляцию:
   единицы (радианы/градусы, 5.12), порядок аргументов, ABI классов.
10. **Не объявляй успех без теста.** Собралось ≠ работает. Не выдумывай
    пути/файлы — бери реальные (`ls`, `grep`), а не догадки.

## 2. Порядок работы

1. **Прочитать исходник целиком, построчно.** Разметить карандашом, где:
   подготовка (`GOSUB` init и катсцен), объекты сцены, **главный игровой цикл**
   (одна метка-цикл + `GOTO` в начало), условия успеха/провала, награда,
   очистка (этот блок в оригинале почти всегда есть — `MISSION_HAS_FINISHED`).
   В миссии Riot основным циклом является `:@L4725d` → `GOTO @L4725d`, а не
   `LOCATE`-цикл в шапке. Ищи строку вида `0002: GOTO @<та же метка>`.
2. **Выписать последовательность геймплея**: какие объекты, где стоят, что
   делает игрок, какие кнопки/блайпы наводят его на цель, когда миссия
   заканчивается, сколько денег и что ещё даёт награда.
3. **Выписать все исходные переменные**, которые меняются по ходу и влияют на
   поведение (флаги «уже сработало», счётчики). У каждой взять смысл:
   например `$2212` — «сколько пикетчиков игрок уже укусил», `$2198` —
   «сколько пикетчиков умерло», `$2213` — «переоделся ли», `$2205` — «бой
   начался». В Lua каждый такой флаг → отдельная `local`.
4. **Сопоставить каждый нужный опкод с Lua-функцией** (сверять с
   `LUA_API_СПРАВОЧНИК.md` и `lua_register` в plugin.cpp). Если функции нет —
   добавить в funcs.h (реализацию в стиле соседних: try/catch + writelog,
   русский комментарий, проверка типов через `lua_type`) + plugin.cpp
   (регистрацию), пересобрать `./build.sh`. Список уже добавленных для Riot —
   раздел 2.2.
5. **Написать миссию по каркасу** (раздел 3) и правилам (раздел 4). Локальные
   переменные внутри `if Star_mission_marker`, координаты инлайн, ни одного
   глобального состояния.
6. Проверить синтаксис: `luajit -bl "misson X.lua"` — без ошибок в конце.
7. Установить в папку `lualoader/` с кодировкой UTF-8 + BOM + CRLF
   (конвертировать скриптом, как в README). Только ОДНА миссия в папке
   одновременно (правило 5, раздел 4).
8. **Отдать на тест в игру.** Смотреть `lualoader/log.txt` (загрузились ли
   скрипты, нет ли `runtime`-ошибок) и `lualoader/trace.txt` (трассировка
   критичных функций: `SMM srabotal`, `pipir: …`, `createobj`, `Createcar: ok`).
   Прогнать до `miss(1000)` / `mission failed!`.

## 2.1 Сверка API: чего нет, и чем заменить (грабли переноса Riot)

Перед написанием — проверить КАЖДЫЙ вызов по `LUA_API_СПРАВОЧНИК.md` и
`lua_register` в plugin.cpp. Часть «очевидных» функций в lualoader отсутствует —
таблица проверенных замен:

| Опкод/механика оригинала | Нет в API | Рабочая замена |
|---|---|---|
| `HAS_PICKUP_BEEN_COLLECTED` | да | проверка расстояния `ped_in_point_in_radius(player, x, y, z, 2,2,2)` до точки пикапа |
| Катсцены (`LOAD_CUTSCENE`) | да | текст через `printmessage` + камера (`set_camera_position`/`camera_at_point`/`restore_camera`) + `fade` |
| `SET_RIOT_INTENSITY`, крики толпы | да (было) | теперь есть `set_riot_intensity(уровень)` (0552) — см. 2.2; крики — текстом `printmessage` |
| `ADD_SPRITE_BLIP_FOR_COORD` (спрайт) | частично | `radar_set_coord_blip(type,x,y,z,colour,display)` + `radar_set_blip_sprite(id, sprite)` — виден из любой точки карты |
| Одежда (`CREATE_CLOTHES_PICKUP`) | нет, есть лучше | `create_pickup_clothes(model, x, y, z)` + `set_skin(ped, "имя")` (модель одежды 2 = рабочий; `set_skin` в mod.lua подгружает скин) |
| Спец-акторы (`LOAD_SPECIAL_ACTOR`) | НО `Createped` умеет | `Createped("SPANDXA", x, y, z)` — спец-скин определится по `type_specpeds_list` (пол → базовый пед → скин); **не использовать** `create_spec_ped` (создаёт клона Томми) |
| Урон толпы (`SET_CHAR_WAIT_STATE`, `SET_CHAR_PERSONALITY`, `SET_CHAR_ONLY_DAMAGED_BY_PLAYER`, `IS_CHAR_HEALTH_GREATER`) | да (было) | теперь есть `set_ped_wait_state`, `set_ped_personality`, `set_ped_only_damaged_by_player`, `is_ped_health_greater` — см. 2.2 |
| Объекты-цели (`MAKE_OBJECT_TARGETTABLE`) | да (было) | теперь есть `make_obj_targettable(obj, flag)` — см. 2.2 |
| Выпавшее из трупа оружие (`GET_DEAD_CHAR_PICKUP_COORDS`) | да (было) | теперь есть `get_dead_char_pickup_coords(ped)` → x,y,z + `create_weapon_pickup` — см. 2.2 |
| Модели по id | — | только имена из списков funcs.h: `car_model_list` (MODEL_SPAND=213…), `name_peds_list` (GDA=91…), `type_specpeds_list` (IGGONZ, SPANDXA, …) |

**Порядок высадки/приёма:** опкоды `ENTER_CAR_AS_DRIVER/PASSENGER` и задачи
педа из машины — работают (`setcardrive`, `setcarpassenger`, `putincar`,
`exitcar`), но после `exitcar` пед ещё ~2 сек в анимации: давать задачу
`ped_walk_to_point` можно только после полного выхода (C++ теперь
принудительно высаживает через `warp_ped_out_of_car` — но цикл ожидания

```
  local step
  local mission_blip

  -- Краткий текст вместо катсцены (LOAD_CUTSCENE нет в API)
  printmessage("~w~Ken: задание...", 5000, 1)

  -- Пикап одежды / подготовка (если есть в оригинале). Подбор проверяем
  -- РАССТОЯНИЕМ, потому что has_pickup_been_collected в API нет.
  local clothes = create_pickup_clothes(2, X_PICKUP, Y_PICKUP, Z_PICKUP)

  -- Глобальный блайп на цель (виден из любой точки карты)
  mission_blip = radar_set_coord_blip(0, X_TARGET, Y_TARGET, Z_TARGET, 2, 2)
  if mission_blip ~= nil then radar_set_blip_sprite(mission_blip, 19) end

  -- Предзагрузка анимаций в начале (request_animation), выгрузка в конце
  -- (remove_animation) — как в оригинале пара REQUEST_ANIMATION/REMOVE_ANIMATION.
  request_animation("RIOT")

  printmessage("~g~Поезжай к месту.", 5000, 1)
  step = 1

  while true == Getflagmission() do wait()

   -- ЭТАП 1: подъезд к цели (в машине/пешком)
   if step == 1 and ped_in_point_in_radius(player, X_TARGET, Y_TARGET, Z_TARGET, RX, RY, RZ)
   then
    if mission_blip ~= nil then remove_blip(mission_blip) mission_blip = nil end
    -- Создаём сцену в темноте (SMM уже затемнил экран)
    set_riot_intensity(127)
    ... Createcar/Createped/create_marker на месте действия ...
    fade(1, 1200) wait(1200)          -- засветка
    printmessage("~g~Цель на месте: уничтожить грузовики.", 6000, 1)
    step = 2
   end

   -- ЭТАП 2: игровой процесс (убийство целей, защита и т.п.)
   if step == 2 and условие_победы
   then
    ... чистка бланков/машин/педов ...
    set_riot_intensity(0)
    remove_animation("RIOT")
    ma_trace("mission: ВЫПОЛНЕНА")
    miss(НАГРАДА)
    step = nil
    break
   end

  end
  step = nil
 end
end
end
```

- **Внешний цикл** — ждёт подъезда к значку НА МАШИНЕ. `Star_mission_marker`
  создаёт значок, высаживает игрока, убирает его авто, поднимает флаг миссии.
- **Внутренний цикл** — `while true == Getflagmission()` пока миссия активна.
  Каждый этап = блок `if step == N`. Успех — `miss(деньги)`, провал —
  `end_mission("mission failed!")`.
- Смерть/арест игрока обрабатывает C++-сторож `Getflagmission` (функция
  `destroy()` очищает всё созданное).
- **Флаги-«одноразы»** из оригинала (например «бой начался», «уже показал
  текст») — `local` и обнулять сразу после выполнения условия, чтобы не
  срабатывали дважды.

## 3.1 Архитектура файла: вспомогательные функции ВЫШЕ `main()` (урок Riot, 9–11-я ревизии)

Крупные самостоятельные блоки — катсцены, создание сцены, эскалация боя,
дублирующиеся операции — выносить в `local function` **перед** `main()`:
читаемость, одна точка правки, создаются один раз при загрузке скрипта (а не на
каждом старте миссии). Шаблон связи с `main` (проверено на Riot):

- **Состояние миссии** (`step`, флаги, счётчики) остаётся в `main`.
- **Таблицы** (`rioters`, `bite_flag`, `dead_flag`, `hp_prev`, `guard_target`)
  передаются ПАРАМЕТРАМИ и мутируются **по ссылке** — возвращать их не надо.
- **Созданные сущности** функция **возвращает многозначным `return`**, а вызов
  присваивает их локалам `main`:
  ```lua
  truck1, truck2, truck3, mt1, mt2, mt3, obj1, obj2, gate, agit1, agit2, leader =
      spawn_riot_scene(player, rioters, bite_flag, dead_flag, hp_prev, riot_intensity)
  ```
  (11 значений — нормально для Lua; главный цикл дальше работает с привычными
  локалами, а не с `scene.truck1`).
- **Флаги-результаты** (`escalated = 1`, `agit1_drop = 1`) выставляет
  **вызывающий** — функция делает только своё дело (поведение педов, создание
  сущностей), состояние миссии ей не принадлежит. Символьные обёртки для
  флагов: `agit1_drop = drop_agitator_colt(agit1, agit1_drop)`.
- Имена — глаголы: `dressed_as_worker`, `dress_cutscene`, `spawn_trucks`,
  `spawn_rioters`, `spawn_riot_scene`, `start_riot`, `drop_agitator_colt`.
  Перед каждой — шапка-комментарий: что делает, какие опкоды оригинала, что
  мутирует/возвращает.

> ⚠ **НЕ выносить этапные переходы.** Блок `if step == N and <триггер> then …
> step = M end` — это логика главного цикла: ему нужны `step`, блайпы, сообщения.
> В `spawn_riot_scene` ушло **создание сущностей**, а триггер подъезда к
> стройке, тексты и `step = 3` остались в `main`.

### 6 правил канона

1. **Фазы — именованные функции ВЫШЕ `main()`** (`first_step`, `foes_on_bikes`).
   Имена — глаголы/сцены. Каждая: готовит сцену (спавн, камеры, fade, реплики) и
   **выставляет `step`** в конце. Вызываются из `main` один раз.
2. **`main()` — только цикл и переходы.** Внешний `while true do wait()` ждёт
   маркер; внутренний `while true do Getflagmission()` — step-машина. Каждый
   блок `if step == N and <триггер> then … step = M end` — один переход.
3. **Триггер этапа — условие в `and`** (`ped_in_point_in_radius`,
   `not player_defined(ped)`, `car_in_point_in_radius`). Успех — `miss(деньги)`,
   провал — `end_mission("mission failed!")`.
4. **Маркер+сфера — парой**: `blip, sp = create_marker_and_sphere(...)`,
   снимаются парой `remove_blip(blip); remove_sphere(sp)` при переходе этапа.
5. **Катсцены — за fade**: `fade(0,…)` → действия в темноте → `fade(1,…)` →
   `wait()`. Камеру ставить/снимать парой
   `set_camera_on_car`/`restore_camera()` (или `set_camera_position`/
   `camera_at_point`/`restore_camera`).
6. **Комментарии оригинала внизу файла** — дизассемблированный SCM (`-- 00F5:
   player ...`) оставляем как справочник, рабочий код — только наверху.

### Чек-лист соответствия канону

- [ ] Фазы — функции выше `main()`, вызываются из неё
- [ ] В `main()` нет спавна/камер — только `if step == N and … then … step = M end`
- [ ] Маркер и сфера создаются и снимаются парой
- [ ] Fade обрамляет каждую катсцену/телепорт
- [ ] `miss()` — единственная точка успеха
- [ ] Нет `while get_fading_status() do wait() end` (см. §7, ревизия 22.09)

## 4. Правила переноса

1. **Координаты — инлайн.** НЕ выносить в верхний блок констант вида
   `local X, Y, Z = ...` с шапкой «-- Координаты из оригинальной миссии».
   Такой блок только засоряет код. Писать координаты прямо в месте
   использования (в вызове Createcar/Createped/ped_in_point_in_radius и т.п.).
2. **Все переменные состояния — local** (объявлять в начале блока after
   `if Star_mission_marker`). Все скрипты папки lualoader/ крутятся в потоках
   на ОБЩЕМ lua_State, поэтому глобалы разных миссий (step, blip, car...)
   пересекаются и ломают друг друга.
3. **Катсцены и спец-скины не переносятся буквально.** Полноценные катсцены
   (LOAD_CUTSCENE LAW_*) нет API — заменять коротким текстом через
   printmessage. Спец-модели (LOAD_SPECIAL_CHARACTER) не грузятся — брать
   обычных педов из name_peds_list / спец-акторов через `Createped("SPANDXA")`.
   Эффекты (SET_RIOT_INTENSITY) — теперь ЕСТЬ (`set_riot_intensity`), включать
   как в оригинале, в конце миссии выкл.
4. **Модели - только по именам из списков funcs.h:**
   - Createcar("MODEL_<Название>", x, y, z) — имена в `car_model_list`
     (напр. MODEL_SPAND=213, MODEL_PONY=143).
   - Createped("<Имя>", x, y, z) — имена в `name_peds_list` (обычные педы,
     напр. HMYST, GDA) или спец-акторы в `type_specpeds_list` (IGGONZ и т.п.).
- Оружие Giveweaponped(ped, патроны, "имя") — имена в `name_weapon_list`/
      `types_weapon_list` (molotov=тип 15, colt45=тип 17, nitestick=тип 4).
   Сверять с data/default.ide (id → имя), вызывать по имени из списков.
5. **Одна миссия в папке lualoader одновременно.** star_mission_marker в C++
   использует общие static (point/create) — две миссии будут драться за
   значок. Остальные скрипты (autoaim и диагностика) не мешают.
6. Кодировка Lua-файла: UTF-8 с BOM и CRLF. MD-документы: UTF-8 без BOM, LF.
7. Каждое имя функции проверять: оно должно быть зарегистрировано
   (`lua_register` в plugin.cpp) либо определено в mod.lua. Иначе — runtime
   ошибка в игре.
8. **Состояние игрока читать из игры, а не из флага-переменной** (урок Riot:
   «переоделся ли Томми»). Одежда/скін определяются через `get_player_skin()`
   (C++ читает `CModelInfo` — реальное имя модели, `"player"`/`"player3"`),
   обёрнутые в `local function dressed_as_worker()` со сравнением в нижнем
   регистре. Почему НЕ флаг: флаг не переживает Ctrl-reload (глобалы
   обнуляются, а скин живёт в мире игры) и не учитывает смену скина любым
   путём.    Аналогично для других «состояний мира» — лучше читать из игры.
   Старая `get_current_skin_name()` — кэш последнего `set_skin`, её не
   использовать для проверок.
9. **Покадровый цикл — только NULL-безопасные C++-функции.** Перед тем как
   добавить вызов в кадровый цикл, прочитать его реализацию в funcs.cpp:
   `find*inpool` → проверка `== NULL` → безопасный возврат. **Остерегаться
   OOB-обёрток SDK**: например `CModelInfo::GetModelInfo(int)` проверяет только
   верхнюю границу (`modelId < ms_modelInfoCount`) — при отрицательном индексе
   читается `ms_modelInfoPtrs[-1]` → краш (`CPed::Dress` держит
   `m_modelIndex = -1` при смене модели). Если обёртка ненадёжна — проверять
   границы в своей функции.
10. **Потоки `create_newthread` — только для независимых рабочих.** Каждый
    поток = отдельный `lua_State` (подробнее — `ПОТОКИ_CREATE_NEWTHREAD.md`).
    Из потока **НЕЛЬЗЯ** дёргать `create_marker*`/`remove_blip`/`create_*`:
    они пишут общие `markeron`/`mapcars`… **без мьютекса** → data race на
    `std::map` → плавающий краш через десятки секунд. Следить за объектом
    (маркер снять при уничтожении, HP цели) — **в главном цикле покадрово**;
    это и безопаснее, и отзывчивее (поток с `wait(100)` — задержка до 100 мс).
11. **«Слепые» покадровые циклы инструментировать.** Боевой цикл не оставляет
    трейсов (`isped`/`iscardead`/`getpedhealthf` не трейсятся) — краш в нём
    нельзя локализовать. Обязательно: счётчик кадров + `ma_trace` раз в N
    кадров (`riot: бой frame=… bitten=… killed=… esc=…`), а при крашах —
    `cpp_trace` на подозреваемой C++-функции (хвост `trace.txt` укажет на
    последний выполнившийся вызов).
12. **Форензика краша по `trace.txt`:** обрыв трейса + **нет** `destroy: ВХОД`
    и нет `mission_watch: игрок погиб/арестован` = **жёсткий краш** (segfault),
    а не штатный провал миссии; Lua-ошибка в `main()` не роняет игру (она
    молча умирает — `lua_resume` без проверки), её видно по исчезновению
    активности скрипта. `log.txt` при segfault чист.

## 5. Подводные камни платформы

- `ped_frozen(0)` = управление игроком ВЫКЛЮЧЕНО (заморожен), `ped_frozen(1)` —
  включено. Именование обратное смыслу.
- `end_mission()` вызывает destroy() — чистит ВСЁ созданное миссией; свои
  переменные-указатели при этом обесцениваются — обнулять и не использовать.
- `remove_fire(id)` стирает запись из внутренней map (иначе destroy() удалит
  огонь повторно). Все remove_* гигиеничны.
- `set_current_weapon_ped(ped, тип)` — положить оружие педу в руки (01B9).
  Сначала Giveweaponped (выдать + загрузить модель), потом эта функция.
- `set_ped_stay_when_attacked(ped, true)` — пед не сходит с места при атаке
  (0350), как «бригадир» с кольтом в Riot.
- `ped_in_point_in_radius(ped, x,y,z, rx,ry,rz)` — чистое расстояние по 3D,
  работает и в машине, и пешком (внутри sleep ~10мс — не злоупотреблять
  количеством вызовов в тик).
- `iscardead(car)` — авто уничтожено (для условий «уничтожь все грузовики»).
- `getpedhealth(victim) == 0` — пед мёртв; sethealth(e,n) добавляет +0.99.
- **Толпа с wait_state (бой, как в Riot):** педы создать с
  `set_ped_wait_state(ped, 29, 99999999)` + `ped_clean_threat` +
  `set_ped_personality(ped, 16)` + `set_ped_only_damaged_by_player(ped, true)`.
  Они стоят, пока игрок не ранит: `is_ped_health_greater(ped, 99) == false`
  → снять wait (`clean_ped_wait`) → `set_char_obj_kill_player_on_foot(ped,
  player)`. «Рассердить всех сразу» — `set_ped_personality(ped, 30)` +
  `ped_search_threat(ped, 16)` + `ped_search_threat(ped, 1)` каждому живому.
- **Выпадение оружия из трупа:** `get_dead_char_pickup_coords(ped)` вернёт
  x,y,z (про Z уже прибавить 0.5, как в оригинале `$2250 += 0.5`), затем
  `create_weapon_pickup(274, 3, 17, x, y, z)` (274 = модель colt45,
  патроны/тип 17). Так в оригинале из убитых зачинщиков падают кольты.
- **`set_ped_mood` действует на ИГРОКА, а не на педа** (обёртка 04E3
  SET_PLAYER_MOOD) — не путать с настроением толпы.
- Настроение игрока в миссии Riot ставится один раз после катсцены —
  `set_ped_mood(1, 60000)`, ровно как в оригинале.

  Initial.txt), поэтому `find_object_by_model(-33)` вернёт ПЕРВЫЙ объект пула,
  а не ворота. Искать ТОЛЬКО по координатам: `get_obj_in_cord(298.0, -313.6,
  11.0, 8.0)` (радиус 8 м) — вернёт именно ворота стройки.
- **Значок одежды — спрайт-блайп, а не квадратик.** В оригинале маркер
  магазина одежды — `02A8: ADD_SPRITE_BLIP_FOR_COORD ... 28` (спрайт 28,
  значок одежды), стройплощадка — `018A: ADD_BLIP_FOR_COORD` (обычный
  квадрат). На Lua: `dress_blip = radar_set_coord_blip(0, 95.4, -1135.5, 9.4,
  2, 2)` + `radar_set_blip_sprite(dress_blip, 28)`. НЕ использовать для
  одежды `createmarker` — это розовый квадратик, пользователь его не
  воспринимает как «значок одежды». Удалять `remove_blip`.
- **Сферу `create_sphere` ставить ТОЛЬКО там, где реальный триггер в 1-3 метра**
  (у точки переодевания radius 3.0), и НЕ ставить на большое событие:
  `create_sphere(x, y, z, 70.0)` «заливает» весь квартал и видна издалека —
  пользователь это явно отметил как недостаток.

### Жёсткие правила samопроверки (ОБЯЗАТЕЛЬНО перед заявлением «сделано»)

1. **Найти РЕАЛЬНУЮ причину, а не «идею».** Симптом ≠ причина. Три настоящих
   бага этой миссии ни разу не оказались теми, которые казались по первому
   взгляду. Каждый раз причина была в другом месте (тип-проверка C++, опкод
   с покадровой семантикой, C++ `sleep_for` на каждый вызов). Прежде чем менять
   код — открыть `log.txt`/`trace.txt` РЕАЛЬНОГО прогона и прочитать, что там.
2. **Сверять каждое движение объекта/педа с семантикой опкода в движке.**
   Не предполагать по имени: `SLIDE_OBJECT` = 0.1/кадр (нужен цикл),
   `SET_CHAR_WAIT_STATE 29` = стоит вечно (нужен 053D), `SET_CHAR_ONLY_DAMAGED_BY_PLAYER 1`
   = урон между педами запрещён. Искать реализацию в `re3-miami/src/control/Script4.cpp`
   и в `funcs.cpp` (больше всего багов было ИМЕННО там: `(L, 2)` = оператор-запятая,
   неверное число аргументов на проверке типа).
3. **C++-функции проверять по типам аргументов и семантике, а не «по аналогии».**
   `write_log`/`findobjinpool`/любые функции с `sleep_for` НЕ вызывать в кадровых
   циклах — это вешает игру. Перед добавлением функции в кадровый цикл — прочитать
   её реализацию.
4. **Каждое серьёзное изменение — отдельная правка + отдельная проверка.**
   Не валить в один коммит «фикс драки + ворота + охранников». Сначала чиним
   одно, ждём прогон пользователя, потом следующее. Практика показала: фиксы
   наслаиваются и конфликтуют (ворога двигалась, но зависла игра).
5. **Не приписывать себе недоказанное.** «Не подтверждено: полный E2E» — так
   и писать в MD. «Сработало у пользователя» — писать отдельно от «я поправил».
6. **Бэкап перед каждой правкой**: `misson X.lua.orig-<тег>`, чтобы откат был
   мгновенным. Откат — всегда назад к последнему РАБОЧЕМУ состоянию, а не к
   «красивому коду».
7. **Спрашивать пользователя о тестировании коротко и конкретно** («перезапусти
   и скажи: драка есть? ворота? зависло?»), а не «поверь мне».

## 1. ГЛАВНОЕ: все переменные — `local` (и ловушка «невидимого глобала»)

### Симптом

Миссия работает, но «отравляет» остальные скрипты: на общем `lua_State`
(все `.lua` из `lualoader/` крутятся на **одном** состоянии Lua) глобальные
переменные разных миссий пересекаются. В Riot файл **вообще не содержал ни
одного** `local` — `player`, `pp`, `step`, `truck1`, `gate`, `dress_blip`…
были глобалами. Другой скрипт, прочитав свой `player`, получал указатель из
Riot; миссия «меняла переменную нахождения игрока» в чужом коде.

### Как находить

```bash
# 1) хоть какой-то local есть?
grep -c local "misson X.lua"        # 0 = тревога

# 2) список всех ПЕРВЫХ присваиваний без local
grep -nP '^\s*[A-Za-z_]\w*\s*=[^=]' "misson X.lua" | grep -v local
```

Второе даёт и пере-присвоения — их надо отличать вручную: `step = 3` внутри
цикла — это запись в уже объявленный `local`, а не глобал.

### Правила

0. **Стилистическое правило пользователя (2-я ревизия):** поясняющий
   комментарий — ТОЛЬКО на той же строке, что и код/объявление; формат —
   `(оригинал ОПКОД … : что это)` в скобках. Отдельных comment-строк в теле
   миссии не писать (кроме документационного заголовка файла и этого MD).
   Примеры из `misson riot.lua`:
   `if step == 3 then  -- (оригинал @L4725d: главный цикл боя — пикетчик жив,
   здоровье ≤99 и толпа не взбешена → в бой, 053D+01CA)`;
   `local gate  -- (ворота стройки, объект -33) — открываются при эскалации`;
   `ped_search_threat(r, 1)  -- (оригинал 011A: угрозой считается игрок)`.

1. **Каждая переменная миссии — `local`** в блоке после `if Star_mission_marker(...)`.
   Включая «пустые» объявления-заголовки групп:
   ```lua
   local truck1, truck2, truck3    -- без local это не объявление, а no-op
   local mt1, mt2, mt3
   local obj1, obj2
   local agit1, agit2, leader
   local gate
   ```
   (голая строка `truck1, truck2, truck3` в Lua — просто выражение, она
   **ничего не объявляет**; миссия тихо работала на глобалах).
2. **Переменные внутри циклов — тоже `local`** (`skin`, `r` в теле `for`,
   `dx, dy, dz` при чтении координат).
3. `local pp = findplayer()` — **внутри** цикла миссии, на каждой итерации
   свой. Запасной вариант, если свежий не получился:
   `if pp == nil then pp = player end` (`player` — внешний `local`).
4. Пере-присвоения (`step = 3`, `dressed = 1`, `gate = get_obj_in_cord(...)`)
   пишутся **без** `local` — они ссылаются на объявленные ранее локалы.
5. Одноразовые флаги из оригинала («уже сработало») → отдельные `local` и
   сброс сразу после срабатывания: `dressed` ($2213), `law4_13_shown`,
   `agit1_drop`/`agit2_drop`, `escalated` ($2205), `gates_open` ($2206).

## 3. Опечатки в именах → «bad argument» в log.txt → висячие объекты

### Симптом

В `log.txt`: `bad argument in function remove_blip`. При этом скрипт
продолжает работать, а маркер стройки **навсегда остаётся на карте**.

### Механика (почему так тихо)

В строке была опечатка — склейка двух имён:
```lua
if site_blip ~= nil then remove_blip(site_blipriot_intensity) site_blip = nil end
```
`site_blipriot_intensity` — несуществующий глобал → `nil`. C++-функция
ловит `throw "bad argument"` через `try/catch` и **продолжает выполнение**:
реальный `remove_blip` не вызывается, маркер не снимается, а `site_blip = nil`
присваивается — Lua больше не попытается его удалить.

### Диагностика

1. `log.txt` пишется C++ через `writelog` — каждая строка `bad argument in
   function X` = в функцию X передан `nil`/несовместимый тип.
2. Искать опечатки в **имени переменной внутри вызова**: grep подозрительного
   имени по файлу — если встречается один-два раза в вызовах и ноль в
   объявлениях, это склейка/опечатка.
3. `trace.txt` подтвердит, что код после вызова выполнялся (трассы есть), а
   вот «снятия» не произошло.

### Правила

- Имена в `remove_*` / `set_*` вызовах писать только из объявленных `local`
  (см. §1). После правки — `grep` имени: оно должно встречаться и в объявлении,
  и в использовании.
- Все `remove_*`-вызовы оборачивать в `if x ~= nil then … x = nil end` —
  но **переменная в вызове должна быть тем же `x`**.
- Любая строка `bad argument in function …` в `log.txt` — это **реальный
  баг**, «само не рассосётся»: вызов молча ничего не сделал, объект завис в
  map-е плагина.

## 5. Стиль комментариев (требование пользователя)

Комментарий — **на той же строке, что и код**. Отдельных comment-строк в теле
миссии не должно быть (допускается один документационный заголовок в начале
файла — описание потока оригинала).

### Формат

```lua
set_riot_intensity(riot_intensity)  -- 0552 SET_RIOT_INTENSITY 127 — уровень беспорядков
```

- **Сначала опкод оригинала** (`ОПКОД ИМЯ АРГУМЕНТЫ`), потом `—` и короткое
  пояснение. Это связка Lua-вызова с оригинальным SCM — следующему переносу
  будет видно, какой опкод тут лежит.
- Комментарий **описывает**, а не приказывает: не «поставь педа», а
  «обычный горожанин» / «стоит, пока игрок не ранит».

### Объявления переменных — всегда с пояснением смысла

```lua
local step = 1          -- этап миссии: 1 = переодевание/подъезд к стройке, 3 = бой, nil = конец
local dressed = 0       -- переоделся ли в рабочего у Рафаэля ($2213)

```

Переменные оригинала (`$2213`, `$2205`, `$2206`…) полезно оставлять в
комментарии — это прямой мостик к SCM при разборе.

### Многострочные if

Комментарий ставится в конец строки с `then`:

```lua
if step == 3 and law4_13_shown == 0
 and ped_in_point_in_radius(pp, 299.0, -314.6, 11.4, 20.0, 20.0, 10.0) then  -- ШАГ 2: LAW4_13 — игрок БЛИЗКО к стройке (LOCATE 20 20 10)
```

### Заголовок-документация

В начале файла — блок `-- ====…` с построчным разбором потока оригинала
(этапы 1–7, координаты ключевых точек, ловушки вроде «модель -33 встречается
по всей карте»). Это единственный разрешённый многострочный комментарий.

## 6. Верификация файлов: байты, а не «как помнится»

При правке `.lua` сверять реальное содержимое файла **побайтово**:
инструменты чтения могут показывать «улучшенный» текст (например, добавлять
`local`, которого в файле нет). До начала правок:

```bash
grep -c local "misson X.lua"                 # реальные local
awk '{gsub(/\r$/,""); printf "%d\t%s\n", NR, $0}' "misson X.lua"   # точный текст + отступы
xxd -l 9 "misson X.lua"                      # efbb bf... = BOM на месте
file "misson X.lua"                          # UTF-8 (with BOM), with CRLF
luajit -bl "misson X.lua" >/dev/null && echo OK   # синтаксис
```

После правок:

```bash
# код не изменился — вычитка без комментариев, отличия д.б. только в комментах
strip() { tr -d '\r' < "$1" | sed 's/--[^\n]*//' | sed 's/[[:space:]]\+/ /g' | sed 's/^ //; s/ $//' | grep -v '^$'; }
strip "misson X.lua.orig" > /tmp/o.txt; strip "misson X.lua" > /tmp/n.txt
diff /tmp/o.txt /tmp/n.txt
```

**Кодировка:** `.lua` — UTF-8 **с BOM** + **CRLF**; MD-документы — UTF-8
**без** BOM, LF. При правке скриптом — не добавлять BOM повторно: декодируя
файл, ты получаешь BOM в тексте, дописывание ещё одного даёт двойной/тройной
BOM ( Lua это «проглотит», но `file` и другие инструменты — нет).

## 6.1 ПОЧЕМУ НЕ ВИДНЫ БЛАЙПЫ НА КАРТЕ — ЛОВУШКА `radar_set_coord_blip` (2-я ревизия, 20.09.2026)

Блайпы Riot (майка одежды + маркер бунта) в игре **не отображались**, хотя
`radar_set_coord_blip` возвращал валидный id, а `radar_set_blip_sprite` его не
ломал. Диагноз поставлен по движку (Radar.cpp reVC) и переписан в C++:

1. **Тип блайпа.** Для координатной метки нужен `BLIP_COORD = 4`
   (eBlipType: BLIP_NONE=0, BLIP_CAR=1, BLIP_CHAR=2, BLIP_OBJECT=3,
   BLIP_COORD=4, BLIP_CONTACTPOINT=5…). В Riot было `type = 0`
   (BLIP_NONE) → движок блайп не рисует.
2. **Сырой `CRadar::SetCoordBlip` не рисует в этом билде.** Даже с
   `type=4` метка не появлялась: движок рисует миникарту через
   `DrawBlips()` — блайп попадает в цикл рисования только через
   `m_eRadarSprite`, и сырой вызов без `ChangeBlipScale` остаётся «потухшим».
   **Работает** тот же путь, что идёт штатные опкоды через
   `Command<>` (движок сам делает все подготовительные шаги,
   `ChangeBlipScale(handle, 3)` внутри `018A`).
3. **Решение — оригинальные опкоды, как в исходнике:**
   - `018A ADD_BLIP_FOR_COORD x y z &id` → `CRadar::SetCoordBlip(BLIP_COORD,
     pos, 5, BLIP_DISPLAY_BOTH)` + `ChangeBlipScale(…, 3)` — квадрат (цвет 5);
     для ЖЁЛТОГО бунта после создания вызвать
     `radar_change_blip_colour(id, 4)` (оригинал `016B CHANGE_BLIP_COLOUR`,
     eBlipColour: YELLOW=4). Виден и на карте, и в мире.
   - `02A8 ADD_SPRITE_BLIP_FOR_COORD x y z sprite &id` →
     `SetCoordBlip(BLIP_COORD, pos, 5, BLIP_DISPLAY_BOTH)` +
     `CRadar::SetBlipSprite(id, sprite)` — спрайт-блайп (значок одежды,
     sprite 28).
   Добавлены C++-обёртки **`radar_add_blip_for_coord(x,y,z) → id`** и
   **`radar_add_sprite_blip_for_coord(x,y,z,sprite) → id`** (funcs.cpp,
   регистрации `register.cpp:469-470`), обе кладут id в `markeron` →
   `destroy()` снимает автоматически (как `createblip`/`createmarker`).
   Удалять — обычным `remove_blip(id)` (он делает `COMMAND_REMOVE_BLIP`
   + стирает запись из `markeron`).

> ⛔ **Больше НЕ использовать `radar_set_coord_blip`/`radar_set_blip_sprite`
> для миссионных маркеров на карте** — это сырые вызовы, не видимые в этом
> билде. Рабочие — `radar_add_blip_for_coord` (018A) и
> `radar_add_sprite_blip_for_coord` (02A8). `radar_set_coord_blip` оставить
> только для диагностики/кратковременных меток.

### 5-я ревизия (20.09.2026): детектор урона «HP упал относительно прошлого кадра» — бунт теперь стартует от ЛЮБОГО урона, даже минимального

- **Почему бунт не стартовал**: детектор был `not is_ped_health_greater(r, 99)`
  (оригинал `8184 NOT IS_CHAR_HEALTH_GREATER $2177 99`). `is_ped_health_greater`
  сравнивает float-HP **строго** с порогом: `m_fHealth > 99`. Удар на 0.5 по
  полному HP (100 → 99.5) даёт `99.5 > 99` = **true** → `not` = false → тик не
  выставляется. Порог ловит только урон, роняющий HP **≤ 99**. К тому же
  `getpedhealth` возвращает ЦЕЛОЕ (усечение float) — для микро-урона ненадёжно.
- **Решение**: новая C-функция **`getpedhealthf(ped)` → float** (добавлена в
  `funcs.cpp:479` рядом с `getpedhealth`, объявлена в `funcs.h`,
  зарегистрирована в `register.cpp`, реализация идентична, но
  `lua_pushnumber((double)ped->m_fHealth)`). В `mod.lua` НЕ переопределена,
  поэтому вызывается напрямую в C, без trace-спама.
- **Новая логика боя**: для каждого живого пикетчика хранится `hp_prev[i]`
  (float-HP прошлого кадра, инициализируется при создании). Условие тика
  теперь `h < hp_prev[i]` — **любое** уменьшение HP, даже на 0.01, даёт тик.
  После проверки `hp_prev[i] = h` (следующий кадр сравнивается с этим).
  Мёртвый пикетчик как раньше: `killed` (для эскалации) без bite.
- **Файлы**: `misson riot.lua` (обновлён, 23661 байт, sha256
  `ed1d75b8…c2f3b99125`), `.asi` пересобран через `build.sh`
  20.09.2026 06:54 (6 405 365 байт), Бэкап: `misson riot.lua.orig-bitecheck`.

## 3. Правило: isped ПЕРЕД getpedcoordes (главная причина вылетов)

`getpedcoordes` (`funcs.cpp:964`) вызывает `findpedinpool(p)` и **разыменовывает
результат без NULL-проверки**:
```cpp
CPed* ped = findpedinpool(p);
lua_pushnumber(L, ped->GetPosition().x);   // ped == NULL → SEGFAULT
```
`findpedinpool(NULL)` возвращает NULL (не крашит), но любая невалидная
передача далее — вылет. **Всегда**:
```lua
if isped(pp) then local x, y = getpedcoordes(pp) ... end
```
Особенно в **кадровых** местах (ИИ охраны каждые 500 мс) — там `findplayer()`
может вернуть nil в любой момент.

# Заметка о переносе миссии: принципы и подходы (на примере "Riot")

Перенос оригинальных миссий GTA Vice City (написанных на SCM/Sanny Builder) на Lua для плагина lualoader требует не прямого перевода строк, а адаптации логики под архитектуру плагина. Оригинальный движок использует потоки (threads) и опкоды, а lualoader работает через конечные автоматы (state machines) в главном цикле. 

Ниже приведены основные принципы, которые были применены при переносе миссии «Riot» (Мятеж).

### 1. Архитектура: Функции ВЫШЕ `main()`
Оригинальный SCM-код часто представляет собой «спагетти» из меток и `GOTO`. В Lua весь код структурируется:
- Вспомогательные функции (спавн сцены, проверка статусов, катсцены, очистка) выносятся на уровень файла **перед** `main()`.
- В `main()` остаётся только внешний цикл ожидания подъезда к маркеру и внутренний цикл (`while true == Getflagmission() do wait()`) с конечным автоматом (переменная `step`).
- Функции общаются с `main` через параметры и возврат нескольких значений. Состояние миссии (счётчики, флаги) живёт в локальных переменных `main`.

### 2. Отказ от потоков в пользу покадровых проверок
Оригинальный движок мог запустить отдельный поток (thread), чтобы следить за здоровьем грузовика и снимать маркер при его уничтожении. В lualoader **потоки использовать нельзя** — они работают в изолированных `lua_State` и вызывают гонку данных (data race) в общих C++ коллекциях (что приводит к крашу).
- **Принцип:** Любая проверка состояния объекта (здоровье, смерть, уничтожение) делается покадрово в главном цикле.
- **Реализация:** Создаются функции-чекеры (например, `check_trucks_destroyed(trucks, markers)`), которые вызываются каждый кадр. Они возвращают `true/false`, а внутри себя безопасно снимают маркеры, если объект мертв.

### 3. Использование списков (таблиц Lua)
Вместо создания 10–20 одиночных переменных для педов или машин, всё собирается в таблицы (списки).
- `spawn_trucks()` возвращает `trucks` и `markers` — две таблицы с индексами 1, 2, 3.
- Это позволяет перебирать объекты в цикле `for i=1,3 do`, массово проверять их статус и массово удалять при очистке сцены (`cleanup_scene`).
- Аналогично со списками рабочих: `spawn_rioters()` возвращает списки сундости (педы, флаги урона, HP).

### 4. Безопасность и NULL-указатели
Игра может удалить объект (педа, машину) из пула в любой момент (например, игрок взорвал машину, и игра убрала обломки). Если Lua-функция обратится к удаленному указателю, игра вылетит (segfault).
- **Принцип:** Перед любым действием с объектом идёт проверка на валидность.
- `if isped(r) and not ispeddead(r) then` — стандартный паттерн перед выдачей оружия или назначения цели.
- `if trucks[i] ~= nil and isvehicle(trucks[i]) and not iscardead(trucks[i])` — проверка авто перед снятием маркера.

### 5. Изоляция состояния (Только `local`)
Все `.lua` скрипты в папке `lualoader/` работают на **одном** общем `lua_State`. Если написать `step = 1` без `local`, эта переменная перетрется другим скриптом (например, автоаимом или другой миссией), и всё сломается.
- **Принцип:** Абсолютно все переменные внутри миссии объявляются строго как `local`. Никаких глобалов.

### 6. Гигиена мира: Очистка и сброс глобальных эффектов
Миссия не должна оставлять мусор после завершения (успех или провал).
- Все созданные сущности (педы, машины, объекты, блайпы, сферы) удаляются через специально написанную функцию `cleanup_scene()`.
- Если миссия изменяла глобальные настройки игры (например, `set_riot_intensity(127)` или `request_animation("RIOT")`), они **обязательно** сбрасываются в 0 или выгружаются при выходе из цикла миссии.

### 7. Замена отсутствующих опкодов
В оригинале были катсцены (`LOAD_CUTSCENE`) и пикапы одежды (`CREATE_CLOTHES_PICKUP`), которых нет в API lualoader.
- Катсцены заменяются на текстовые реплики (`printmessage`) + управление камерой (`set_camera_position` / `camera_at_point` / `restore_camera`).
- Подбор одежды определяется не флагом пикапа, а проверкой расстояния (`ped_in_point_in_radius`) + вызовом `set_skin` за черным экраном (`fade`).
- Урон толпе определяется не опкодом `IS_CHAR_HEALTH_GREATER`, а покадровым сравнением float-здоровья (`getpedhealthf`) с прошлым кадром.

### 8. Инлайн координат
Координаты (X, Y, Z) пишутся прямо в местах вызова функций (например, `Createcar("MODEL_SPAND", 286.7, -302.1, 11.9)`), а не выносятся в блок констант в начале файла. Это уменьшает "простыни" кода и делает чтение логики локализованным.

### 9. Стиль комментариев (требование пользователя)
- Код должен быть самодокументируемым через короткие комментарии.
- Комментарии ставятся **на той же строке**, что и код, через 1 пробел от него.
- Формат: короткое описание действия (например, `ped_frozen(1) -- Разморозить`). Никаких многострочных простыней текста внутри функций.

---
**Итог:** Перенос миссии сводится к переписыванию линейной логики с `GOTO` в структуру "Функции + State-Machine в главном цикле", с максимальным использованием таблиц для групп объектов, строжайшей проверкой указателей и полным отказом от потоков в пользу покадровых проверок.
