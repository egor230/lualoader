## 1. Что это за плагин

**lualoader** — ASI-плагин для оригинальной GTA Vice City (gta-vc.exe 1.0/1.1),
позволяющий писать моды на скриптовом языке **Lua 5.4.9** (миграция с 5.3 —
см. `ОТЧЁТ_миграция.md`). Скрипты из папки
`lualoader/` автоматически загружаются и выполняются при запуске игры.

- Плагин сделан против **Plugin-SDK** (плюс-инклуды `plugin_vc` — Vice City
  ветка SDK).
- Готовая DLL: `lualoader.asi`, кладётся в корень игры рядом с `gta-vc.exe`.
- Лог работы: `lualoader/log.txt` (какие скрипты загружены, ошибки).

Главный файл: `gta-vc.exe` 1.1 EN (Steam). Сборка идёт кросс-компиляцией из
Linux под Windows (i686-w64-mingw32), поэтому все пути в командах — Linux-монтирования.

## 4. Как устроен сам плагин (код)

- `funcs.h` + `funcs.cpp` — прототипы и реализации Lua-функций соответственно
  (до 19.09.2026 всё лежало в одном funcs.h; стиль автора сохранён — см. пример).
  Типичная Lua-функция выглядит так:
  ```cpp
  int имя_функции(lua_State* L) {// комментарий на русском, что делает.
      try {
          if (LUA_TLIGHTUSERDATA == lua_type(L, 1) && LUA_TNUMBER == lua_type(L, 2)) {// указатель на педа/авто.
              const void* p = lua_topointer(L, 1);
              CVehicle* car = findcarinpool(p);// получить указатель на авто.
              float value = lua_tonumber(L, 2);
              car->m_fMass += value;
              return 0;
          }
          else { throw "bad argument in function имя_функции"; }
      }
      catch (const char* x) { writelog(x); }// записать ошибку в файл.
      return 0;
  };
  ```
  - Аргумент «указатель на объект» передаётся как **lightuserdata**
    (`LUA_TLIGHTUSERDATA`, получается `lua_topointer`).
  - Игровые объекты ищутся по пулам: `findcarinpool(p)`, `findpedinpool(p)`.
  - Ошибки оформляются через `throw`/`catch` + `writelog`.
  - Комментарии внутри кода пишутся по-русски, стиль автора сохранён.

- `register.cpp` — функция `funs(lua_State* L)`, в которой регистрируются функции:
  ```cpp
  lua_register(L, "имя_из_lua", имя_функции_c); // номер комментарий.
  ```
  Вызывается из `plugin.cpp` (`startscipt`, `create_newthread`) при создании
  каждого `lua_State`.

- `plugin.cpp` — точка входа ASI (Events), загрузка скриптов (цикл по файлам
  папки `lualoader/`), планировщик `ma_sched_frame()` на игровом потоке,
  count-хук `hookFunc`, остановка/пауза/перезагрузка. Ключевое правило
  исполнения: **все скрипты крутятся на одном игровом потоке**, а не на
  отдельных `std::thread` на скрипт. `wait()` паркует состояние через
  `ma_sched_park()`, busy-циклы вытесняются по бюджету кадра. В
  `non-yieldable` окнах (`require`, `dofile`, парсинг, меж-резюмы) `lua_yield`
  запрещён — тогда функции паркуются без yield.

- Примеры уже добавленных функций (стиль-образец). ВАЖНО: точные текущие
  версии см. в разделах 4.1 и 4.2 ниже — не копировать вслепую.

**`set_car_mass(car, 3000)` — увеличение массы (funcs.h:8193).**
- Масса НЕ участвует в разгоне: ускорение считается только из
  `fEngineAcceleration` в `CalculateDriveAcceleration` (Automobile.cpp:836,
  Transmission.cpp:90-133). Масса влияет лишь на столкновения/подвеску.
- Поэтому используется штатный опкод `Command<COMMAND_SET_CAR_HEAVY>(...)`
  (0x1EC, Script2.cpp:1489): ставит флаг `bIsHeavy` (+2x в столкновениях,
  Physical.cpp:610-623, подвеска *0.75/*2.0 — Physical.cpp:509,526) и сам
  задаёт 3x массы / 5x поворотной массы. Потом `m_fMass += value;
  m_fTurnMass += value` (перкопия у самой машины, офсеты 0xB8/0xBC).
- Флаг `bIsHeavy` после вызова остаётся навсегда — осознанно.
- Ручной бит bIsHeavy в VC не писать: SDK его не объявляет, оффсет
  неизвестен — только через опкод.

**`set_car_acceleration(car, 0.2)` — ускорение (funcs.h:8217).**
- Поле правильное: `m_pHandlingData->m_transmissionData.m_fEngineAcceleration`
  (0x4C) — читается каждый кадр, работает «живьём» без пересчётов.
- ВНИМАНИЕ, масштаб: в памяти хранится КОНВЕРТИРОВАННОЕ значение =
  cfg×0.4/2500 (LoadHandlingData HandlingMgr.cpp:301 + ConvertDataToGameUnits).
- Писать 0.2 «как в cfg» напрямую = ~6250x сильнее задуманного (дикая
  «ракета»). Если нужна честная cfg-семантика — писать `value*0.4f/2500.0f`
  (решение с пользователем не принято, сейчас пишется как есть).

**`set_car_max_speed(car, 100)` — макс. скорость, км/ч (funcs.h:8235).**
- ИСПРАВЛЕН КРИТИЧНЫЙ БАГ (было `m_fMaxSpeed` = 0x54 — это КРУИЗНАЯ
  скорость ИИ-автопилота, fMaxCruiseVelocity, Vehicle.cpp:1247; на
  скорость игрока не влияет вообще).
- Настоящий лимитер — `m_fMaxGearVelocity` (0x50 = reVC `fMaxVelocity`):
  `CalculateDriveAcceleration` каждый кадр проверяет
  `if (fVelocity > fMaxVelocity) return 0;` (Transmission.cpp:71; в exe
  адрес 0x5B2E20 читает [ecx+0x50], поле 0x54 физикой не читается вовсе).
- После записи НУЖНО пересчитать передачи — иначе верхняя передача
  держит старый таргет и новая скорость недостижима:
  ```cpp
  (*(void(__thiscall*)(void*))0x5B3120)(&car->m_pHandlingData->m_transmissionData);
  // cTransmission::InitGearRatios — пересчёт Gears[] из нового fMaxVelocity
  ```
- Единицы: в памяти значение = км/ч / 180 (ConvertDataToGameUnits:
  `fMaxVelocity *= 1000/(3600*50)`), поэтому в функции делится на 180.
- SDK-имена полей cTransmission ОБМАНЫВАЮТ: `m_fMaxGearVelocity` (0x50)
  = reVC `fMaxVelocity` (лимит!), `m_fMaxSpeed` (0x54) = reVC
  `fMaxCruiseVelocity` (AI-круиз), `m_fMinGearVelocity` (0x58) =
  `fMaxReverseVelocity`, `m_fCurrentSpeed` (0x5C) = `fCurVelocity`.
  Раскладка cTransmission (SDK cTransmission.h:37-41): gears[6]=0x0,
  nDriveType 0x48, nEngineType 0x49, nNumberOfGears 0x4A, flags 0x4B,
  accel 0x4C, maxGearVel 0x50, maxSpeed 0x54, minGearVel 0x58, curSpeed 0x5C.

**`set_car_traction(car, 0.9)` — сцепление (funcs.h:8264).**
- Поле `m_pHandlingData->fTractionMultiplier` (0x30) — правильное, без
  конвертации (значение в памяти = cfg-значению), читается каждый кадр
  (Automobile.cpp:903, Bike.cpp:779: `traction *= fTractionMultiplier/4.0f`).

**Общая ГРАБЛЯ характеристик**: `m_pHandlingData` — указатель на ГЛОБАЛЬНУЮ
запись handling (общая для ВСЕХ машин модели). Ускорение/макс.скорость/
сцепление меняются у всей модели целиком, а не у конкретной машины.
Масса (m_fMass/m_fTurnMass у самой машины) — наоборот, перэкземплярная.
До смены игры правки не откатываются.

### 4.4 Подсистема миссий: флаг, сторож и уничтожение (сессии 10–14)

Подробно — документ 03 (структура/ошибки) и часть 4 документа 03
(дизайн флага). Здесь — интерфейс, который надо знать перед любой правкой.

**Флаг миссии** — общий для всей игры байт в ScriptSpace (`0x978748`):
- `getflagmission` / `setflagmission` (C++, `funcs.h`) — тупой геттер/сеттер.
- **`Getflagmission` / `Setflagmission` (с большой буквы, C++, `funcs.h`) —
  «умные»: поднимают (или обновляют) кооперативный сторож
  `ma_task_mission_watch`, который крутится в `ma_tasks_frame()` на игровом
  потоке раз в 100 мс: погиб/арестован игрок → «Миссия провалена» + флаг
  `false` + `destroy()`; флаг сменился сам / загрузка / teardown → выход.**
  Сторож **ровно один**: повторный вызов обновляет его `lua_State`, а не
  создаёт второй. Регистрация — `register.cpp` (строки 63–64). Lua-версии
  этих функций в `mod.lua` быть НЕ должно (перекроют C++).

**Уничтожение — одна функция `destroy(lua_State* L)`** (`funcs.h`, регистрация —
`register.cpp`). Мёртвый дубль `all_destroy` удалён.
Порядок очистки: маркеры → сферы → пикапы → огни → звуки → **авто** (с высадкой
сидящих) → **педы** (с высадкой из авто и `ClearObjective`) → объекты → сброс
короны → **снятие держаний моделей** (`ma_stream_let_go_all((void*)L)` — строго
ПОСЛЕ удаления сущностей, правило 27.10). Хелперы: `warp_out_car_occupants`,
`warp_ped_out_of_car`, `safe_remove_car` (проверка висячего указателя через пул →
высадка → `MARK_CAR_AS_NO_LONGER_NEEDED` (0233); **без** `CWorld::Remove`).
Любая функция создания кладёт объект в свой список (`mappeds`/`mapcars`/`mapobjs`/
`pickupsids`/`markeron`/`spheres`/`firesids`/`soundsids`), любая `remove_*` — стирает
(см. полный реестр: `КАК_НАПИСАТЬ_МИССИИ.md` §5.9). Модель созданной сущности
**держится** (`hold_model`) до её удаления; ранний `MARK`/`release_model` запрещён.

**Трассировка** — `cpp_trace(msg)` / `cpp_tracef(fmt, ...)` (`funcs.h`): пишут
`C++| <msg>` в `lualoader/log.txt` (персистентный поток, flush ≤ 100 мс).
С 24.10.2026 — только ошибки и редкие события, без покадровых строк.

## 6. Как добавить новую Lua-функцию (шаги)

1. В `funcs.h` рядом с похожими добавить ПРОТОТИП:
   ```cpp
   int новая_функция(lua_State* L); // русский комментарий + пример использования.
   ```
   (Если для функции-образца прототипа не было — см. блок «прототипы функций
   массового расширения API» в конце funcs.h, туда можно дописать.)
2. В `funcs.cpp` добавить РЕАЛИЗАЦИЮ (рядом с группой однотипных функций;
   если пользователь сказал «после функции XXX» — вставить сразу после неё).
3. В `register.cpp` (функция `funs`) добавить строку регистрации рядом со
   смежными:
   ```cpp
   lua_register(L, "имя_в_lua", новая_функция); // номер комментарий.
   ```
   Номера в комментариях — сквозная нумерация, следить чтобы не было повторов.
4. Собрать (`build.sh`), проверить `log.txt` после запуска игры.

ПРИМЕЧАНИЕ о порядке: `register.cpp` и `plugin.cpp` видят функцию только через
прототип в `funcs.h` — без него будет `use of undeclared identifier` (до 19.09.2026
одно определение в одном funcs.h служило объявлением, теперь TU три).

## 7. Ключевые правила и «грабли» (НЕ нарушать)

- **⛔ ГЛАВНОЕ (директива пользователя, обновлена 19.10.2026): работать ТОЛЬКО над
  моделями — загрузка/выгрузка моделей и получение модели скина главного героя
  (`get_player_skin`), плюс создание автомобилей/объектов/педов.** Шрифты — не
  направление работы: шумные сторожа/INT3 не возвращать. **Уточнение 27.10.2026:**
  вернувшийся `0x551E0D` — это переполнение буфера шаблона сообщения (одна запись
  длиннее `0x400` затирает курсор `[0x70975C]`), а не «мусорный стиль из ниоткуда»;
  закрыт тихим `PRINT-CLAMP` (док 00, блок 27.10). Не-причины (тексты, стили,
  сообщения, очередь как «источник») — игнорировать (документ 00, блок
  «⛔ ДИРЕКТИВА» + «УКАЗАНИЕ БУДУЩИМ СЕССИЯМ»).
- **⛔ МОДЕЛЬНЫЙ ЖИЗНЕННЫЙ ЦИКЛ — ОДИН ПОРЯДОК (27.10.2026):**
  **загрузить → создать → ДЕРЖАТЬ → отпустить только после удаления сущности.**
  - после успешного `CREATE_*` — `hold_model(L, model)` (обычные id) или
    `hold_model_special(L, slot, name)` (спец-слоты 109..116); модель не
    выгружается, пока жив пед/авто/объект;
  - `MARK (0249)`/`release_model` по живой сущности **запрещены** — прежняя
    формула «refCount > 0, значит MARK безопасен» отменена: движок мог выгрузить
    модель и удалить клэмп, пока указатель на сущность ещё использовался;
  - снятие держания — только `destroy(L)` **ПОСЛЕ** удаления сущностей
    (`ma_stream_let_go_all`), явный Lua `releasemodel` или полный reload
    (`ma_stream_let_go_everything`);
  - **пикапы — исключение:** объект пикапа сам держит ref модели, поэтому после
    создания у них допустим `release_model` (канон SCM `029B → 038B → 00A5 → 0249`);
  - **`set_skin`:** `0352 UNDRESS_CHAR` → `038B LOAD_ALL_MODELS_NOW` →
    `0248 HasModelLoaded` → `0353 DRESS_CHAR` внутри ОДНОГО `ma_cmdq_defer`,
    без предварительного `RequestSpecialModel`;
  - `load_model_before_avalible` **не трогать** (директива пользователя).
- **Стиль автора**: try/catch + `writelog`, комментарии по-русски, скобки и
  отступы как в соседних функциях. Не «переписывать стиль под себя».
- **Не трогать хрупкие места**: потоковые/мутекс-механики, деструкторы,
  сырые вызовы типа `CMatrix::SetRotate*`, OnAMissionFlag, гравитацию и т.п.
  Править точечно, под задачу.
- **Числа-хардкоды** игровых функций, где известны символы SDK, заменять на
  символы (пример уже сделан при миграции: GetHeading, FrontEndMenuManager,
  gGameState, CTimer, TheCamera, CWanted, DoorsExample). Но новые офсеты НЕ
  изобретать без проверки в `gta vc база` или SDK.
- `findcarinpool`/`findpedinpool` обходят пул — каждый кадр нагружают; в
  циклах типа `while true do wait()` стараться брать указатель один раз.
- Если правки касаются сценария Lua (`.lua`), их правят в `lualoader/*.lua`
  напрямую, сборка плагина при этом не нужна.
- После правки всегда **проверять сборку** или синтаксис; «готово» говорить
  только после проверки (см. раздел 8).
- **Сырые адреса функций**: адреса из `gta vc база/ОТЧЁТ_функции_gta-vc_steam.md`
  (база gta-vc_steam.idb) для РЯДА функций НЕ совпадают с установленным
  `gta-vc.exe` (примеры мусора при дизасме: 0x5B2F50, 0x5AAC50). Адреса,
  которые уже работают в funcs.h (0x4DF450/0x4DF4F0/0x4E3690), и адреса из
  файлов `Plugin-SDK/plugin_vc/game_vc/*.cpp` (напр. InitGearRatios
  0x5B3120, CalculateDriveAcceleration 0x5B2E20, GetWeaponInfo 0x5D5710)
  установленному exe СООТВЕТСТВУЮТ — SDK собран под него. Новый сырой адрес
  брать из SDK; если из отчёта — сначала проверить.
- **Проверка адреса перед сырым вызовом** (дизасм установленного exe):
  ```bash
  pip3 install --break-system-packages pefile capstone   # один раз
  python3 -c "import pefile; from capstone import Cs,CS_ARCH_X86,CS_MODE_32
  pe=pefile.PE('gta-vc.exe',fast_load=True); data=open('gta-vc.exe','rb').read()
  off=pe.get_offset_from_rva(0xАДРЕС-0x400000)
  [print('%-8s %s'%(i.mnemonic,i.op_str)) for i in Cs(CS_ARCH_X86,CS_MODE_32).disasm(data[off:off+0x40],0xАДРЕС)]"
  ```
  (запускать из корня игры). Начало вида `in al,5` / `add al,0xd9` / `pop ecx`
  без пролога = адрес НЕ той версии, вызывать нельзя. Нормальное начало —
  push/sub esp/mov ebx,ecx и т.п. objdump PE не парсит («file format not
  recognized») — не пытаться.
- **⛔ ABI `CVector` (критичнейшая грабля, 18.09.2026).** В `Plugin-SDK/shared/game/CVector.h`
  копирующий конструктор должен быть `= default` (из `CVectorImplementation.h`
  внешнее определение удалено). Пользовательский copy-ctor делает класс
  нетривиальным → clang/MinGW передаёт его **по скрытой ссылке** (4 байта), а
  игра (`0x521840` и др.) ждёт **12 байт по значению** (`ret 0x10`) → мусорные
  координаты + порча стека → вылет на ~15 местах `SetObjective(OBJ, pos)` и
  `SetSeek`. Апстрим собирается MSVC (там ABI иной), поэтому баг «дремал».
  **НИКОГДА не откатывать фикс**; при каждом обновлении SDK — переносить патч
  заново и перепроверять толкатель дизасмом (`i686-w64-mingw32-objdump -dr`:
  чистый `jmp *%eax`, без `push %esp`/`sub $0xc`). Бэкапы:
  `*.orig-presdk-abifix`.
- **Игровые вызовы — ТОЛЬКО из игрового потока.** Не поднимать
  `std::thread(...).detach()` для дёрганья `Command<>` — он использует общий
  `static CRunningScript` (`ScriptCommands.h`), гонка → зависание/вылет
  (баг `expectations` в `Createcar`, сессия 13). Нужен отложенный запуск —
  через `ma_sched_scan()`/`ma_sched_spawn()` и планировщик `ma_sched_frame()`.
- **Общий `lua_State` на все скрипты.** Каждый `.lua` имеет своё `lua_State`,
  но все состояния крутятся на одном игровом потоке планировщика → глобалы
  разных скриптов **не пересекаются**, однако общие C++ `static` (карты объектов,
  маркеров и т. п.) пишутся только из игрового потока. Правило: **все переменные
  миссии — `local`**, а `star_mission_marker` и другие C++-статические объекты
  требуют **ровно ОДНА миссия** в папке `lualoader/`.
- **`lua_yield` из C — только в yieldable-контексте.** В `non-yieldable` окнах
  (`require`, `dofile`, парсинг, меж-резюмы) `lua_yield(L, 0)` бросает
  `attempt to yield from outside a coroutine` и убивает скрипт. Все C-функции,
  делающие `lua_yield` (`wait`, `my_yield`, `newthread`, count-хук), обязаны
  проверять `lua_isyieldable(L)` и в `non-yieldable` окне парковаться через
  `ma_sched_park` **без** `lua_yield`. Это и есть фикс `mod.lua:82` при
  `require("lualoader/mod")`.
- **Кодировки**: `.lua` — UTF-8 **с BOM** + **CRLF**; MD-документы — UTF-8 без
  BOM, LF. Старые `.lua` (autoaim.lua) лежат в cp1251 — правки делать
  побайтовым копированием, не вставляя русские комментарии в этих файлах.
- **`funcs.h` может «откатиться» извне** (сторонний редактор на Windows-стороне
  сохранял старую копию поверх смонтированного файла): перед «готово»
  сверять число строк/регистраций с ожидаемыми (баг сессии 5).
- **⛔ Инклуд `.cpp` из SDK — только в funcs.cpp.** В funcs.h исторически висели
  `#include "CAnimManager.cpp"` и `#include "CBaseModelInfo.cpp"` (в SDK для
  этих классов нет отдельных определений статических членов, автор подключал
  исходники напрямую). Пока всё было одним TU, это работало; при 3 TU
  статические члены (`CAnimManager::ms_aAnimations` и др.) определялись в
  каждом .o → `повторное определение` на линковке. Теперь оба инклуда — в
  **funcs.cpp** (единственный TU, использующий эти классы; plugin.cpp и
  register.cpp их не трогают). НЕ возвращать в funcs.h и НЕ подключать в
  другие .cpp.
- **Любая функция, на которую ссылается `register.cpp`, должна иметь прототип в
  `funcs.h`** (345 функций этапов 13–17 его не имели — работало только в

## Часть 3. Текущая архитектура (27.10.2026)

Подробный разбор причин и планировщика — документ 00 §0-I. Здесь — карта.

### 3.1 Поток исполнения

```
Events::gameProcessEvent (игровой поток)
  ├─ ma_task_start_keyboard()      клавиатура/пауза
  ├─ [ma_tasks_frame()]            задачи: getcord/turncar/expectations/mission_watch
  ├─ [lifecycle_tick()]            scan при входе в игру, teardown при выходе
  ├─ [ma_sched_frame()]            прокачка Lua-корутин
  ├─ spite::draw / corona::draw    отрисовка
  └─ iters++                       счётчик кадров для is_wanted_level
```

* Скрипты — корутины на одном игровом потоке; ноль OS-потоков на `.lua`.
* `wait(ms)` = `ma_sched_park` + `lua_yield`; busy-цикл вытесняется count-хуком
  (слайс 1 мс / проход 6 мс).
* `create_newthread` = `ma_sched_spawn` — новый экземпляр в тот же планировщик.
* Скобки `[...]` — **история диагностического режима 24.10**; с 25.10 pump-вызовы
  включены (планировщик работает).

### 3.2 `Command<>` и игровая память

* Очередь `LUALOADER_CMDQ`: вызов из чужого потока → `ma_cmdq_defer` → задание
  исполняется на игровом потоке в `gameProcessEvent`; игровой поток никогда не
  блокируется на мьютексе (`try_lock`, при занятом — пропуск кадра).
* `ma_cmdq_post` — fire-and-forget без ожидания.
* `ma_streaming`: запросы моделей шлются в кадре; `ma_stream_wait` паркует корутину
  на 32 мс и перепроверяет движок (не однократная проверка). После успешного
  `CREATE_*` модель **ДЕРЖИТСЯ** (`hold_model`/`hold_model_special`, счётчик
  `holds`); снятие — только после удаления сущности (`destroy` →
  `ma_stream_let_go_all`), по явному `releasemodel` или при reload.

### 3.3 Lifecycle и teardown

| Событие | Что происходит |
|---|---|
| Ctrl | `teardown_all(true)` → `ma_sched_request_teardown(true)` → разборка и повторный scan на игровом потоке |
| clrfl | `scripts_disabled`, `star_thread::set(false)`, `teardown_all(false)` — без рестарта |
| Выход в меню (`gGameState != 9`) | `teardown_all(false)`, `scripts_started=false` |
| Загрузка сейва | двухфазный teardown: `kill_resume` + count-хук бросают `SCRIPT_STOPPED_BY_CPP` |

Финализация: `onScriptTerminate` → `destroy` → снятие из реестров; всё на игровом
потоке. Владелец закрывает своё состояние, сирот добивает общий свип.

  реальная разборка идёт на игровом потоке.
* `lifecycle_tick()` — scan при входе в игру (`gGameState == 9`) и teardown при выходе.
* `search_scripts()`, `start_lualoder()`, `final_scripts()`, `reload()`, `pause_scripts()`.
* Crash-фильтры: `lua_crash_write`, `lua_crash_filter`, `lua_vectored_filter`,
  `lua_terminate_handler`, `lua_atexit_handler`, `install_crash_filter`.
* `class Message`: `ma_diag::install()` → `ma_cmdq_install_hook()` →
  `ma_stream_install_hook()`, затем подписки `Events::gameProcessEvent` и
  `vehicleRenderEvent`.
* `create_newthread` → `ma_sched_spawn` (новый экземпляр в тот же планировщик).

## 1. Главное правило: единственный писатель — игровой поток

Весь Lua-код и все игровые вызовы (`Command<>`, `ScriptSpace`, `CMessages::…`)
исполняются только на игровом потоке — внутри `Events::gameProcessEvent` через
`ma_sched_frame()` и `ma_tasks_frame()`.

* НЕ добавляй `std::thread(...).detach()`, который трогает Lua или игровую память.
* Отложенный запуск — только через `ma_sched_scan()` / `ma_sched_spawn()`.
* Код из другого потока имеет право трогать только `std::atomic`-флаги.
* `teardown_all()` — эталон: только атомики, разборка на игровом потоке.

## 2. Горячий путь (`gameProcessEvent`)

Каждый кадр выполняется этот код. Он НЕ должен:

* писать в файл (никакого `WriteFile`/`FlushFileBuffers` на кадр);
* аллоцировать `std::vector`/`std::string` на кадр;
* держать мьютекс во время исполнения Lua;
* звать `sleep_for` (застопорит кадр).

**Текущий режим (24.10.2026):** вызовы `ma_tasks_frame`, `lifecycle_tick`,
`ma_sched_frame` в `plugin.cpp` закомментированы — скрипты не запускаются.
Возвращать по одному: `ma_sched_frame` → `lifecycle_tick` → `ma_tasks_frame`.
Периодического «ЗАМЕРА КАДРА» больше нет: хвост `log.txt` не покажет метрики.

## 3. Подписки на события

* Никогда не делай `Events::xxx += handler` изнутри обработчика того же списка:
  SDK держит `std::list`, итераторы будут испорчены.
* Все подписки — один раз в `Message::Message()`.
* Порядок критичен: `ma_diag::install()` (инициализирует `g_fileLock`), потом
  `ma_cmdq_install_hook()` (он сразу лочит эту секцию). Иначе игра не стартует
  (`RtlpWaitForCriticalSection … blocked by 0000`).
* Двери подписываются на другой список (`vehicleRenderEvent`) — это безопасно.

## 4. Планировщик и задачи

* Загрузка/пересканирование файлов — `ma_sched_scan()`; один скрипт — корутина.
* `wait(ms)` = `ma_sched_park()` + `lua_yield`; busy-цикл вытесняется count-хуком
  (слайс 1 мс / проход 6 мс).
* `create_newthread` = `ma_sched_spawn(parent, firstArg)`.
* Кооперативные задачи (`getcord`, `turncar`, `expectations`, `mission_watch`,
  keyboard) крутятся в `ma_tasks_frame()`; своего OS-потока у них нет.
* `ma_sched_request_teardown(restart)` и `ma_sched_request_pause()` — только
  атомарные запросы; исполняет их `ma_sched_frame`.

## 5. Работа с Lua API (частые ошибки)

* `lua_resume` — всегда с валидным 4-м аргументом `&nres` (Lua 5.4 пишет туда
  безусловно; `NULL` = краш).
* Не крути `lua_resume` по мёртвой корутине: выходи, если статус не `YIELD` и не `OK`.
* На `lua_newthread` тоже ставь count-хук.
* При ошибке запуска — снимай метку и `lua_close(L1)`, иначе утекут состояние и
  указатели на игровые объекты.

## 6. Teardown / reload

* Ctrl → `teardown_all(true)` → `ma_sched_request_teardown(true)`; разборка и
  повторный scan — на игровом потоке.
* `clrfl` → `scripts_disabled`, полная остановка без рестарта.
* Выход из игры (`gGameState != 9`) → `teardown_all(false)`.
* Владелец состояния закрывает его сам; сирот добивает общий цикл финализации.
* `wait()` сам `_ma_terminate` не читает: teardown будит запаркованную
  корутину через `kill_resume`, а `ma_sched_hook` бросает
  `SCRIPT_STOPPED_BY_CPP` (longjmp, не C++-исключение).

## 7. Диагностика и журнал

* Единственный файл — `lualoader/log.txt`; `trace.txt` не создаётся с 19.10.2026.
* `cpp_trace`/`cpp_tracef` пишут туда же (префикс `C++|`), `writelog` — ошибки.
* Не добавляй покадровые/периодические строки: `heartbeat` и «ЗАМЕР ОЧЕРЕДИ»
  удалены 24.10.2026. Ошибки, таймауты и crash-отчёт — можно.
* `ma_diag::mark()` пишет крошку в память и строку в журнал; на горячем пути
  используй `push_crumb`/`lua_note` (без файла).

## 8. Стиль, сборка, чек-лист

* Стиль автора: `try/catch (const char*)` + `writelog`, комментарии по-русски.
* Новые Lua-функции — не в `plugin.cpp`: прототип в `funcs.h`, реализация в
  `funcs.cpp`, регистрация в `register.cpp`.
* Перед заменой файлов — `.bak`; правки точечные, не переписывай функцию целиком.
* После правки — `./build.sh`. Критично: `error:`, `undefined reference`,
  повторное определение. «duplicate section .rdata$…» — штатный шум MinGW.
* BUILD-GATE: `_GLOBAL__sub_I == 30`, `.tls == 0x24`; иначе `.asi` удаляется.
* Успех не объявлять без проверки в игре: смотреть `lualoader/log.txt`.

# Часть C. Vice.Lua и MoonLoader — только выводы (полный разбор удалён 27.10.2026)

Изучение двух аналогов (Vice.Lua 1.1 Beta, MoonLoader 0.26.5) дало три полезных
вывода; полные дизассемблерные заметки и таблицы импортов удалены как архив.

1. Оба используют hook-based скриптовый движок и отдельный поток на скрипт. Для VC
   это неприменимо: игра однопоточная. Поэтому lualoader перешёл на очередь команд
   и однопоточный планировщик `ma_sched`.
2. Регистрация Lua-API через обёртку с крошками «файл:строка → API» полезна для
   crash-отчёта — реализовано `ma_lua_api_wrap`.
3. Массовая регистрация опкодов (сотни функций) — правильный путь, но каждая
   функция обязана проверять типы и границы: одна ошибка Lua роняет игру.
