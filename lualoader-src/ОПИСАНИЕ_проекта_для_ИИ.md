## 1. Что это за плагин

**lualoader** — ASI-плагин для оригинальной GTA Vice City (gta-vc.exe 1.0/1.1),
позволяющий писать моды на скриптовом языке **Lua 5.4.9** (миграция с 5.3 —
см. `ОТЧЁТ_миграция.md`). Скрипты из папки
`lualoader/` автоматически загружаются и выполняются при запуске игры.

- Встраиваемый Lua: статически слинкован (исходники Lua в `lualoader-src/lua/`),
  внешняя DLL НЕ нужна.
- Плагин сделан против **Plugin-SDK** (плюс-инклуды `plugin_vc` — Vice City
  ветка SDK).
- Готовая DLL: `lualoader.asi`, кладётся в корень игры рядом с `gta-vc.exe`.
- Лог работы: `lualoader/log.txt` (какие скрипты загружены, ошибки).

Главный файл: `gta-vc.exe` 1.1 EN (Steam). Сборка идёт кросс-компиляцией из
Linux под Windows (i686-w64-mingw32), поэтому все пути в командах — Linux-монтирования.

## 4. Как устроен сам плагин (код)

- `funcs.h` — это заголовочник, в котором лежат **и реализации, и прототипы**.
  Типичная Lua-функция выглядит так:
  ```cpp
  int имя_функции(lua_State* L) {// комментарий на русском, что делает.
      try {
          if (LUA_TLIGHTUSERDATA == lua_type(L, 1) && LUA_TNUMBER == lua_type(L, 2)) {// указатель на педа/авто.
              const void* p = lua_topointer(L, 1);
              CVehicle* car = findcarinpool(p);// получить указатель на авто.
              float value = lua_tonumber(L, 2);
              car->m_fMass += value;
              return 0;
          }
          else { throw "bad argument in function имя_функции"; }
      }
      catch (const char* x) { writelog(x); }// записать ошибку в файл.
      return 0;
  };
  ```
  - Аргумент «указатель на объект» передаётся как **lightuserdata**
    (`LUA_TLIGHTUSERDATA`, получается `lua_topointer`).
  - Игровые объекты ищутся по пулам: `findcarinpool(p)`, `findpedinpool(p)`.
  - Ошибки оформляются через `throw`/`catch` + `writelog`.
  - Комментарии внутри кода пишутся по-русски, стиль автора сохранён.

- `plugin.cpp` — в функции инициализации регистрируются функции:
  ```cpp
  lua_register(L, "имя_из_lua", имя_функции_c); // номер комментарий.
  ```
  Плюс там: загрузка скриптов (цикл по файлам папки lualoader), хук-поток,
  остановка/пауза.

- Примеры уже добавленных функций (стиль-образец). ВАЖНО: точные текущие
  версии см. в разделах 4.1 и 4.2 ниже — не копировать вслепую.

### 4.1 Функции характеристик авто (добавлены/исправлены 2026-09-15)

Все четыре: `set_car_mass`, `set_car_acceleration`, `set_car_max_speed`,
`set_car_traction` (funcs.h ~8193-8290, регистрация в plugin.cpp:724-727).
Принимают `(car, value)`, значение — «как в handling.cfg».

**`set_car_mass(car, 3000)` — увеличение массы (funcs.h:8193).**
- Масса НЕ участвует в разгоне: ускорение считается только из
  `fEngineAcceleration` в `CalculateDriveAcceleration` (Automobile.cpp:836,
  Transmission.cpp:90-133). Масса влияет лишь на столкновения/подвеску.
- Поэтому используется штатный опкод `Command<COMMAND_SET_CAR_HEAVY>(...)`
  (0x1EC, Script2.cpp:1489): ставит флаг `bIsHeavy` (+2x в столкновениях,
  Physical.cpp:610-623, подвеска *0.75/*2.0 — Physical.cpp:509,526) и сам
  задаёт 3x массы / 5x поворотной массы. Потом `m_fMass += value;
  m_fTurnMass += value` (перкопия у самой машины, офсеты 0xB8/0xBC).
- Флаг `bIsHeavy` после вызова остаётся навсегда — осознанно.
- Ручной бит bIsHeavy в VC не писать: SDK его не объявляет, оффсет
  неизвестен — только через опкод.

**`set_car_acceleration(car, 0.2)` — ускорение (funcs.h:8217).**
- Поле правильное: `m_pHandlingData->m_transmissionData.m_fEngineAcceleration`
  (0x4C) — читается каждый кадр, работает «живьём» без пересчётов.
- ВНИМАНИЕ, масштаб: в памяти хранится КОНВЕРТИРОВАННОЕ значение =
  cfg×0.4/2500 (LoadHandlingData HandlingMgr.cpp:301 + ConvertDataToGameUnits).
- Писать 0.2 «как в cfg» напрямую = ~6250x сильнее задуманного (дикая
  «ракета»). Если нужна честная cfg-семантика — писать `value*0.4f/2500.0f`
  (решение с пользователем не принято, сейчас пишется как есть).

**`set_car_max_speed(car, 100)` — макс. скорость, км/ч (funcs.h:8235).**
- ИСПРАВЛЕН КРИТИЧНЫЙ БАГ (было `m_fMaxSpeed` = 0x54 — это КРУИЗНАЯ
  скорость ИИ-автопилота, fMaxCruiseVelocity, Vehicle.cpp:1247; на
  скорость игрока не влияет вообще).
- Настоящий лимитер — `m_fMaxGearVelocity` (0x50 = reVC `fMaxVelocity`):
  `CalculateDriveAcceleration` каждый кадр проверяет
  `if (fVelocity > fMaxVelocity) return 0;` (Transmission.cpp:71; в exe
  адрес 0x5B2E20 читает [ecx+0x50], поле 0x54 физикой не читается вовсе).
- После записи НУЖНО пересчитать передачи — иначе верхняя передача
  держит старый таргет и новая скорость недостижима:
  ```cpp
  (*(void(__thiscall*)(void*))0x5B3120)(&car->m_pHandlingData->m_transmissionData);
  // cTransmission::InitGearRatios — пересчёт Gears[] из нового fMaxVelocity
  ```
- Единицы: в памяти значение = км/ч / 180 (ConvertDataToGameUnits:
  `fMaxVelocity *= 1000/(3600*50)`), поэтому в функции делится на 180.
- SDK-имена полей cTransmission ОБМАНЫВАЮТ: `m_fMaxGearVelocity` (0x50)
  = reVC `fMaxVelocity` (лимит!), `m_fMaxSpeed` (0x54) = reVC
  `fMaxCruiseVelocity` (AI-круиз), `m_fMinGearVelocity` (0x58) =
  `fMaxReverseVelocity`, `m_fCurrentSpeed` (0x5C) = `fCurVelocity`.
  Раскладка cTransmission (SDK cTransmission.h:37-41): gears[6]=0x0,
  nDriveType 0x48, nEngineType 0x49, nNumberOfGears 0x4A, flags 0x4B,
  accel 0x4C, maxGearVel 0x50, maxSpeed 0x54, minGearVel 0x58, curSpeed 0x5C.

**`set_car_traction(car, 0.9)` — сцепление (funcs.h:8264).**
- Поле `m_pHandlingData->fTractionMultiplier` (0x30) — правильное, без
  конвертации (значение в памяти = cfg-значению), читается каждый кадр
  (Automobile.cpp:903, Bike.cpp:779: `traction *= fTractionMultiplier/4.0f`).

**Общая ГРАБЛЯ характеристик**: `m_pHandlingData` — указатель на ГЛОБАЛЬНУЮ
запись handling (общая для ВСЕХ машин модели). Ускорение/макс.скорость/
сцепление меняются у всей модели целиком, а не у конкретной машины.
Масса (m_fMass/m_fTurnMass у самой машины) — наоборот, перэкземплярная.
До смены игры правки не откатываются.

### 4.2 Функции оружия (добавлены 2026-09-15)

`set_damage_current_weapon(ped, damage)` (funcs.h:4331) — урон; меняет
`CWeaponInfo::m_nDamage` через `CWeaponInfo::GetWeaponInfo(type)` (0x5D5710).

`set_clip_current_weapon(ped, clip)` (funcs.h:4351, регистрация plugin.cpp:535)
— объём обоймы текущего оружия:
- Проверяет, что оружие огнестрельное: `w->m_eWeaponFire ==
  WEAPON_FIRE_INSTANT_HIT` (пистолеты/ПП/дробовики/винтовки/снайперки;
  MELEE и PROJECTILE отсекаются с throw → writelog).
- Обойма = `CWeaponInfo::m_nAmountofAmmunition` (офсет 0x10; поле F
  weapon.dat, у m4 = 30). `CWeapon::Reload()` читает именно его:
  `m_nAmmoInClip = min(m_nAmountofAmmunition, m_nAmmoTotal)`
  (Weapon.cpp:2843-2848).
- Дополнительно сразу наполняет текущую обойму педа:
  `ped->m_aWeapons[ped->m_nCurrentWeapon].m_nAmmoInClip = min(clip,
  m_nAmmoTotal)` (m_nAmmoInClip = 0x8, m_nAmmoTotal = 0xC, m_aWeapons =
  0x408, m_nCurrentWeapon = 0x504 у CPed) — чтобы HUD показал `10/600`
  без перезарядки.
- CWeaponInfo — глобальная на тип оружия (aWeaponInfo[37]): обойма/урон
  меняются у всех педов с этим оружием, как и set_damage.
- Тест: в autoaim.lua блок VK_J — `Giveweaponped(player,600,"m4")` +
  `set_clip_current_weapon(player, 10)` → HUD `10/600`, после 10 выстрелов
  перезарядка на новый магазин (не на 30 из weapon.dat).
- Числа weapon.dat: m4 — INSTANT_HIT, обойма 30, урон 40; огнестрел =
  INSTANT_HIT (16 шт.), MELEE 12, PROJECTILE 7, AREA_EFFECT/CAMERA — по 1.

## 5. Сборка (главная команда)

```bash
cd "/mnt/807EB5FA7EB5E954/games/old GTA Vice City/lualoader-src" && ./build.sh
```

- Требует уже собранную `Plugin-SDK/output/lib/libPlugin_VC.a` (иначе build.sh
  скажет об этом и выйдет).
- Результат кладётся в корень игры как `lualoader.asi`.
- Предупреждения «duplicate section .rdata$... has different size» из
  libstdc++.a — ШТАТНЫЕ, не ошибки. Критично смотреть на `ГОТОВО: ../lualoader.asi`
  или на строки `error:` / `undefined reference`.
- Очистка объектников: `./build.sh clean`.

### После успешной сборки:
1. Проверить, что появился `../lualoader.asi` свежий.
2. Запустить игру, посмотреть `lualoader/log.txt` (загрузились ли скрипты,

## 6. Как добавить новую Lua-функцию (шаги)

1. В `funcs.h` рядом с похожими добавить ПРОТОТИП:
   ```cpp
   int новая_функция(lua_State* L); // русский комментарий + пример использования.
   ```
2. В `funcs.h` добавить РЕАЛИЗАЦИЮ (рядом с группой однотипных функций;
   если пользователь сказал «после функции XXX» — вставить сразу после неё).
3. В `plugin.cpp` добавить строку регистрации рядом со смежными:
   ```cpp
   lua_register(L, "имя_в_lua", новая_функция); // номер комментарий.
   ```
   Номера в комментариях — сквозная нумерация, следить чтобы не было повторов.
4. Собрать (`build.sh`), проверить `log.txt` после запуска игры.

## 7. Ключевые правила и «грабли» (НЕ нарушать)

- **Стиль автора**: try/catch + `writelog`, комментарии по-русски, скобки и
  отступы как в соседних функциях. Не «переписывать стиль под себя».
- **Не трогать хрупкие места**: потоковые/мутекс-механики, деструкторы,
  сырые вызовы типа `CMatrix::SetRotate*`, OnAMissionFlag, гравитацию и т.п.
  Править точечно, под задачу.
- **Числа-хардкоды** игровых функций, где известны символы SDK, заменять на
  символы (пример уже сделан при миграции: GetHeading, FrontEndMenuManager,
  gGameState, CTimer, TheCamera, CWanted, DoorsExample). Но новые офсеты НЕ
  изобретать без проверки в `gta vc база` или SDK.
- `findcarinpool`/`findpedinpool` обходят пул — каждый кадр нагружают; в
  циклах типа `while true do wait()` стараться брать указатель один раз.
- Если правки касаются сценария Lua (`.lua`), их правят в `lualoader/*.lua`
  напрямую, сборка плагина при этом не нужна.
- После правки всегда **проверять сборку** или синтаксис; «готово» говорить
  только после проверки (см. раздел 8).
- **Сырые адреса функций**: адреса из `gta vc база/ОТЧЁТ_функции_gta-vc_steam.md`
  (база gta-vc_steam.idb) для РЯДА функций НЕ совпадают с установленным
  `gta-vc.exe` (примеры мусора при дизасме: 0x5B2F50, 0x5AAC50). Адреса,
  которые уже работают в funcs.h (0x4DF450/0x4DF4F0/0x4E3690), и адреса из
  файлов `Plugin-SDK/plugin_vc/game_vc/*.cpp` (напр. InitGearRatios
  0x5B3120, CalculateDriveAcceleration 0x5B2E20, GetWeaponInfo 0x5D5710)
  установленному exe СООТВЕТСТВУЮТ — SDK собран под него. Новый сырой адрес
  брать из SDK; если из отчёта — сначала проверить.
- **Проверка адреса перед сырым вызовом** (дизасм установленного exe):
  ```bash
  pip3 install --break-system-packages pefile capstone   # один раз
  python3 -c "import pefile; from capstone import Cs,CS_ARCH_X86,CS_MODE_32
  pe=pefile.PE('gta-vc.exe',fast_load=True); data=open('gta-vc.exe','rb').read()
  off=pe.get_offset_from_rva(0xАДРЕС-0x400000)
  [print('%-8s %s'%(i.mnemonic,i.op_str)) for i in Cs(CS_ARCH_X86,CS_MODE_32).disasm(data[off:off+0x40],0xАДРЕС)]"
  ```
  (запускать из корня игры). Начало вида `in al,5` / `add al,0xd9` / `pop ecx`
  без пролога = адрес НЕ той версии, вызывать нельзя. Нормальное начало —
  push/sub esp/mov ebx,ecx и т.п. objdump PE не парсит («file format not
  recognized») — не пытаться.

1. Симптом (жалоба пользователя с 4-й сессии, фикс в `Createped`):
   `Createped("IGMERC", x, y, z)` создавал **клона Томми**, а не Мерседес.
   Причина: имени спец-актора нет в `name_peds_list` → `find_in_map` = 0 →
   `CREATE_CHAR` с моделью 0 (Томми); последующий `UNDRESS_CHAR`/`DRESS_CHAR`
   не прикладывал скин поверх чужой по полу основы.
2. **Решение** в `funcs.h` (`Createped`, ~4921): если `model == 0`, но имя
   найдено в `type_specpeds_list` — спец-актор:
   - пол = значение из `type_specpeds_list` (`PED_TYPE_CIVMALE=4` /
     `PED_TYPE_CIVFEMALE=5`; женские: IGMERC, IGMERC2, IGCANDY, STRIPA…);
   - создаётся **базовый пед того же пола**: женский `WFYST`, мужской `HMYBE`
     (загрузка через `load_model_before_avalible` + `MARK_MODEL_AS_NO_LONGER_NEEDED`);
   - надевается скин: `UNDRESS_CHAR(ped, имя)` + `DRESS_CHAR(ped)`.
   **Никакой загрузки спец-модели** (слоты/`RequestSpecialChar` сознательно
   НЕ используются — такое требование пользователя).
3. `create_spec_ped` оставлена как есть (создаёт клона Томми) — для старых
   скриптов; фолбэк-обёртка в `mod.lua` сохранена. `LUA_API_СПРАВОЧНИК.md`
   в поведение `Createped` не правился (сигнатура та же).
4. Сборка: `./build.sh` → `ГОТОВО: ../lualoader.asi (6,1M)`, 0 ошибок.
   Проверка в игре подтверждена пользователем: `IGMERC` — девушка с кожей
   Мерседес.
5. Документы обновлены: `КАК_НАПИСАТЬ_МИССИИ.md` (разделы 5.1, 5.2, 4.4, 9–11),
   этот файл (раздел 9.1з).

### 9.1и Десятая сессия (2026-09-16: тотальная регистрация созданных объектов)

1. Задача пользователя: **всё, что создаёт скрипт** (педы, авто, объекты,
   пикапы, маркеры, сферы, огни, непрерывные звуки), должно автоматически
   попадать в свой список и уничтожаться ОДНОЙ функцией `destroy()` —
   «синтаксический сахар»: вызвал `destroy()` (или `end_mission`/`miss` в
   mod.lua, которые его зовут) → чистится всё, что наворотила миссия.
2. **Аудит** всех `Command<COMMAND_...>` создания в funcs.h выявил пробелы:
   - **педы-водители/пассажиры** создавались ВНЕ списков: `setcardrive`,
     `setcarpassenger`, `set_ped_in_car` (обе ветви: driver и passenger) —
     созданный пед не удалялся ни `destroy()`, ни индивидуально;
   - **непрерывные звуки** `play_continuous_sound` не трекались вообще
     (не было map-а звуков), а `all_destroy()` вдобавок не чистил **огни**
     (`firesids` — был только в `destroy(L)`).
3. **Сделано в funcs.h**: новый `static map<int, lua_State*>soundsids`;
   во все 4 точки создания педа в авто добавлено `mappeds.emplace(ped, L)`
   (с `if (ped != NULL)`); `play_continuous_sound` → `soundsids.emplace`;
   `remove_sound_by_id` → `find`+`erase` (как остальные `remove_*`).
4. **Сделано в plugin.cpp**: `destroy(L)` — новый цикл по `soundsids`
   (`REMOVE_SOUND` + erase, по `lua_State`); `all_destroy()` — добавлены
   циклы `firesids` и `soundsids` (чистит ВСЁ, а не только своё), а в цикле
   `mappeds` добавлен `ped->ClearObjective()` — освобождать педов от задач
   перед удалением (как в `destroy(L)`).
5. Сборка: `./build.sh` → `ГОТОВО: ../lualoader.asi (6,1M)`, 0 ошибок.
   Документы: `КАК_НАПИСАТЬ_МИССИИ.md` раздел 5.9 (реестр + список функций
   создания), этот файл (9.1и).
6. **Безопасное удаление (продолжение темы)**: игрок мог сидеть в машине,
   которую `destroy()`/`all_destroy()` удаляли через `CWorld::Remove` → вылет.
   Добавлены хелперы в funcs.h: `warp_out_car_occupants(car)` (опкод
   0x362 WARP_CHAR_FROM_CAR_TO_COORD выкидывает игрока + водителя + 8
   пассажиров, только живых) и `safe_remove_car(car)` (проверка висячего
   указателя через `findcarinpool` → выкинуть сидящих → MARK_NO_LONGER_NEEDED
   → `CWorld::Remove`). `remove_car` тоже стал выкидывать сидящих перед
   удалением. Порядок очистки изменён: **сначала авто, потом педов** — иначе
   удаление авто под сидящим педом роняет игру. Циклы педов/объектов стали
   проверять указатель через `findpedinpool`/`findobjinpool` (висячий —
   просто стереть запись из map).
