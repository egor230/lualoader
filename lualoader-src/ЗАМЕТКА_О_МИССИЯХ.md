# Заметка о миссиях: флаг миссии и «сторож» провала

Отдельная заметка (дизайн флага/сторожа). Основной документ —
`КАК_НАПИСАТЬ_МИССИИ.md`: структура миссии — §2 (в т.ч. §2.1 «почему заезд
на машине»), главные ошибки — §5, правила безопасности — §12.

Структура любой Lua-миссии (эталон `misson party.lua`): внешний цикл
`while true do wait() ... Star_mission_marker(...) ... end` → подъезд к значку
на машине → высадка → основной цикл `while true == getflagmission() do wait()`
с конечным автоматом `step` → `miss()`/`end_mission()` → очистка.

**Главное правило:** функции с БОЛЬШОЙ буквы (`Getflagmission`,
`Setflagmission`) живут на стороне **C++** (`funcs.h`, регистрация в
`plugin.cpp`, как `getflagmission`/`setflagmission`). Lua-версию (например
`Getflagmission` в `mod.lua:548`) надо **удалять**, иначе Lua перекроет
C++-функцию (Lua грузится после `lua_register`).

**СТАТУС (18.09.2026): РЕАЛИЗОВАНО и СОБРАНО.**
- `Getflagmission` — C++ `funcs.h:3434`; `Setflagmission` — C++ `funcs.h:3441`.
- Регистрация — `plugin.cpp:379-380`.
- Сторож — `mission_watch_proc` (`funcs.h:3399`), запуск — `mission_watch_start`
  (`funcs.h:3423`), **ровно один** поток (новый запуск делает `join` старому).
- Lua-версия `mod.lua:548` заменена комментарием.
- Бэкапы: `funcs.h.orig-watchdog`, `plugin.cpp.orig-watchdog`,
  `mod.lua.orig-watchdog`.

## 1. Флаг миссии

- `getflagmission` (C++, `funcs.h:3356`) — читает флаг из `ScriptSpace[0x978748]`.
- `setflagmission` (C++, `funcs.h:3364`) — пишет туда же (обычная запись байта).
- Миссия крутится в `while true == Getflagmission() do wait()` — пока флаг `true`.

## 2. `Getflagmission` (большая) vs `getflagmission` (маленькая)

- **`getflagmission()`** — примитив (маленькая, C++): только читает и
  возвращает значение флага. Ничего не проверяет, флаг не меняет.
- **`Getflagmission()`** — «умная» (большая, C++): при КАЖДОМ вызове проверяет,
  погиб ли игрок или арестован. Если да — выводит «Миссия провалена», меняет
  флаг на `false` и возвращает его. Если нет — просто возвращает флаг.

Потокобезопасность — **проверку делает ровно ОДИН поток**:

- Нельзя, чтобы проверяли одновременно и `Getflagmission()`, и сторож `watch`
  (гонка на флаге и на игровых вызовах, см. §5.11 основного документа).
- Выбираем ОДИН механизм: либо проверка внутри `Getflagmission()`, либо
  отдельный сторож `watch`.
- Признак занятости — атомарный флаг, чтобы второй сторож не стартовал.

## 3. `Start_mission` (C++): ставит флаг и поднимает ОДИН сторож

- Ставит `setflagmission(true)` и запускает сторож.
- **Работает только ОДИН поток:** если сторож уже запущен, при новом
  `Start_mission` старый уничтожается (сигнал остановки + `join`), затем
  запускается новый. Двух сторожей одновременно быть не может.

```cpp
std::atomic<bool> watch_stop{false};
std::thread watch_thread;

void Start_mission(CPed* player) {
    setflagmission(true);
    if (watch_thread.joinable()) {     // старый сторож ещё жив?
        watch_stop = true;             // приказать ему выйти
        watch_thread.join();           // дождаться и уничтожить поток
    }
    watch_stop = false;
    watch_thread = std::thread(watch, player);   // ровно один поток
}
```

## 4. Сторож `watch` (C++)

```
void watch(CPed* player) {
    while (!watch_stop) {                       // выход по сигналу уничтожения
        std::this_thread::sleep_for(100ms);

        // 1) игрок погиб ИЛИ арестован:
        //    надпись -> сменить флаг -> выйти
        if (arrested_state() || player->m_fHealth <= 1.0f) {
            showtext("Миссия провалена");
            setflagmission(false);
            break;
        }

        // 2) флаг поменялся САМ (миссия завершилась извне) -> выход
        if (!getflagmission()) break;

        // 3) идёт загрузка -> выход
        if (game_is_loading()) break;

        // 4) идёт сохранение -> выход
        if (game_is_saving()) break;
    }
    cleanup();                                  // очистка созданного
}
```

- **Смерть или арест** — единственный случай, где сторож сам печатает
  «Миссия провалена» и меняет флаг; затем выход.
- **Флаг сменился сам** — просто выход (без надписи).
- **Загрузка / сохранение** — просто выход.
- Потоки не пересекаются: старый всегда уничтожается до запуска нового
  (единственный живой поток — текущий сторож).

## 5. Очистка `cleanup` (уничтожение созданного)

`cleanup()` вызывается сторожем сразу после выхода из цикла:
`end_mission("mission failed!")` → `destroy()`.

`destroy()` (`funcs.h:24475`) удаляет **всё**, что создавал скрипт:
- **педы** (`mappeds`) — с высадкой из авто и снятием задач;
- **машины** (`mapcars`) — безопасно, сначала высаживая сидящих;
- **объекты**;
- **пикапы** (`pickupsids`);
- дополнительно блипы, сферы, огни, непрерывные звуки.

Порядок — сначала авто, потом педы (см. `КАК_НАПИСАТЬ_МИССИИ.md` §5.9);
висячие указатели проверяются через `find*inpool`.


createblip — funcs.h:3638 — вызывает скрипт-команду COMMAND_ADD_SHORT_RANGE_SPRITE_BLIP_FOR_CONTACT_POINT (opcode 0x570):

это короткодействующая (short-range) метка-«контакт»: движок внутри зовёт CRadar::SetShortRangeCoordBlip и ставит tRadarTrace.m_bShortRange = true — метка видна на радаре, только когда игрок рядом;

# Заметка о переносе миссии: принципы и подходы (на примере "Riot")

Перенос оригинальных миссий GTA Vice City (написанных на SCM/Sanny Builder) на Lua для плагина lualoader требует не прямого перевода строк, а адаптации логики под архитектуру плагина. Оригинальный движок использует потоки (threads) и опкоды, а lualoader работает через конечные автоматы (state machines) в главном цикле. 

Ниже приведены основные принципы, которые были применены при переносе миссии «Riot» (Мятеж).

### 1. Архитектура: Функции ВЫШЕ `main()`
Оригинальный SCM-код часто представляет собой «спагетти» из меток и `GOTO`. В Lua весь код структурируется:
- Вспомогательные функции (спавн сцены, проверка статусов, катсцены, очистка) выносятся на уровень файла **перед** `main()`.
- В `main()` остаётся только внешний цикл ожидания подъезда к маркеру и внутренний цикл (`while true == Getflagmission() do wait()`) с конечным автоматом (переменная `step`).
- Функции общаются с `main` через параметры и возврат нескольких значений. Состояние миссии (счётчики, флаги) живёт в локальных переменных `main`.

### 2. Отказ от потоков в пользу покадровых проверок
Оригинальный движок мог запустить отдельный поток (thread), чтобы следить за здоровьем грузовика и снимать маркер при его уничтожении. В lualoader **потоки использовать нельзя** — они работают в изолированных `lua_State` и вызывают гонку данных (data race) в общих C++ коллекциях (что приводит к крашу).
- **Принцип:** Любая проверка состояния объекта (здоровье, смерть, уничтожение) делается покадрово в главном цикле.
- **Реализация:** Создаются функции-чекеры (например, `check_trucks_destroyed(trucks, markers)`), которые вызываются каждый кадр. Они возвращают `true/false`, а внутри себя безопасно снимают маркеры, если объект мертв.

### 3. Использование списков (таблиц Lua)
Вместо создания 10–20 одиночных переменных для педов или машин, всё собирается в таблицы (списки).
- `spawn_trucks()` возвращает `trucks` и `markers` — две таблицы с индексами 1, 2, 3.
- Это позволяет перебирать объекты в цикле `for i=1,3 do`, массово проверять их статус и массово удалять при очистке сцены (`cleanup_scene`).
- Аналогично со списками рабочих: `spawn_rioters()` возвращает списки сундости (педы, флаги урона, HP).

### 4. Безопасность и NULL-указатели
Игра может удалить объект (педа, машину) из пула в любой момент (например, игрок взорвал машину, и игра убрала обломки). Если Lua-функция обратится к удаленному указателю, игра вылетит (segfault).
- **Принцип:** Перед любым действием с объектом идёт проверка на валидность.
- `if isped(r) and not ispeddead(r) then` — стандартный паттерн перед выдачей оружия или назначения цели.
- `if trucks[i] ~= nil and isvehicle(trucks[i]) and not iscardead(trucks[i])` — проверка авто перед снятием маркера.

### 5. Изоляция состояния (Только `local`)
Все `.lua` скрипты в папке `lualoader/` работают на **одном** общем `lua_State`. Если написать `step = 1` без `local`, эта переменная перетрется другим скриптом (например, автоаимом или другой миссией), и всё сломается.
- **Принцип:** Абсолютно все переменные внутри миссии объявляются строго как `local`. Никаких глобалов.

### 6. Гигиена мира: Очистка и сброс глобальных эффектов
Миссия не должна оставлять мусор после завершения (успех или провал).
- Все созданные сущности (педы, машины, объекты, блайпы, сферы) удаляются через специально написанную функцию `cleanup_scene()`.
- Если миссия изменяла глобальные настройки игры (например, `set_riot_intensity(127)` или `request_animation("RIOT")`), они **обязательно** сбрасываются в 0 или выгружаются при выходе из цикла миссии.

### 7. Замена отсутствующих опкодов
В оригинале были катсцены (`LOAD_CUTSCENE`) и пикапы одежды (`CREATE_CLOTHES_PICKUP`), которых нет в API lualoader.
- Катсцены заменяются на текстовые реплики (`printmessage`) + управление камерой (`set_camera_position` / `camera_at_point` / `restore_camera`).
- Подбор одежды определяется не флагом пикапа, а проверкой расстояния (`ped_in_point_in_radius`) + вызовом `set_skin` за черным экраном (`fade`).
- Урон толпе определяется не опкодом `IS_CHAR_HEALTH_GREATER`, а покадровым сравнением float-здоровья (`getpedhealthf`) с прошлым кадром.

### 8. Инлайн координат
Координаты (X, Y, Z) пишутся прямо в местах вызова функций (например, `Createcar("MODEL_SPAND", 286.7, -302.1, 11.9)`), а не выносятся в блок констант в начале файла. Это уменьшает "простыни" кода и делает чтение логики локализованным.

### 9. Стиль комментариев (требование пользователя)
- Код должен быть самодокументируемым через короткие комментарии.
- Комментарии ставятся **на той же строке**, что и код, через 1 пробел от него.
- Формат: короткое описание действия (например, `ped_frozen(1) -- Разморозить`). Никаких многострочных простыней текста внутри функций.

---
**Итог:** Перенос миссии сводится к переписыванию линейной логики с `GOTO` в структуру "Функции + State-Machine в главном цикле", с максимальным использованием таблиц для групп объектов, строжайшей проверкой указателей и полным отказом от потоков в пользу покадровых проверок.
