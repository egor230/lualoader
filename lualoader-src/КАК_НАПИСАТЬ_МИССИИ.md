# Как написать миссию на Lua для lualoader (GTA Vice City)

Полное практическое руководство: пошаговый подход к созданию миссий, разбор
всех известных на момент написания ошибок и «граблей». Написано по итогам
реальной работы над миссией `lualoader/misson party.lua` (2026-09-16).
Дополнено 16.09.2026: раздел 5.1 — приём спец-акторов починен в `Createped`.
Дополнено 17.09.2026: 5.10 — ABI-краш `CVector`/`SetObjective` и его лечение;
5.11 — зависание `Createcar` (гонка detached-потока); 5.12 — радианы в
`GetHeading`; раздел 12 — правила безопасности «как НЕ сломать работающее».
Дополнено 18.09.2026: 5.9 переписан под единственную функцию удаления
`destroy()` (мёртвый дубль `all_destroy` удалён из кода и документации);
C++-сторож `Getflagmission`/`Setflagmission` (см. `ЗАМЕТКА_О_МИССИЯХ.md`);
перенос реальной миссии на Lua — отдельный документ
`КАК_ПЕРЕНОСИТЬ_МИССИИ.md` (читать его перед переносом любой миссии).
Цель документа — чтобы любую новую миссию можно было написать с нуля без
повторения чужих (и наших) ошибок.

Документ лежит в `lualoader-src/` вместе с остальными MD-файлами проекта
(ОПИСАНИЕ_проекта_для_ИИ.md, LUA_API_СПРАВОЧНИК.md и др.).

## 1. Что нужно знать перед стартом

- Плагин **lualoader.asi** загружает ВСЕ `.lua`-файлы из `lualoader/`
  при запуске игры. Каждый файл — отдельный Lua-скрипт, у каждого своё
  состояние Lua-машины (`lua_State*`).
- Игра — **GTA Vice City** (steam 1.1 EN). Плагин мингается из Linux
  кросс-компилятором i686-w64-mingw32.
- Миссии в этом lualoader — это НЕ штатные миссии игры (не через
  `CTheScripts`). Это Lua-скрипты, которые отслеживают флаг «идёт миссия»
  (`Getflagmission()`/`setflagmission(true/false)`) и сами выполняют логику.
- Скрипты автозагружаются в порядке папки. Отладка — через `lualoader/log.txt`
  (ошибки) и `lualoader/trace.txt` (альтернативный трассер, пишем сами).

### 1.1 Терминология пользователя

| Фраза | Значит |
|---|---|
| «исходники», «funcs.h» | `lualoader-src/funcs.h` — ВСЕ Lua-функции (реализации+прототипы, ~24500 строк) |
| «plugin.cpp» | `lualoader-src/plugin.cpp` — регистрация функций (`lua_register`), загрузка скриптов |
| «установка», «скрипты» | `lualoader/` — только `.lua` файлы + log.txt |
| «собери» | `cd lualoader-src && ./build.sh` → `ГОТОВО: ../lualoader.asi` |
| «Lua-скрипт/миссия» | `.lua` файл в `lualoader/` |

Координаты в API — всегда **три отдельных числа X, Y, Z**.
Указатели на пед/авто/игрока — светлые userdata из функций поиска/создания.

## 2. Каркас миссии (обязательный скелет)

Эталон — реальный рабочий файл `lualoader/misson party.lua`. Скелет:

```lua
require("lualoader/mod")                 -- обёртки и фиксы (обязательно)

function main()
while true do wait() player = findplayer()   -- ВНЕШНИЙ цикл: ждём вход в маркер
 if Star_mission_marker(9, 118.0, -825.9, 10.5)  -- маркер: подъезд НА МАШИНЕ
 then showtext(" patry", 500, 1)                 -- имя миссии на экран
  setcord(player, 118.0, -825.9, 10.5) setangle(player, 54.0)
  bike = Createcar("MODEL_FREEWAY", 123.8, -810.9, 10.5)  -- стартовый транспорт
  setangle(bike, 320)
  fade(1, 2900)                                  -- проявление (из тьмы)
  blip = createmarker(1, 2, 95.4, -1136.2, 10.5) -- маркер цели на карте
  setsizemarker(blip, 3)
  sp = create_sphere(95.4, -1136.2, 10.5, 3.0)   -- сфера (зона срабатывания)
  printmessage("~r~Текст задания", 3000, 1)

  while true == getflagmission() do wait()        -- ОСНОВНОЙ цикл миссии
   -- ЭТАП 0 -> 1: игрок дошёл пешком до точки
   if ped_in_point_in_radius(player, 95.4, -1136.2, 10.5, 2.0,2.0,2.0)
      and not is_ped_in_car(player) and step == nil
    then remove_blip(blip) remove_sphere(sp)
         -- ... катсцена/создание целей ...
         step = 1
   end
   -- ЭТАП 1 -> 2: новая точка
   if step == 1 and ped_in_point_in_radius(player, -251.2, -1360.8, 8.1, 2.0,2.0,2.0)
      and not is_ped_in_car(player)
    then step = 2
         ped1 = Createped("IGMERC", -241.7, -1360.3, 8.1)  -- создать педа
         -- ... новые маркеры/сферы/враги ...
   end
   -- ЭТАП 2 (финал)
   if step == 2 then
    if ped_in_point_in_radius(player, 100.7,-1477.6,10.1, 2.0,2.0,2.0)
       and ped_in_point_in_radius(ped1, 100.7,-1477.6,10.1, 2.0,2.0,2.0)
     then remove_ped(ped1) miss(1000)              -- УСПЕХ: деньги + «passed»
          step = nil break
    end
    if getpedhealth(ped1) == 0 then                 -- ПРОВАЛ
       printmessage("dead", 3000, 1) end_mission("mission failed!")
       step = nil break
    end
   end
  end
  -- после выхода из основного цикла флаг уже снят (miss/end_mission)
 end
end
end
```

### 2.1 Почему миссия начинается с заезда НА МАШИНЕ (важно)

- Триггер — `Star_mission_marker(тип, x, y, z)` во **внешнем** цикле
  `while true do wait() end`.
- Он срабатывает, когда игрок **подъезжает к значку на машине**.
  `Star_mission_marker` (`mod.lua`) сам ставит флаг миссии, принудительно
  высаживает игрока (`exitcar`), убирает его машину (`remove_car`) и только
  потом возвращает `true` — после чего начинается тело миссии.
- Как только игрок вышел из машины — **значок исчезает**.
- Зачем именно так:
  1. Сразу видно, что миссия написана на **Lua** — не спутать с миссиями
     игрового движка.
  2. Она **не мешает** другим (оригинальным, движковым) миссиям: свой маркер,
     свои опкоды, своя очистка.
  3. **Безопасно для сохранений** — состояние миссии поднимается и снимается
     аккуратно, сейв не портится.
- Итог: каждая Lua-миссия = «значок, к которому подъезжаешь на машине» →
  высадка → основной цикл.

### 2.2 Правила каркаса (выстраданы опытом)

1. **`wait()` без аргумента** — минимум один на каждый проход цикла.
   Без него игра может зависнуть/вылететь: цикл закрутится без отдачи кадра.
2. **Флаг миссии** держим поднятым (`setflagmission(true)`) ВЕСЬ цикл
   `while true == Getflagmission()`; снимаем после выхода.
3. **Никогда не удаляй объекты миссии прямо в момент, когда цикл крутится
   по тому же условию** — сначала поменяй `step`, следующей итерацией
   удаляй. Удаление «в тот же кадр, когда что-то проверяем» — частая
   причина вылетов.
4. Переводы текста в `printmessage`/`showtext` — через тильду-коды
   (`~r~` красный и т.д.). Кириллица может не отобразиться (старый VC).

## 3. Пошаговый подход к написанию миссии

Этот рецепт — «как надо». В финальной главе (раздел 8) — что реально
происходит, если рецепт нарушить.

### Шаг 0. Определи сюжет и этапы (step-машину)

Разбей миссию на **дискретные этапы**: `step=nil → step=1 → step=2 → финал`.
На каждом этапе — свой входной триггер (точка/радиус/здоровье/таймер) и
свои действия (создание/удаление объектов). Один этап завершает другой.

### Шаг 1. Стартовый триггер (Star_mission_marker)

```lua
if Star_mission_marker(9, 118.0, -825.9, 10.5) then
```
Срабатывает, когда игрок входит в зону на карте. Стоит сразу:
- поставить игрока (`setcord` + `setangle`),
- создать стартовый транспорт и маркер цели,
- `fade` (затемнение/проявление),
- поднять флаг миссии.

### Шаг 2. Главный цикл с конечным автоматом

Внутри `while true == Getflagmission() do wait()` проверяем `if step == N`
и условия для перехода `step = N+1`. Ключевое — каждый переход сначала
чистит старьё, потом создаёт новое, и только сам `step` в конце.

### Шаг 3. Условия успеха и провала

- Успех: `miss(сумма)` + `printmessage` проходного текста + удалить всё +
  `break`.
- Провал: `end_mission("mission failed!")` (`miss` не даёт), удалить всё,
  `break`.

### Шаг 4. Обязательная очистка

После `break` (успех ИЛИ провал) — **удалить все созданные маркеры, сферы,
пикапы, педов, авто** (`remove_blip`, `remove_sphere`, `remove_ped`,
`remove_car`…). Всё, что не удалишь вручную, висит в map-ах плагина и будет
удалено при `destroy()` при перезагрузке скрипта — см. раздел 6.

### Шаг 5. Тест и диагностика

1. Пройти миссию медленно, смотреть `lualoader/trace.txt` (трассер, см. 7.2).
2. Смотреть `lualoader/log.txt` после каждого вылета.
3. Правило: **каждое изменение C++ (`funcs.h`/`plugin.cpp`)** →
   `./build.sh` → «готово» только после сборки. Изменение `.lua` —
   сборка не нужна, только перезапуск игры.

## 4. Какие API используются в миссиях (шпаргалка)

Полный список всех 1506 функций — в `LUA_API_СПРАВОЧНИК.md`. Ниже —
ядро, используемое почти в любой миссии:

### 4.1 Игрок и триггеры
- `findplayer()` → указатель игрока.
- `Star_mission_marker(тип, x, y, z)` → флаг «игрок на стартовом маркере».
- `setcord(player, x, y, z)`, `setangle(player, угол)` — поставить/довернуть.
- `ped_frozen(0|1)` — заморозить/разморозить игрока (катсцены).
- `fade(0 или 1, время)` — затемнение/проявление.
- `set_widescreen(true|false)`, `set_camera_position`, `camera_at_point`,
  `restore_camera()` — раскадровка катсцены.
- `is_ped_in_car(player)` → флаг «в машине».

### 4.2 Транспорт
- `Createcar("MODEL_ИМЯ", x, y, z)` → указатель авто (макрос по имени).
- `setangle(car, угол)`, `setcarcoordes(car, x, y, z)`.
- `putincar(ped, car)` — посадить педа/игрока в авто.
- `ped_car_as_driver/ped_car_as_passenger(ped, car)` — пед водитель/пассажир.
- `exitcar(ped)` — выйти из авто.
- `setcarspeed`, `setdrivingstyle`, `setcarstrong` — ИИ авто.
- `car_in_point_in_radius(car, x, y, z, r)` → флаг.
- `getcarcoordinates_on_y(car, смещ)` → x,y,z (позиция со смещением).

### 4.3 Маркеры/сферы (радар)
- `createmarker(тип, размер, x, y, z)` → id маркера; `setsizemarker(id, s)`.
- `create_marker_car(car)` / `create_marker_actor(ped)` → маркер на сущность.
- `remove_blip(id)` — удалить маркер (чистит и map плагина).
- `removemarker(id)` — то же через `COMMAND_REMOVE_BLIP`.
- `create_sphere(x, y, z, r)` → id сферы; `remove_sphere(id)`.
- `createblip(тип, x, y, z)` → обычный blip.

### 4.4 Педы
- `Createped("ИМЯ_МОДЕЛИ", x, y, z)` → указатель педа. Принимает И спец-акторов
  (`IGMERC`, `IGPHIL` …): пол — по `type_specpeds_list`, базовый пед того же
  пола, сверху — скин спец-актора (раздел 5.1, починено 16.09.2026).
- `create_spec_ped("IG...", x, y, z)` → старая функция спец-персонажа. СМОТРИ
  РАЗДЕЛ 5.1 — создаёт клона Томми (модель 0); для миссий используй `Createped`.
- `ped_in_point_in_radius(ped, x, y, z, rx, ry, rz)` → флаг.
- `getpedhealth(ped)` → число; `setpedhealth(ped, n)`.
- `follow_the_leader(ped)` → пед следует за лидером (в модах — за игроком).
- `clean_leader(ped)` — убрать из «следования».
- `ped_save_pos_attack(ped, флаг)` — атака позиции.
- `ped_walk_to_point(ped, x, y, z)`, `ped_run_to_point(...)`,
  `ped_sprint_to_point(...)` — движение к точке.
- `getcoordinates_on_y(ped/set)`, `getpedcoordinates_on_y(ped, смещ)`.
- `remove_ped(ped)`, `kill_ped(ped)`, `Giveweaponped(ped, патроны, "тип")`.
- `foel(модель, цель, оружие, x, y, z)` → враг, возвращает `ped, маркер`.
- `is_ped_in_car(ped)`, `incar(ped)` → флаг + авто.

### 4.5 Деньги/миссии
- `givemoney(n)`, `miss(n)` — начислить (успех). `miss` помечает проход.
- `end_mission("текст")` — провал/конец миссии.
- **`Getflagmission()` → флаг** (большая буква = C++: при каждом вызове
  поднимает сторож «погиб/арестован → миссия провалена», см.
  `ЗАМЕТКУ_О_МИССИЯХ.md`); `setflagmission(true|false)` — прямая установка.

## 5. ГЛАВНЫЕ ОШИБКИ (по убыванию коварности)

### 5.1 Спец-персонажи: клоны Томми — ПОЧИНЕНО в `Createped` (2026-09-16)

**Симптом (было):** `Createped("IGMERC", …)` / `create_spec_ped("IGMERC", …)`
создавали «второго Томми», а не Мерседес/нужного персонажа.

**Причина:** имени спец-актора нет в `name_peds_list`, `find_in_map` возвращал
`model = 0`, и `CREATE_CHAR` создавал педа с моделью 0 = Томми. Дальше шёл
`UNDRESS_CHAR`/`DRESS_CHAR` — механизм **скинов** (переодевания), но скин
спец-актора не ложился поверх чужой основы: базовый пед должен быть **того же
пола**, что и спец-актор.

**Решение (funcs.h, `Createped`):** если имени нет в `name_peds_list`, но оно
есть в `type_specpeds_list` — это спец-актор, и функция сама делает три шага:
1. **пол** — из `type_specpeds_list` (`4` = мужской, `5` = женский:
   IGMERC/IGMERC2/IGCANDY/STRIPA… — женщины, IGPHIL/IGGONZ/IGDIAZ… — мужчины);
2. **базовый пед нужного пола** — женский `WFYST`, мужской `HMYBE` (обычные
   модели из `name_peds_list`, с загрузкой и `MARK_MODEL_AS_NO_LONGER_NEEDED`);
3. **скин спец-актора** — `UNDRESS_CHAR(ped, имя)` + `DRESS_CHAR(ped)`.

Никакой загрузки спец-модели в слоты — только пол + базовый пед + скин.

```lua
ped1 = Createped("IGMERC", x, y, z)   -- теперь девушка с кожей Мерседес
```

**Старая `create_spec_ped`** оставлена как есть (всё ещё создаёт клона Томми:
модель 0) — в миссиях её НЕ использовать, спец-акторы всегда через `Createped`.
Фолбэк-обёртка `create_spec_ped` в `mod.lua` нужна только для старых скриптов,
вызывающих её по имени; новые миссии зовут `Createped` напрямую.

### 5.2 «Второй Томми» — симптом, повторённый дважды

Было две версии бага:
1. mиссия вызывала `create_spec_ped("IGMERC", …)` напрямую → Томми-клон.
2. Полуфикс: фолбэк стоял ПОСЛЕ `Createped(name)` и на `if base` — не
   срабатывал (база валидна). Девушка так и оставалась Томми.

Урок: при «не та модель» проверять не только имя модели в миссии, но и
порядок fallback-в-коде пула моделей. Паттерн «проверь маппинг до создания»
надёжнее паттерна «создай и проверь, что получилось».

**Итог (2026-09-16):** обе версии закрыты — `Createped` сам распознаёт
спец-акторов и создаёт педа правильного пола под скин (раздел 5.1).

### 5.3 Вылет «на последней точке клуба» — UB в удалениях (erase во время итерации)

**Симптом:** миссия доезжает до финальной точки (клуб), вызывается
`remove_blip`/`remove_sphere`/`remove_ped` — и вылет.

**Причины (все найдены и исправлены):**

1. **`remove_blip`** в `funcs.h` стирал элемент из `markeron` ВНУТРИ цикла
   `for (auto it = markeron.begin(); it != markeron.end(); ++it)`:
   ```cpp
   if (L == it->second && blip == it->first) {
       markeron.erase(blip);   // ← erase во время итерации!
   }
   ```
   После `erase` итератор `it` инвалидирован, следующий `++it` — UB → краш.
   **Фикс:** `auto it = markeron.find(blip); if (it != end()) { …; markeron.erase(it); }`.

2. **`removemarker`**, **`remove_sphere`**, **`remove_pickup`** вызывали
   команду движка, но НЕ удаляли запись из своей map (`markeron`/`spheres`/
   `pickupsids`). В map оставалась висячая запись → при `destroy()` объект
   удалялся повторно (двойное `REMOVE_*` по уже удалённому id) → краш.
   **Фикс:** в каждой `remove_*` добавлено `map.find(x) + map.erase(it)`
   с проверкой `L == it->second`.

3. **`remove_car`/`remove_obj`/`remove_ped`** — элемент физически удален, а
   запись в `mapcars`/`mapobjs`/`mappeds` осталась. Позже `destroy()` зовёт
   `GetPedRef/GetVehicleRef/GetObjectRef` по висячему указателю → краш.
   **Фикс:** стирание из map сразу после команды удаления.

4. **`destroy()`** — ТЕ ЖЕ паттерны `erase`
   внутри `for (…; ++it)` во ВСЕХ 6 циклах (markeron, spheres, pickupsids,
   firesids, mappeds, mapcars, mapobjs). **Фикс:** все циклы переписаны на
   безопасный `it = map.erase(it);`/`else ++it;`. (Прежний дубль `all_destroy()`
   удалён как мёртвый код — он нигде не вызывался и не регистрировался.)

**Общий вывод (главный урок всех сессии):**
> Никогда не стирай элемент из std::map во время обхода той же map.
> Для «удали все записи конкретного скрипта » используй
> `for (auto it = m.begin(); it != m.end();) { …; it = m.erase(it); }`,
> а для «удали одну» — `find` + `erase(it)`.

### 5.4 NULL-указатели: движок удалил педа/авто, а Lua продолжает им пользоваться

**Симптом:** вылет при входе на маркер миссии / при обращении к педу, который
уже пропал с карты (когда игрок вышел из машины, движок УБРАЛ транспорт из
пула).

**Причина:** Lua-функции (`getpedhealth`, `ped_walk_to_point`, `giveweaponped`,
`kill_ped_on_foot`, `ped_in_point_in_radius`, `getpedcoordinates_on_y`,
`getcarcoordinates_on_x/y`, `follow_the_leader`, `ped_sprint_to_point`,
`clean_leader`, `ped_save_pos_attack`, `create_marker_actor`, `exitcar` и др.)
брали указатель из пула, получали NULL и обращались к `NULL->…` → segfault.
`try/catch` в C++ ловит только `throw "…"`, а не segfault, поэтому лог молчит.

**Фикс (системный):** во ВСЕХ «опасных» функциях добавлена проверка
`if (ped == NULL / car == NULL) return 0;` (или `push false` для проверок)
в начале блоков с `LUA_TLIGHTUSERDATA`. Список защищённых функций —
в разделе 9.

**Правило для автора миссий:** перед использованием педа/авто, которого
долго проверяли (`getpedhealth`), всегда держать в цикле проверку
`ispers(ped)`/`isvehicle(ped)`; не хранить указатель навсегда — получать
его один раз на цикл (`player = findplayer()`), но объекты миссии
обновлять тоже.

### 5.5 `set_skin` (переодевание) без подгрузки модели скина

**Симптом:** игрок переодевается, скин не применяется / миссия ведёт себя
странно.

**Причина:** `set_skin` в C++ шлёт `UNDRESS_CHAR` со строкой имени модели
скина, но не выполняет предзадержку загрузки (RequestModel + Load). Скин из
`name_peds_list` не был подгружен.

**Фикс (mod.lua):** перед вызовом `native_set_skin` загружаем id скина:
```lua
local skin_models = { PLAYER9 = 4 }
function set_skin(ped, name)
	if skin_models[name] then
		loadmodel(id); load_requested_models()
		while not availablemodel(id) and n < 200 do wait(50); load_requested_models() end
	end
	return native_set_skin(ped, name)
end
```
Пример в миссии: `set_skin(player, "PLAYER9")` на этапе «магазин одежды».

### 5.6 Миссия «зависает на чёрном экране» — непереход между fade-этапами

**Симптом:** `fade(0, msec)` затемняет, игрок телепортируется, но экран
остаётся чёрным.

**Причина:** разрыв между `fade(0)` (затемнение) и `fade(1)` (проявление) —
в середине был `set_camera_position`/`camera_at_point`, которые требуют, чтобы
прошёл `wait()`. Плюс `ped_frozen(0)` при уже замороженном педе.

**Фикс/паттерн:** всегда после `fade(0, t)` ставить `wait(t + запас)` перед
`fade(1)`. Телепортация и работа с камерой — только в чёрном кадре.

### 5.7 `follow_the_leader` требует 2 аргумента, а в миссии 1

**Симптом:** Lua-ошибка «bad argument» или вылет при попытке педа следовать.

**Причина:** C++ `follow_the_leader(ped, leader)` принимает 2 педа, а старая
миссия звала `follow_the_leader(ped1)` однин аргумент.

**Фикс (mod.lua):** обёртка `function follow_the_leader(ped) return
native_follow_the_leader(ped, findplayer()) end` (см. раздел 9).

**Вывод:** при адаптации старых миссий проверять сигнатуры функций, а не
полагаться на «работало раньше».

### 5.8 `destroy()` и перезагрузка скрипта

**Когда вызывается:** `destroy(L)` на `reload` (Ctrl+Backspace) и
`final_scripts()` (выход). Это «когда мы выходим из цикла миссии — удаляется
всё, что мы создали».

**До фикса** все 6 циклов erase-в-итерации → краш именно в момент выхода.
После фикса (5.3/п.4) — просто чистится корректно.

**Правило:** миссия сама обязана чистить свои объекты до `break`, а не
рассчитывать на `destroy()` — но и `destroy()` не должен падать.

### 5.9 ВАЖНО про `remove_*` и map-ы — полный «реестр гигиены»

После фиксов БЕЗОПАСНО использовать только эти функции (они чистят map):

| Lua-функция | Что чистит | Где правилась |
|---|---|---|
| `remove_blip(id)` | markeron | funcs.h |
| `removemarker(id)` | markeron | funcs.h |
| `remove_sphere(id)` | spheres | funcs.h |
| `remove_pickup(id)` | pickupsids | funcs.h |
| `remove_ped(ped)` | mappeds | funcs.h |
| `remove_car(car)` | mapcars | funcs.h |
| `remove_obj(obj)` | mapobjs | funcs.h |
| `remove_sound_by_id(id)` | soundsids | funcs.h (16.09.2026) |

Никогда не вызывать штатные `Command<REMOVE_*>`/`DELETE_OBJECT` «напрямую»
из скрипта в обход этих обёрток — это резервирует висячую запись в map.

**Все функции создания теперь регистрируют объект (16.09.2026, аудит):**
`createped`/`Createped`/`create_spec_ped` → mappeds; `createcar`/`Createcar` →
mapcars; `createobj`/`Createobj` → mapobjs; `create_pickup`/`Create_pickup`/
`create_weapon_pickup`/`create_money_pickup`/`create_pickup_clothes` →

`create_sphere` → spheres; `createfireon*` → firesids;
`play_continuous_sound` → soundsids; **и водители/пассажиры** — `setcardrive`,

**Удаление авто теперь безопасно (16.09.2026):** если игрок или пед сидит в

педов**. Висячие указатели (движок уже удалил сущность) проверяются через
`find*inpool` — запись просто стирается из map.

### 5.10 ABI-краш `CVector` — вылет на `SetObjective(OBJ, pos)` (ПОЧИНЕНО 17.09.2026)

**Симптом.** Миссия молча вылетает на ровном месте (нет Lua-ошибки), чаще
всего в конце. В `lualoader/trace.txt` последние строки — что-то вроде
`ped_walk_to_point: ... setobjective (x, y, z)`, но строки «после setobjective»
НЕТ. В игре — резкий выход на рабочий стол без внятного сообщения.

**Причина (фундаментальная, не про Lua).** SDK собирается компилятором
**clang/MinGW**. У класса `CVector` был *пользовательский* копирующий
конструктор `CVector(const CVector& src)`, поэтому clang считал тип
**нетривиальным** и передавал его в C++-функции **по скрытой ссылке
(указателем)**, а не 12 байтами по значению.

Игра же (`gta-vc.exe`) ждёт `CVector` **по значению**: функция `0x521840`
читает x, y, z прямо со стека (`[esp+0x24]`, `[esp+0x2c]`, `[esp+0x30]`) и
делает `ret 0x10` (чистит 16 байт). SDK до фикса присылал указатель
(`flds (%edx)`), а чистилось 8 байт вместо 16 → **мусорные координаты +
порча стека** → мгновенный вылет.

**Доказательства (машинные, не «на глаз»).**
- Дизасм игры: только `python3` + `pefile` + `capstone` (Ubuntu `objdump`
  не понимает `gta-vc.exe` — «file format not recognized»). `0x521840` = приём
  `CVector` по значению, `ret 0x10`.
- Дизасм толкателя в `CPed.o` до фикса: `push %esi; sub $0xc,%esp; ...
  flds (%edx); ... push %esp; push %eax; call *%esi` — это передача
  **указателя**.
- После фикса толкатель стал чистым `mov $0x521840,%eax; jmp *%eax`.

**Почему это не проявлялось раньше.** Апстрим plugin-sdk собирают на MSVC,
где ABI другой (пользовательский copy-ctor не ломает передачу). Баг вскрылся
именно нашей сборкой на clang/MinGW (миграция SDK 15.09.2026, в игре тогда не
тестировалась).

**Фикс (уже применён, 17.09.2026).**
1. `Plugin-SDK/shared/game/CVector.h`, строка с конструктором →
   `CVector(const CVector& src) = default;`
2. `Plugin-SDK/shared/game/CVectorImplementation.h` — удалить внешнее
   определение `inline CVector::CVector(const CVector& src){...}`.
3. Пересобрать `libPlugin_VC.a` (зависимости через `.d`-файлы в
   `output/mingw/obj/Plugin_VC/Release/`), затем `./build.sh`.
4. Проверка: толкатель `CPed::SetObjective(eObjective, CVector)` должен быть
   чистым `jmp` (без `push %esp`/`sub $0xc`).

**Проверка, что это между тобой и вылетом:**
```
# в ассемблере толкателя не должно быть push %esp перед call *%esi
i686-w64-mingw32-objdump -dr <CPed.o> | grep -A20 '<_ZN4CPed12SetObjectiveE...>'
```

**Что лечится этим фиксом.** Все 12 мест `SetObjective(OBJ, pos)` с `CVector` по
значению (актуальный список даёт `grep -n "SetObjective(OBJECTIVE_[A-Z_]*, pos)" funcs.h`;
на 18.09.2026 это 2455, 2478, 2501, 16463, 16481, 16604, 16657, 16675, 16693,
16711, 16822, 17321 — строки плывут при правках, сверять по факту), а также
`CPed::SetSeek(CVector, float)` (0x4FC740) и любые другие вызовы с `CVector`
**по значению**. Перегрузки `(eObjective, CVector const&)` и `(eObjective,
void*)` НЕ ломались (передача по ссылке/указателю).

**Бэкапы (если понадобится сравнить/откатить):**
`shared/game/CVector.h.orig-presdk-abifix`,
`shared/game/CVectorImplementation.h.orig-presdk-abifix`,
`output/lib/libPlugin_VC.a.orig-presdk-abifix`.

> ⛔ **НИКОГДА не откатывать этот фикс.** Если в SDK снова появится
> `CVector(const CVector& src);` без `= default` — это гарантированный
> вылет на всех `SetObjective(OBJ, pos)`. При каждом обновлении SDK
> переносить патч и перепроверять толкатель.

### 5.11 Миссия «не идёт дальше» на `Createcar` — гонка detached-потока (ПОЧИНЕНО 17.09.2026)

**Симптом.** Скрипт замирает (часто на этапе создания машины, напр. на
пристани), игра при этом жива. В `trace.txt` есть `Createcar: <MODEL>` (обёртка
в `mod.lua` печатает ДО вызова C++), но НЕТ `Createcar: ok` и нет следующего
кода. Баг **нестабильный** — в других прогонах те же машины создаются нормально.

**Две причины (обе в связке `Createcar`/`load_model_before_avalible`):**
1. `load_model_before_avalible` крутит `while (!Command<HAS_MODEL_LOADED>)` —
   при неудачной загрузке модели это **вечный цикл** (скрипт стоит, игра жива).
2. `Createcar` запускал **detached `std::thread(expectations, ...)`**, который
   ждал `car->IsVisible()` и вызывал `Command<MARK_MODEL_AS_NO_LONGER_NEEDED>`
   из **неглавного потока**. `Command<>` внутри использует общий
   `static CRunningScript` (`ScriptCommands.h`, `CallCommandById`) → **гонка**
   с главным потоком скрипта → порча движка скриптов → зависание/вылет.
   Это и есть известные «потоки без mutex» из отчёта миграции SDK.

**Фикс (17.09.2026):**
- Detached-поток убран. `COMMAND_MARK_MODEL_AS_NO_LONGER_NEEDED` вызывается
  **сразу после** `COMMAND_CREATE_CAR` на главном потоке. Это канон SCM:
  `029B request_model` → `038B load_requested_models` → `00A5 create_car` →
  `0249 release_model`. Так делает сама Rockstar.
- В `load_model_before_avalible` добавлены трейсы входа/выхода и прогресс
  каждые ~3000 мс — теперь в `trace.txt` видно, на какой модели застряли.

> ⛔ **НИКОГДА не вызывать игровые `Command<...>` из фоновых потоков.**
> Любая работа с движком — только на главном потоке скрипта. Если нужно
> «сделать что-то после появления объекта» — пиши в очередь (под mutex) и
> разбирай очередь в `wait()` на главном потоке.

> **Сторож миссии и API флага (см. `ЗАМЕТКА_О_МИССИЯХ.md`).** Функции с
> большой буквы (`Getflagmission`/`Setflagmission`/`Start_mission`) переносятся
> на **C++**. Сторож (проверка «погиб/арестован») должен быть **ровно один**:
> при запуске нового сторож старый уничтожается, поэтому потоки не
> пересекаются и конфликта нет.

### 5.12 `GetHeading()` теперь в РАДИАНАХ (ломает все углы) — исправлено

SDK v1004 возвращает у `CPlaceable::GetHeading()` **радианы**, а Lua-скрипты
и опкод `COMMAND_SET_CAR_HEADING` ждут **градусы** 0..360. Из-за этого углы
педов/машин уезжали. Фикс: умножение на `57.295779f` (`180/PI`) в четырёх
местах `funcs.h` (`getpedangle`, `getcarangle`, `getobjangle`, `putincar`).

> **Урок:** после обновления SDK проверяй не только компиляцию, но и
> **семантику** — единицы измерения, порядок аргументов, ABI. То, что
> «собралось», ещё не значит «работает как раньше».

## 6. Что происходит «под капотом» при выходе из миссии

1. Миссия делает `break` из `while true == Getflagmission()`.
2. Управление возвращается в `main()` — внешний `while true` продолжает
   крутиться; миссию можно в любой момент запустить заново (снова на маркере).
3. Созданные объекты, которые мы НЕ удалили вручную, живут в map-ах плагина
   (`markeron`, `spheres`, `mappeds`, `mapcars`, `mapobjs`, `pickupsids`,
   `firesids`) и НЕ удаляются сами по себе — до `destroy()`/`reload`.
4. `destroy(L)` вызывается на `reload` (Ctrl+Backspace) и при завершении
   игры; именно тогда «удаляется всё созданное». До фикса — падало (UB).
5. Поэтому: **культура миссии = всегда чистить за собой**. Иначе:
   - объекты копится между перезапусками (найдутся дубли); 
   - `destroy()` падал (было) / риск двойного удаления (после фикса нет,
     но лишние записи в map загрязняют память).

## 7. Диагностика и отладка

### 7.1 log.txt (штатный лог плагина)

`lualoader/log.txt`:
- строки `loaded <имя>.lua` — какой скрипт загрузился;
- тексты ошибок `throw "..."` из C++-функций (например «bad argument…», 
  «create_spec_ped: CREATE_CHAR вернул NULL»);
- **НЕ видит segfault** — если вылетел без записи в log, это было NULL- 
  обращение или UB (см. 5.3/5.4).

### 7.2 Свой трассер (trace.txt) — лучший друг

В `mod.lua` есть `ma_trace(msg)` — пишет строку в `lualoader/trace.txt`
(создан и очищен заранее). Применяется на «тонких» местах:

```lua
function ma_trace(msg)
	local ok, fh = pcall(io.open, "lualoader\\trace.txt", "a")
	if ok and fh then fh:write(msg .. "\n"); fh:close() end
end
```

Паттерн диагностики: оборачиваем подозрительные функции, чтобы увидеть,
какая САМАЯ ПЛОХАЯ сработала перед вылетом:

```lua
local ortgetpedhealth = getpedhealth
function getpedhealth(ped)
	local h = ortgetpedhealth(ped)
	ma_trace("getpedhealth: " .. tostring(ped) .. " = " .. tostring(h))
	return h
end
```

Последняя строка в trace.txt = место вылета (но помни: NULL-краши иногда
не успевают записать следующую строку — используй трассеры в `foel`,
`follow_the_leader`, `ped_in_point_in_radius`, `remove_*` и т.д.).

### 7.3 «Молчит и лог, и трейс» → это UB/NULL (раздел 5)

Если trace оборвался, а log пуст — почти наверняка:
- обращение к NULL-пед/авто без guard (5.4), или
- erase во время итерации (5.3).
Это два самых частых класса вылетов lualoader-миссий.

### 7.4 Пересборка и проверка

```bash
cd "/mnt/807EB5FA7EB5E954/games/old GTA Vice City/lualoader-src" && ./build.sh
```
- Успех = строка `ГОТОВО: ../lualoader.asi (размер)`.
- Предупреждения `duplicate section .rdata$...` из libstdc++ — штатные.
- Ошибки сборки = `error:` / `undefined reference` — искать их.
- Только `.lua` → `luajit -bl script.lua` (синтаксис) — играть не обязательно.

## 8. Истории ошибок из реальной сессии (хроника миссии «party»)

1. **«В автомобиль садится тommy, а не Mercedes»** → root cause:
   `create_spec_ped("IGMERC")` создаёт клона модели 0 (раздел 5.1).
2. **«Переключается только прокрутка, страница чёрная»** (из другой темы,
   YouTube) — напоминание, что симптомы могут гнать по неверному следу:
   у миссий аналогичный ложный след — «пед вроде создан, а выглядит не так».
   Всегда проверять фактические id моделей, а не «похоже, что».
3. **Вылет «на последней точке»** в trace от `create_sphere ok` → root cause:
   UB в удалениях (раздел 5.3). Починено переписыванием erase-циклов.
4. **Синтаксис mod.lua** — однажды после ручной правки файла трейсер с
   трассировкой сломался (опечатка). Проверка `luajit -bl` обязательна.
5. **Молчаливый вылет в конце миссии** (17.09.2026) → root cause: ABI `CVector`
   (раздел 5.10). Симптом обманчив — похоже на «пришёл не туда», на деле
   порча стека в `SetObjective(OBJ, pos)`. Лечится `= default` у copy-ctor.
6. **«Стою на пристани, миссия не идёт дальше»** (17.09.2026) → root cause:
   детач-поток `expectations` дёргал `Command<>` из неглавного потока + вечный
   цикл загрузки модели (раздел 5.11). Симптом нестабилен: в одних прогонах
   те же машины создаются, в других — стоп на `Createcar: MODEL_INFERNUS`
   без `ok`. Лечится `release_model` сразу после `create_car` на главном потоке.

## 9. Приложение: защищённые обёртки mod.lua (эталон)

В `lualoader/mod.lua` собраны ВСЕ надёжные обёртки, которые стоит иметь у
себя при написании миссий. Приводим ключевые с пояснениями:

```lua
function ma_trace(msg) ... end                 -- трассер в trace.txt

local ortexitcar = exitcar                     -- выходить только если в авто
function exitcar(ped)
	if isped(ped) and is_ped_in_car(ped) then return ortexitcar(ped) end
	return 0
end

local ortremove_car = remove_car               -- удалять только живые авто
function remove_car(car)
	if isvehicle(car) then return ortremove_car(car) end
	return 0
end

local native_follow_the_leader = follow_the_leader
function follow_the_leader(ped)                -- 2-аргументная функция ← 1
	return native_follow_the_leader(ped, findplayer())
end

-- create_spec_ped: устаревший фолбэк для старых скриптов (C++ Createped
-- сам умеет спец-акторов с 16.09.2026: пол + базовый пед + скин).
local spec_fallback = { IGMERC="WFYST", IGMERC2="WFYST", IGCANDY="WFYST",
	FLOOZYA="WFYST", FLOOZYB="WFYST", FLOOZYC="WFYST" }
function create_spec_ped(name, x, y, z)
	if name and spec_fallback[name] then
		return Createped(spec_fallback[name], x, y, z)
	end
	return native_create_spec_ped(name, x, y, z)
end

-- set_skin: предзагрузка модели скина
function set_skin(ped, name)
	if skin_models[name] then
		loadmodel(id); load_requested_models()
		while not availablemodel(id) and n < 200 do wait(50); load_requested_models() end
	end
	return native_set_skin(ped, name)
end
```

## 11. Финальное резюме (что важно запомнить)

1. Миссия на lualoader — это конечный автомат на step-ах внутри
   `while true == Getflagmission()`.
2. Пять классов проблем (по убыванию):
   **UB в удалениях > NULL-указатели > спец-персонажи/скины (починено в
   `Createped`) > сигнатуры функций > fade/камера**.
3. Никогда не erase-в-итерации; всегда чистить свои map.
4. Спец-акторы — только через `Createped` (пол → базовый пед → скин);
   `create_spec_ped` оставлен для старых скриптов и создаёт клона Томми.
5. Всё, что может быть NULL, — проверяй. Движок удаляет сущности без спроса.
6. Трассируй тонкие места (trace.txt), читай log.txt, помни что segfault
   не пишется в лог.
7. Сборка после каждых C++-правок; синтаксис после каждых .lua-правок.

## 12. ПРАВИЛА БЕЗОПАСНОСТИ — как НЕ сломать то, что работает

> Прочитай ПЕРЕД любой правкой. Цена нарушения — часы на поиск и сломанная
> миссия.

1. **Бэкап до правки.** Трогаешь SDK или `funcs.h` — сначала
   `cp file file.orig-<что-и-зачем>`. Пример имён:
   `CVector.h.orig-presdk-abifix`.
2. **Патч `CVector` ABI (5.10) — неприкосновенен.** Не откатывать, не
   «упрощать». При обновлении SDK — переносить заново и перепроверять
   толкатель дизасмом.
3. **«Работает — не трогай».** Не переписывай рабочие функции ради красоты,
   стиля или «а вдруг так лучше». Меняешь только то, что доказанно сломано.
4. **Игровые вызовы — только из главного потока.** Никаких `std::thread`,
   дёргающих `Command<>` (5.11). Нужен отложенный эффект — очередь под mutex,
   разбор в `wait()`.
5. **Каждая C++-правка → `./build.sh`.** Успех — строка
   `ГОТОВО: ../lualoader.asi (6,1M)`, 0 ошибок. «duplicate section … has
   different size» — известный безвредный шум MinGW.
6. **Каждая правка `.lua` → `luajit -bl файл.lua`** (проверка синтаксиса).
7. **Проверяй в игре и читай trace.** Последняя строка `trace.txt` — где
   остановилось; `log.txt` — ошибки Lua; сегфолт в лог не пишется.
8. **Фикс доказывай машинно.** Дизасм (objdump/pefile+capstone), а не
   «вроде заработало». После обновления SDK прогоняй миссию целиком.
9. **Проверяй семантику после обновления SDK**, а не только компиляцию:
   единицы (радианы/градусы, 5.12), порядок аргументов, ABI классов.
10. **Не объявляй успех без теста.** Собралось ≠ работает. Не выдумывай
    пути/файлы — бери реальные (`ls`, `grep`), а не догадки.
