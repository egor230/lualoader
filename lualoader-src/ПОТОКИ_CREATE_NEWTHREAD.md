# Потоки в lualoader: `create_newthread` — что это на самом деле, и почему
маркеры грузовиков переехали в главный цикл

**Дата:** 21.09.2026. **Повод:** миссия `misson riot.lua` стала крашиться через
~47 секунд после старта бунта (жёсткий вылет игры, без сообщения о провале).
Документ — выводы из разбора этого краша, чтобы больше не повторять.

---

## 1. `create_newthread` — это ОТДЕЛЬНЫЙ `lua_State`, а не корутина

Реализация — `plugin.cpp:357-387`. По шагам:

```cpp
lua_pushlightuserdata(L, L);
lua_gettable(L, LUA_REGISTRYINDEX);      // достать имя текущего скрипта
lua_State* L1 = luaL_newstate();         // НОВОЕ состояние, не корутина на L
luaL_openlibs(L1);  funs(L1);            // свой набор C++-функций
for (...) { lua_pushvalue(L, i); lua_xmove(L, L1, 1); }   // копия аргументов
luastate.push_back(L1);
luaL_loadfile(L1, luaname);              // загрузить ТЕКУЩИЙ lua-файл
lua_pcall(L1, 0, 0, 0);                  // ...И ВЫПОЛНИТЬ ЕГО ЦЕЛИКОМ (top-level)
lua_pushvalue(L1, 1);
std::thread([=]() { lua_resume(L1, NULL, args, NULL); }).detach();
this_thread::sleep_for(chrono::milliseconds(301));
```

Что из этого следует (проверено, а не предположено):

1. **Поток живёт в другом `lua_State`.** Все `local` главного состояния
   (включая upvalues замыканий) там **не существуют**. Функция, которую
   передаёшь в поток, обязана быть **глобальной** — `local function` дочерний
   поток не увидит (в эталоне `lualoader.tar` `check_car` — глобальная).
   Исключение: то, что передано **аргументами**.
2. **Аргументы копируются через `lua_xmove`.** `lightuserdata` (указатели на
   педов/авто/объекты) — это сырые адреса, они переносятся корректно:
   эталонный `create_car_with_driver(m, x, y, z, a)` именно так и передаёт
   созданную машину в `check_car`.
3. **Файл выполняется в дочернем состоянии второй раз** (`lua_pcall(L1,0,0,0)`
   — top-level). Для `misson riot.lua` это безопасно: на верхнем уровне только
   `require("lualoader/mod")` и определение глобальной `main()`. **Если бы
   top-level создавал объекты/блайпы — они бы задвоились.** Перед
   использованием потоков в новом скрипте — проверить top-level файла.
4. **`main()` в дочернем потоке НЕ вызывается** (resume'ится только переданная
   функция). Двойного старта миссии не происходит.
5. `sleep_for(301ms)` стоит **после** отщёлкивания потока — поэтому несколько
   `create_newthread` подряд разносят старт потоков на ~0.3 с. Это НЕ защита от
   race, просто случайный stagger.

## 2. `Getflagmission` (большая) vs `getflagmission` (маленькая) — ловушка
   привязки `mission_watch_L`

- `getflagmission` (`funcs.cpp:2323`) — **чистое чтение** флага миссии. Поток
  безопасен для состояния: ничего не меняет.
- `Getflagmission` (`funcs.cpp:2410`) — **перепривязывает глобальный
  `mission_watch_L` к вызывающему `lua_State`** на каждом вызове. Это тот
  указатель, по которому C++-сторож гибели/ареста игрока вызывает `destroy()`.

**Следствие:** если цикл потока-наблюдателя вызовет большую `Getflagmission`,
то при смерти игрока `destroy()` почистит объекты **дочернего** состояния
(маркер потока), а объекты главного состояния (грузовики, педы, блайпы)
**останутся в мире навсегда** — утечка + мусор на карте после возрождения.

**Правило:** в дочерних потоках — **только маленькая** `getflagmission`
(именно так делает эталон `check_car` из `lualoader.tar`). В главном цикле
миссии — большая `Getflagmission` (она и держит привязку).

## 3. Аудит потокобезопасности плагина — что можно дёргать из потока

Проверено по `funcs.cpp`:

| Ресурс | Где | Потокобезопасно? |
|---|---|---|
| `markeron`, `spheres`, `pickupsids`, `firesids`, `soundsids`, `mappeds`, `mapcars`, `mapobjs` | `funcs.cpp:16-23` | **НЕТ** — `static std::map` **без мьютекса** |
| `findcarinpool` / `findpedinpool` / `findobjinpool` | `funcs.cpp:23635` / `23589` / `23610` | **НЕТ** — `sleep_for(1ms)` + полный скан пула; игра в это время мутирует пул (трафик, riot-педы) |
| `cpp_trace` / `cpp_tracef` | `funcs.cpp:23983+` | **ДА** — `mtx.lock()` |
| `getflagmission` (маленькая) | `funcs.cpp:2323` | Да (чистое чтение) |
| `Getflagmission` (большая) | `funcs.cpp:2410` | См. §2 — побочный эффект на `mission_watch_L` |

**Любая C++-функция, пишущая в `markeron`/`mapcars`/… (`create_marker*`,
`remove_blip`, `create_*`, `remove_*`), из потока = data race на `std::map`.**
`std::map` при одновременной вставке/удалении — UB, классический segfault.

## 4. Краш Riot: что показал `trace.txt`, и где корень

### Симптом
После переноса «снять маркер с грузовика сразу при уничтожении» на 3
потока-наблюдателя (`create_newthread(truck_marker_watch, truckN)`) миссия
стала вылетать. `trace.txt` (2294 строки) последовательно:

1. `riot: вся толпа взбешена ($2205=1), dressed=0` — эскалация.
2. `riot: ворота открываются (SLIDE_OBJECT …)` + `printmessage` (LAW4_14).
3. **1420 строк `getflagmission = true`** — это 3 потока-наблюдателя крутились
   ~47 с (wait(100) каждый).
4. **И больше ничего.** Нет `destroy: ВХОД`, нет `mission_watch: игрок
   погиб/аррестован`.

**Вывод №1: это НЕ провал миссии** (тогда был бы `destroy`/`M_FAIL`), а
**жёсткий краш** (segfault) — процесс умер, никто не успел дописать трассу.
`log.txt` тоже чист — Lua-ошибок нет, падение не в Lua.

### Корень
Поток-наблюдатель делал `create_marker(truck)` → `create_marker_car`
(`funcs.cpp:1240`): **`markeron.emplace(marker, L)` без мьютекса** +
`findcarinpool` (скан пула + `sleep_for`). При уничтожении — `remove_blip` →
**`markeron.erase`**. Три потока + главный цикл + возможный `destroy()` —
одновременные вставка/удаление в `std::map` → UB → segfault.

**Почему именно ~47 с и «сразу после открытия ворот»:** ворота открываются при
эскалации, дальше идёт бой. Игрок жжёт грузовики молотовами — 2-3 машины
гибнут в одной вспышке → **2-3 `remove_blip` одновременно** → race в `markeron`
→ краш. До боя потокам было не за что бороться (только чтение), поэтому
47 с всё работало.

### Фикс
Потоки убраны. Маркеры создаются в `spawn_trucks()` (главный поток), а
снимаются **покадрово в главном цикле** `step == 3`:

```lua
if mt1 ~= nil and (truck1 == nil or not isvehicle(truck1) or iscardead(truck1)
 or 0 == getcarhealth(truck1) or iscarfire(truck1)) then remove_blip(mt1) mt1 = nil end
-- (и для mt2, mt3)
```

Поведение «маркер исчезает в момент уничтожения грузовика» сохранено в точности
и стало даже **быстрее**: главный цикл крутится каждый кадр, а поток делал
`wait(100)` (до 100 мс задержки). Заплатили только потерей «параллельности»,
которая тут и не нужна.

Пост-цикловая очистка (смерть/арест) тоже снимает `mt1..mt3`, если миссия
провалена до уничтожения грузовиков.

## 5. Выводы-правила (бери в следующую миссию)

1. **Поток в lualoader — это не «лёгкий способ следить за объектом».** Каждый
   дочерний поток, дотрагивающийся до `markeron`/`mapcars`/… или сканирующий
   пулы, — кандидат на плавающий краш через десятки секунд.
2. **Следить за состоянием объекта (маркер, HP, «уничтожен?») — в главном
   цикле миссии**, каждый кадр. Это и потокобезопасно, и отзывчивее
   (`wait(100)` в потоке = задержка до 100 мс).
3. **Потоки оправданы** только для действительно независимой долгой работы,
   которая НЕ касается общих map-ов и пулов (чистые вычисления, свой
   `lua_State`, свой набор объектов). Если из потока нужно повлиять на мир —
   безопасного канала в Lua **нет** (состояния изолированы, общие globals
   отсутствуют), а C++-канал не мьютексен.
4. **Маленькая `getflagmission` в потоках, большая `Getflagmission` в главном
   цикле** (§2).
5. **Top-level файла выполняется в каждом дочернем потоке заново** — не
   создавать объектов/блайпов на верхнем уровне скрипта (§1.3).
6. **Функция потока — глобальная**, аргументы (включая указатели) переходят
   через `lua_xmove` корректно; локалы главного состояния — нет (§1.1-1.2).
7. **Диагностика краша по `trace.txt`:** обрыв на «молчаливых» повторах
   (`getflagmission = true` × N) + отсутствие `destroy: ВХОД` и
   `mission_watch: игрок погиб` = жёсткий краш, а не штатный провал. Считать
   какие именно трассы забили хвост — это укажет на виновный поток.

## 6. Бонус этой же сессии: софтлок «пикап одежды пропадает»

**Симптом пользователя:** если сразу пойти на стройку (мимо Рафаэля), метка
одежды пропадает — переодеться больше нельзя.

**Причина:** при подъезде к стройке (`step 1 → 3`) блайп и сфера у Рафаэля
снимались **безусловно**. А триггер катсцены переодевания был привязан только к
`step == 1` — после старта сцены (`step == 3`) переодевание становилось
недоступно навсегда.

**Фикс:**
- Блайп/сфера одежды снимаются **только если `dressed == 1`** (игрок уже
  одет). Без одежды метка остаётся на всю миссию.
- Триггер катсцены переодевания работает и на `step == 1`, и на `step == 3`:
  `(step == 1 or step == 3) and dressed == 0 and not is_ped_in_car(pp)`.

Это укладывается в логику оригинала: в одежде рабочие дерутся друг с другом,
без одежды — валят игрока; переодеться можно в любой момент, но если толпа
уже взбесилась на игрока, одежда её не успокоит (как в оригинале).

**Универсальное правило:** любые навигационные маркеры/сферы снимаются в
переходе этапов **только когда соответствующий флаг выполнен**, а не «по
факту перехода».
