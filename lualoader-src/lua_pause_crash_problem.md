# ПАУЗА СКРИПТОВ В GTA VC (reVC/Wine): ХРОНИКА МГНОВЕННОГО ВЫЛЕТА

> Дата последнего обстоятельства: **2026-09-22 09:32 (локальное время)**
> Плагин: `lualoader.asi` (Lua 5.4.9 статика), игра GTA Vice City (reVC), Wine 9+ на Linux
> Архитектура: 5 Lua-скриптов, каждый в отдельном `std::thread` (`pump_owner`), которые выполняют 504+ прямых вызовов `Command<COMMAND_*>` / обращений к игровым структурам (CPed/CVehicle) **параллельно с игровым потоком**.

---

## 1. СИМПТОМ (НЕИЗМЕННЫЙ ВО ВСЕХ ИТЕРАЦИЯХ)

При нажатии **Ctrl** (пауза / отключение всех Lua-скриптов) игра **мгновенно вылетает**.
В `lualoader/trace.txt` последняя запись — строка входа/запрос паузы, после — обрыв.
Пользователь квалифицирует: «получил вызов» (краш-диалог / завершение процесса).

**Цель (не поменялась):** Ctrl = поставить ВСЕ Lua-скрипты на паузу (заморозить)
без вылета. Пауза обратимая, без закрытия и переинициализации lua_State.

## 2. ХРОНОЛОГИЯ ИТЕРАЦИЙ

### Итерация 1 — исходный баг (краш в reload-потоке)
- НЕПОСРЕДСТВЕННО в потоке перезагрузки (thread=472, reload-поток) вызывались:
  ```cpp
  CMessages::AddMessageJumpQ(L"Scripts disabled", 2000, 1);
  CTheScripts::ScriptSpace[OnAMissionFlag] = false;
  ```
- Трейс: `ПАУЗА: вход (thread=472), скрипты замораживаются (yield-пауза без teardown)` → ОБРЫВ.
- **Диагноз сервиса:** data race — reload-поток писал игровую память (`ScriptSpace`,
  `AddMessageJumpQ`) без синхронизации с игровым потоком.

### Итерация 2 — первый фикс (перенос записи игровой памяти в игровой поток)
Внедрено:
1. Флаги-запросы `std::atomic<bool> pause_requested / resume_requested / teardown_mission_flag_pending`.
   reload/teardown-потоки **перестали** писать игровую память — только ставят флаги.
2. Реальные записи (`ScriptSpace[OnAMissionFlag]=false`, `AddMessageJumpQ`)
   перенесены в `Events::gameProcessEvent` — исполняется на игровом потоке каждый кадр.
3. `mission_flag_get()/mission_flag_set_safe()` со bounds-guard `OnAMissionFlag < 260512`
   (размер `CTheScripts::ScriptSpace`), продублировано в `setflagmission`,
   `setstatusmission`, `getstatusmission`, `getflagmission`.
4. `load_model_before_avalible` и `expectations` — кооперативный wait по `scripts_paused`
   (`if (scripts_paused.load()) { sleep; continue; }`).
5. Crash handler `SetUnhandledExceptionFilter` — пишет `trace.txt` прямым WinAPI
   (CreateFileA/WriteFile, без CRT-буферов): код/адрес/тип исключения.

**Результат:** трейс стал `ПАУЗА: запрос (thread=468)` → `ПАУЗА: применена в игровом
потоке (thread=280), скрипты заморожены` → ОБРЫВ. Вылет остался, crash handler
НЕ оставил строки `CRASH:` (grep == 0).

### Итерация 3 — текущий фикс (по детальному плану сервиса от 2026-09-22 09:26)
Сервису задан максимально подробный вопрос (полный новый трейс, код, гипотезы,
включая «почему handler не сработал»). Получен план в `/home/egor/lua_crash_final_analysis.md`.
Внедрено:

1. **УБРАН источник гонки** — при паузе плагин больше **НЕ пишет**
   `ScriptSpace[OnAMissionFlag]=false`. Заключение сервиса (Q3/Q7):
   - запись в момент активных `Command<>` = data race → мгновенный краш;
   - скрипты останавливаются через `scripts_paused` (yield в `wait()`), флаг миссии им не нужен;
   - сброс «миссии» ломает логику самой ИГРЫ.
2. **Барьерная пауза** — счётчик `active_pump_threads`:
   - pump-потоки `fetch_add(1)` перед активной зоной (`lua_resume`, в которой вызываются
     `Command<>`), `fetch_sub(1)`+`pause_cv.notify_all()` после (скрипт отдал ход / yield);
   - при `scripts_paused` pump паркуется в цикл (`continue`), счётчик остается 0;
   - `pause_scripts()`: `scripts_paused=true` → ждёт через `pause_cv.wait_for(1с)`
     пока `active_pump_threads==0` (лог: `барьер — все припаркованы` / `TIMEOUT`);
   - только после барьера игровой поток применяет `AddMessageJumpQ`.
3. **Усиленный ловец краша**:
   - `AddVectoredExceptionHandler(1, lua_vectored_filter)` — FIRST=1, видит исключение
     РАНЬШЕ любых SEH reVC (в т.ч. если reVC перезаписал наш UnhandledExceptionFilter);
   - `std::set_terminate(lua_terminate_handler)` — ловит abort/необработанное C++;
   - `atexit(lua_atexit_handler)` — отличает нормальный `exit()` от краша.

## 3. НАБЛЮДЕНИЯ ПОСЛЕ ИТЕРАЦИИ 3 (сессия 09:32, трейс-в-трейс)

Трейс (последние строки, реальные маркеры НОВОГО билда):

```
C++| VECTORED: code=0x40010006 addr=0x7B569767 thread=280        (xN раз)
C++| ПАУЗА: барьер — жду выход из активной зоны (активных=0)
C++| ПАУЗА: барьер — все pump-потоки припаркованы (активных=0)
C++| VECTORED: code=0xC0000005 addr=0x7725EFDD thread=448
C++| ПАУЗА: запрос (thread=468), скрипты замораживаются (yield-пауза без teardown)
C++| ПАУЗА: применена в игровом потоке (thread=280), скрипты заморожены
C++| VECTORED: code=0xC0000005 addr=0x7725EFDD thread=460
C++| (множественные сообщения VECTORED: code=0xC0000005 addr=0x7725EFDD thread=448/460/464 ...)
```

**Ключевые факты (новые, точные):**
1. **Vectored-обработчик теперь работает** — в отличие от `SetUnhandledExceptionFilter`,
   краш пойман. Именно это подтверждает гипотезу сервиса: reVC/Wine не давали нашему
   UnhandledExceptionFilter управление (перезаписанный фильтр / `__try/__except` внутри
   reVC / трансформация в POSIX-сигнал).
2. **Барьер паузы РАБОТАЕТ**: `активных=0`, все pump-потоки припаркованы ДО применения паузы.
3. **Краш всё равно происходит** — и это теперь **Access Violation 0xC0000005** по одному
   и тому же адресу **0x7725EFDD** на нескольких потоках (448, 460, 464).
4. `code=0x40010006` (DBG_PRINTEXCEPTION_C) в thread=280 — **нормальное** отладочное
   исключение Wine, НЕ краш (игнорируется нами через EXCEPTION_CONTINUE_SEARCH).

**Интерпретация:**
- Краш — это AV **по одному адресу 0x7725EFDD**, причём одновременно/подряд на 3 разных
  потоках. 0x7725EFDD — системный модуль (Wine/ntdll/kernel32-образная область) — вероятно,
  общий код (например, строковые/аллокационные паттерны Wine, стековый вызов из DLL-процедуры),
  на который приходят паразитные/псевдоуказатели.
- Проверка `OnAMissionFlag < 260512` и отсутствие записи ScriptSpace при паузе устранили
  «классическую» гонку — но краш жив. Значит либо (а) осталась гонка игровых данных от
  Command<> в OTHER контексте, либо (б) повреждение кучи/стека системных структур случилось
  РАНЬШЕ и проявилось именно в момент паузы (точечный симптом в 0x7725EFDD — следствие,
  а не причина).

## 5. НЕ РЕШЕНО / ОТКРЫТЫЕ ВОПРОСЫ

1. **Причина AV 0x7725EFDD на потоках 448/460/464** — НЕ установлена.
   Нужно: под каким модулем адрес (Wine/ntdll?), что за код (сигнатура/символ),
   какой «виновник» передавал параметр в этот системный вызов.
2. Возможна ли **остаточная гонка самих `Command<>`** между pump-потоками и игровым
   циклом ВНЕ момента паузы (она существует по построению: 504 вызова из worker-потоков).
   Барьер защищает только «во время паузы», не «во время обычной работы».
3. Может ли повреждение памяти происходить **ДО паузы** и лишь проявляться в момент
   паузы (симптом-следствие)? Для ответа — трейс с записью `pump_owner START/END`,
   и/или проверка кучи (в Wine это сложно).
4. Проверить `0x7725EFDD` с помощью привязки к модулю через
   `WINEDEBUG=+seh,+relay` и/или gdb backtrace всех потоков на момент краша.

## 6. СЛЕДУЮЩИЕ ШАГИ (черновик, когда возобновим работу)

1. Определить модуль/функцию по адресу 0x7725EFDD (gdb на живом процессе:
   `gdb -p $(pidof reVC.exe) -batch -ex "x/i 0x7725EFDD"`, или лог `WINEDEBUG=+seh`).
2. Понять, ЧТО передаёт каждый поток в 0x7725EFDD (общий буфер/строка/аллокация) —
   это укажет на источник порчи.
3. Подтвердить/опровергнуть гипотезу «повреждение до паузы»: добавить контрольную
   маркировку состояния Lua/педов перед паузой (схема «сертификат здоровья»).
4. Если причина — системный вызов при массовой припарковке потоков — рассмотреть
   вариант, что парковка потоков через 1ms-sleep мутирует N потоков слишком близко;
   альтернатива — парковать через `WaitOnAddress` / ConditionVariable с полноценным
   сном (std::condition_variable), а не busy-sleep цикл.
