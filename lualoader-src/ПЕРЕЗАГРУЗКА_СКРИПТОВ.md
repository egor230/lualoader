# Перезагрузка скриптов в lualoader — как это устроено (подробно)

**Файл:** `plugin.cpp` (ядро плагина, точка входа ASI).
**Версия документа:** 20.09.2026, совместно с правками «расширение reload»
(stop_mission_watch + onScriptTerminate + lua_close). Документ описывает ТОЛЬКО
фактическое состояние кода после этих правок.

ВАЖНО: это **свой** lualoader для GTA VC (встраивание Lua 5.4), НЕ MoonLoader.
Несмотря на то, что термин `reload()` тут есть, механика основана на паттерне
«Hot Reload» (детекция → teardown → пересоздание состояний) — но реализована
СВОИМИ руками:

---

## 0. Общая картина (3 флага + 2 системных потока)

Ядро работает одним долгоживущим C++-кодом внутри ASI. Управление скриптами
держится на двух глобальных флагах и двух служебных потоках:

| Что | Где | Роль |
|-----|-----|------|
| `star_thread::star_second_thread` | plugin.cpp:6 | «Скрипты вообще разрешены/запущены». Выкл. → reload не стартует |
| `star_coroutine::coroutine` | plugin.cpp:15 | «Второй поток у скрипта разрешён». Выкл. → скриптам запрещается второй поток |

## 1. Триггер: как перезагрузка включается (Ctrl)

Функция `reload()` (plugin.cpp:262) — отдельный бесконечный поток, который
рождается из `search_scripts()` при КАЖДОМ запуске скриптов. То есть после
каждой перезагрузки наблюдатель перезапускается снова (см. конец §4).

```cpp
int reload() {
    // ФАЗА 1: ждём НАЖАТИЕ Ctrl ИЛИ отключение скриптов
    while (true) {
        sleep_for(1ms);
        if (KeyPressed(VK_CONTROL) || !star_thread::get())
            break;                    // Ctrl нажат (либо скрипты выключены)
    }

    // ФАЗА 2: ждём ОТПУСКАНИЕ Ctrl — затем производим перезагрузку
    while (true) {
        sleep_for(1ms);
        if (!KeyPressed(VK_CONTROL)) {   // Ctrl отпущен → перезагрузка!
            CMessages::AddMessageJumpQ(L"Script reloaded", 2000, 1);
            … teardown всех состояний (см. §3) …
            sleep_for(100ms);
            std::thread(start_lualoder).detach();  // НОВЫЙ запуск скриптов
            break;
        }
        if (!star_thread::get()) break; // скрипты выключили во время удержания Ctrl
    }
    return 0;
}
```

КЛЮЧЕВОЕ ПРО ТРИГГЕР:
- `KeyPressed(VK_CONTROL)` — это `plugin::KeyPressed` из Plugin-SDK
  (Other.cpp:23): `(GetKeyState(keyCode) & 0x8000) != 0`. Отрабатывает
  ТОЛЬКО по высокому биту (клавиша УДЕРЖИВАЕТСЯ), не по краю. Поэтому
  перезагрузка НЕ сработает при системном «повторе нажатия» — фаза 2 ждёт
  именно отпускания.
- Тест две фазы: Ctrl нажат → Ctrl отпущен. Если просто коротко «дожать» —
  сработает; если держать долго и отпустить — сработает по факту отпускания.
- Если в этот момент `star_thread` выключен (игра в меню/на загрузке) — reload
  вылетает без действий.

## 2. Что значит «перезагрузить» архитектурно

Перезагрузка = **полностью пересоздать набор `lua_State`**:

1. Остановить старое поколение состояний (teardown, §3).
2. Заново вызвать `start_lualoder()` → `search_scripts()` → для каждого `.lua`
   новый `startscipt` → новый `lua_State` → заново зарегистрировать функции,
   заново выполнить файл (`luaL_loadfile` + `lua_pcall`), заново запустить
   `main()` через `lua_resume`.

ВАЖНО (классическая проблема Hot Reload, она здесь реальна):
- Каждый `lua_State` — **изолирован** (plugin.cpp:58 `struct state` создаёт
  `luaL_newstate()` + `luaL_openlibs`). Глобальные переменные скрипта НЕ
  переживают перезагрузку. Если нужно хранить состояние между reload —
  писать на диск (файл) или в C++-хранилище плагина.
- `lua_close` полностью освобождает состояние. Поэтому после reload
  ссылки из «прошлой жизни» (глобалы, userdata, upvalues) — мертвы.

## 3. Teardown / graceful shutdown — шаги 1 на 1 с кодом

Полный блок teardown (plugin.cpp:274-297, идентичен тексту в `final_scripts`
plugin.cpp:226-249). Разберём последовательно:

```cpp
// ---- (1) Стоп-флаги ----
bool k = false;
star_coroutine::set(k);                 // запретить скриптам второй поток
unsigned int& OnAMissionFlag = *(unsigned int*)0x978748;
CTheScripts::ScriptSpace[OnAMissionFlag] = k;  // выключить творческий флаг миссии
stop_mission_watch();                   // остановить сторож миссии (funcs.cpp:2399)
```

(1) Причина порядка: флаг миссии снимается ПЕРВЫМ, чтобы скрипт, висящий в
`while true == Getflagmission()`, увидел ложь и штатно вышел (а не был бы
разорван в неопределённом месте). `stop_mission_watch()` присоединяет/jоин сторож,
иначе тот захочет `destroy(mission_watch_L)` уже ПОСЛЕ `lua_close` (висячий
указатель / UAF — это и было «проблемой мёртвых хуков»).

```cpp
// ---- (2) По каждому живому состоянию ----
for (auto L : luastate) {

    // (2a) Поднять прерывающий хук: форсить остановку исполнения
    lua_sethook(L, (lua_Hook)hookFunc, LUA_MASKCOUNT, 100);

    // (2b) Дождаться, пока main-корутина скрипта завершится (status == LUA_OK)
    while ((LUA_YIELD == lua_status(L)) || (LUA_OK != lua_status(L)))
        sleep_for(1ms);

    // (2c) GRACEFUL: если скрипт объявил глобальную onScriptTerminate() — вызвать её
    lua_getglobal(L, "onScriptTerminate");
    if (lua_type(L, -1) == LUA_TFUNCTION) {
        if (lua_pcall(L, 0, 0, 0) != LUA_OK) {   // pcall — ошибка не роняет reload
            const char* err = lua_tostring(L, -1);
            if (err) writelog(err);
            lua_pop(L, 1);
        }
    }
    else { lua_pop(L, 1); }                       // не объявлена → просто убрать nil

    // (2d) destroy(L) — СУЩЕСТВУЮЩАЯ функция очистки всех игровых объектов
    destroy(L);                    // funcs.cpp:23468 — снимает блобы/пикапы/педы/авто/огни/звуки/объекты

    // (2e) Принудительный GC
    lua_gc(L, LUA_GCCOLLECT, 100);

    // (2f) ПОЛНОЕ уничтожение состояния (это был пропущенный шаг до 20.09.2026)
    cpp_trace("reload: lua_close состояния");
    lua_close(L);
};

// ---- (3) Очистка списка ----
luastate.clear();                 // было UB: pop_front() в range-for по std::list
cleanstl();                       // очистка C++-STL-хранилищ (markeron, spheres, …)
```

### Что реально делает `destroy(L)` (funcs.cpp:23468)
Итерирует ВСЕ C++-контейнеры, чьи ключи привязаны к `lua_State*`:
- `markeron` → `COMMAND_REMOVE_BLIP` (блобы на карте)
- `spheres` → `COMMAND_REMOVE_SPHERE`
- `pickupsids` → `COMMAND_REMOVE_PICKUP`
- `firesids` → `COMMAND_REMOVE_SCRIPT_FIRE`
- `soundsids` → `COMMAND_REMOVE_SOUND`
- `mapcars` → `safe_remove_car` (сначала высадить сидящих)
- `mappeds` → высадить из авто, `COMMAND_MARK_CHAR_AS_NO_LONGER_NEEDED`, убрать из мира
- `mapobjs` → `COMMAND_DELETE_OBJECT`, убрать из мира
- сбрасывает `corona::set(…)`

Внимание: `destroy` использует `findpedinpool`/`findobjinpool`, в которых есть
`sleep_for(1ms)` — то есть destroy в этом виде тяжеловат, но НЕ вызывается в
кадровом цикле, только в teardown, так что ок.

### Что НЕ входит в teardown (не добавлять без необходимости)
- Хуки на события игры / рендер? Если скрипт их вешал — их снимает сам скрипт
  в `onScriptTerminate()` (это ровно та причина, по которой шаг (2c) добавлен).
- Потоки, созданные `create_newthread` — они на своих `lua_State*`, и эти
  состояния тоже лежат в `luastate`, поэтому будут закрыты этим же циклом.

## 4. Новая жизнь скрипта: startscipt (plugin.cpp:87)

После teardown вызывается `start_lualoder()` → `search_scripts()` →
`startscipt(res, luafile, luastate)`. Это отдельный detached-поток на КАЖДЫЙ
`.lua`:

```cpp
int startscipt(string res, char* luafile, list<lua_State*>& luastate) {
    state Lua;                          // luaL_newstate + luaL_openlibs
    lua_State* L = Lua.get();
    lua_gc(L, LUA_GCSTOP, 1);           // GC выключен до reload (экономия кадров)

    // пакетный путь: package.path = <папка игры>\?.lua
    …

    funs(L);                            // register.cpp: зарегистрировать ВСЕ функции (lua_register)

    int status = luaL_loadfile(L, luafile);  // компиляция в байткод (НЕ выполнение)
    if (status == 0) {
        writelog("loaded " + res);      // строка в log.txt
        star_coroutine::set(true);      // разрешить второй поток

        // Реестр: L -> имя файла (для get_current_name_luascript)
        lua_pushlightuserdata(L, L);
        lua_pushstring(L, luafile);
        lua_settable(L, LUA_REGISTRYINDEX);

        lua_sethook(L, hookFunc, LUA_MASKCOUNT, 0);  // хук выключен
        lua_pcall(L, 0, 0, 0);           // ВЫПОЛНИТЬ файл (создаст main() и пр.)

        lua_getglobal(L, "main");
        if (lua_type(L, -1) == LUA_TFUNCTION) {
            luastate.push_back(L);       // теперь состояние видно core (reload его увидит)
            lua_resume(L, NULL, 0, NULL); // запустить main()

            lua_State* L1 = lua_newthread(L);  // второй поток (корутина)
            … // цикл перекрёстных resume: пока main не закончен —
              // поочерёдно возобновляет L (основной) и L1 (второй)
              // с хуком на 800 инструкций
        }
    }
    else { writelog("could not load " + lua_tostring(L,-1)); }  // синтаксис/загрузка
    return 0;
}
```

Ключевые детали для будущей модели:
- **Лёгкое несовпадение с пунктом «про MASKCOUNT 100» в teardown:** обычный после
  старта hook = 0 (выкл), а во время цикла ожидания ставится 800. Смысл этих
  чисел — «сколько инструкций скрипт работает до принудительного yield корутины»,
  чтобы игра не умирала от одного жрущего CPU скрипта.
- Когда reload ставит hook на 100 — это «аварийный тормоз»: скрипт, у которого
  `main` не хочет заканчиваться (не слушает `getflagmission`), в итоге будет
  yield-иться каждые 100 инструкций, и `lua_status(L)` не станет `LUA_OK`
  вечно → reload ЗАВИСНЕТ на шаге (2b). Скрипты обязаны слушать флаг миссии.
- `dellod()` в `search_scripts` чистит `log.txt` перед запуском: НЕЛЬЗЯ
  диагностировать reload по «старому» логу — только по свежему, после прогона.

## 5. Что делает сторож миссии (funcs.cpp:2345+)

`Getflagmission`/`Setflagmission` (большие буквы) поднимают **один** независимый
C++-поток `mission_watch_proc`:
- каждые 100 мс: умер/арестован игрок → «Миссия провалена» + флаг false + `destroy(L)`.
- флаг сменился сам → выход.
На reload ОБЯЗАТЕЛЬНО вызывать `stop_mission_watch()` (funcs.cpp:2399) — она
приказывает потоку выйти и делает `join()`, а после ставит `mission_watch_L = nullptr`,
чтобы не остался висячий указатель на закрытый `lua_State`.

## 6. О чём МОЛЧИТ код (важные ошибки/грабли для будущей модели)

1. **`luastate` — не защищён мьютексом.** `startscipt` пушит в конец, а `reload`
   итерирует и чистит. Обычно стартуют не одновременно (search_scripts работает,
   reload ждёт Ctrl), но при очень быстром Ctrl ДО окончания всех startscipt —
   data race. Пока не чинили; знать и не устраивать гонку.
2. **Хук 100 в teardown не «останавливает» сам по себе** — он лишь заставляет
   бесконечный скрипт yield-иться; выход из цикла ожидания (2b) гарантирован
   только если `main()` в итоге вернётся (обычно через `getflagmission=false`).
   Если скрипт упёрся в `while true do wait() end` без проверки флага миссии —
   reload зависнет навсегда. Это диагностируется по trace: нет строк
   «reload: lua_close состояния».
3. **`pause_scripts` (plugin.cpp:252) — НЕ тот же teardown.** Он только ставит
   hook и снимает флаг миссии, состояния НЕ закрывает (это «заморозка» при
   переходе в меню, позже они всё равно перейдут в reload/final_scripts).
4. **`with ` onScriptTerminate`: смотреть тип через `lua_type` ДО pcall**
   (непенсённая функция — nil). pcall прощает ошибки внутри функции, но если
   функция не функция — `lua_tostring(L,-1)` вернёт «attempt to call a nil value»,
   это перехватится pcall и запишется в лог; скрипт всё равно продолжится.
5. **Не разворачивать `lua_close` без `lua_gc` перед ним по смысле** — `lua_close`
   сам вызывает GC, но тут до него `LUA_GCCOLLECT` вызывается явно для
   управляемости; порядок (destroy → gc → close) важен: сначала снять игровые
   объекты (C++-мир), потом освободить Lua-память.
6. **`CMessages::AddMessageJumpQ(L"Script reloaded", 2000, 1)`** — сообщение НА
   ЭКРАНЕ ставится ДО teardown. Если teardown долгий (>2c), сообщение пропадёт
   раньше финала — это нормально, диагностику вести по lualoader/log.txt.
7. **ВАЖНО про лог:** `dellod()` стирает log при каждом старте скриптов. После
   reload в логе должны быть строчки:
   - `loaded <путь> …` (каждый скрипт заново)
   - при падении/ошибке скрипта — `could not load …` или стек ошибки.
   В `trace.txt` (общий C++-трейс) — маркеры `destroy: ВХОД/ВЫХОД` и
   `reload: lua_close состояния`.

## 7. Как написать скрипт, ЧТОБЫ reload его пережил корректно

1. `main()` обязан слушать флаг миссии и возвращаться:
   ```lua
   function main()
       while true == getflagmission() do
           wait()  -- игровой цикл
       end
   end
   ```
   Тогда teardown (2b) завершится, не зависнет, и `destroy` корректно подберёт
   объекты этого скрипта.
2. Если скрипт регистрирует хуки/окна/не-Lua ресурсы — добавить:
   ```lua
   function onScriptTerminate()
       -- снять свои хуки, закрыть окна, освободить ресурсы
   end
   ```
3. После reload глобальные переменные обнулены. Готовить скрипт так, чтобы
   `main()` можно было запускать с чистого листа.

## 8. Быстрые вопросы-ответы (для себя/будущей модели)

- **Когда именно срабатывает reload?** Ctrl нажат → отпущен (две фазы в reload()).
  Точный скан-код — VK_CONTROL (0x11), любой Ctrl.
- **Какие файлы?** Все `.lua`/`.LUA` рекурсивно в папке `lualoader/` игры.
  Меняешь Lua-файл → Ctrl-reload → новый `lua_State` перечитает файл с диска.
- **C++-код (funcs.cpp/plugin.cpp) меняется?** Нет: `.asi` уже скомпилирован.
  Ctrl перезагружает ТОЛЬКО Lua-скрипты, не сам плагин. Для правок C++ —
  пересборка (`./build.sh`) и рестарт игры.
- **Что если игра вылетает при reload?** Смотрим две вещи по порядку:
  1) свежий `lualoader/log.txt` (после dellod) — ошибки Lua/onScriptTerminate;
  2) хвост `trace.txt` — дошёл ли до `reload: lua_close состояния` и не
     застрял ли между `destroy: ВХОД` и `destroy: ВЫХОД`.
