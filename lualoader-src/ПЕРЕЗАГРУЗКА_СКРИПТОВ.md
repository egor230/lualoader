# Перезагрузка скриптов в lualoader — как это устроено (подробно)

**Файл:** `plugin.cpp` (ядро плагина, точка входа ASI) + `funcs.cpp` (функции).
**Версия документа:** 24.09.2026 (soft restart через флаг `g_scripts_teared_down` + `search_scripts` напрямую).
Описывает ТОЛЬКО фактическое состояние кода после правок этой версии.

ВАЖНО: это **свой** lualoader для GTA VC (встраивание Lua 5.4), НЕ MoonLoader.
Механика «Hot Reload» (реагрузка .lua → teardown → пересоздание состояний) реализована
СВОИМИ руками. Модель исполнения: **каждый скрипт живёт в своём C++-потоке**
(в отличие от MoonLoader, где скрипты — корутины на главном потоке игры).

Отличие от прошлой версии документа: раньше StopHook был ВЫКЛЮЧЕН (count=0), а
остановка шла через `g_lua_epoch` + кооперативные `wait()`-safe-point; сейчас прямо
наоборот — **хук ВСЕГДА активен (count=1000) и бросает `luaL_error`, а остановка
скрипта — ошибкой (не yield)**. Это стало возможно после исправления `lua_resume`.

## 1. Триггеры

- **Ctrl** → `reload()`: две фазы (нажатие + отпускание) → `teardown_all(true)` →
  поднимается флаг `g_scripts_teared_down` → `gameProcessEvent` на игровом потоке
  перезапускает скрипты через `search_scripts()` (§3.1).
- **clrfl** (Clear/Flush, команда из регистра) → `TriggerClearFlush()` →
  detached-поток `HandleClearFlush()` → **только флаг + teardown без рестарта**.
- **Финал / выход в меню** → `final_scripts()` → `teardown_all(false)`.

`KeyPressed(VK_CONTROL)` = `plugin::KeyPressed` (высокий бит — «удерживается»).

## 2. StopHook — база остановки (главное изменение)

**История вопроса.** В прошлых версиях стояло «хук нельзя включать: lua_error из
хука = segfault». Это было НЕВЕРНО: segfault происходил не из-за хука, а из-за
кривого вызова `lua_resume(L, from, narg, NULL)` — в Lua ≥5.4 появился ЧЕТВЁРТЫЙ
аргумент `int *nresults`, и `ldo.c:889` пишет `*nresults` БЕЗУСЛОВНО при ЛЮБОМ
возврате resume (yield / ошибка / OK). NULL-указатель там = мгновенный краш как
раз «мгновенный выход после ПАУЗА». С валидным `&nres` hook + `luaL_error` под
`lua_resume` работает идеально (эмпирически проверено на `lua/*`, EXIT=0).

**Текущее состояние (plugin.cpp):**

```
int hookFunc(lua_State* L, lua_Debug* ar) {
    if (g_shouldStopAllScripts.load()) {
        return luaL_error(L, "SCRIPT_STOPPED_BY_CPP");   // ошибка, НЕ yield
    }
    return 0;                                             // флаг не поднят — дёшево
}
```

- Хук ставится **всегда**: `lua_sethook(L, hookFunc, LUA_MASKCOUNT, 1000)` в
  `startscipt` (plugin.cpp:352) и в `create_newthread` для свежего состояния L1
  (plugin.cpp:586). Без флага хук — пустой возврат каждые 1000 инструкций (дёшево).
- Флаг `g_shouldStopAllScripts` поднимает ТОЛЬКО `HandleClearFlush()` (clrfl).
  Ctrl/reload поднимает НЕ его, а `teardown_active` + эпоху (см. §3).
- Ошибка из хука БЕЗОПАСНА: любой скрипт всегда выполняется под защищённым
  вызовом — `lua_resume` с валидным `nres` или `lua_pcall`. Resume возвращает
  `LUA_ERRRUN`, корутина не рвётся, поток скрипта завершается по статусу.

**Все вызовы `lua_resume` в плагине — с валидным `int nres`** (plugin.cpp:250,
252, 255, 259(+261), 262, 360; локальная `int nres = 0;`). Это не косметика —
это устранение скрытого краша при любом возврате resume.

## 3. Teardown «по владельцу» — асинхронно, ПО ЭПОХАМ

**Почему НЕ «ждать потоки»:** ранняя версия teardown блокировала reload-поток в
ожидании `active_pumps==0` — а pump-потоки сидят ВНУТРИ `lua_resume` и не каждый
вовремя видит флаг; при Ctrl игра «зависала», по таймауту разборка отменялась.

**Принцип модели:** состояние закрывает ТОЛЬКО его владелец (pump-поток).
Teardown переводит все существующие состояния в «устаревшее» поколение одним
инкрементом эпохи; владельцы сами закрывают свои состояния на ближайшем `wait()`.
Новые скрипты штампуются НОВОЙ эпохой — их `wait()` не срабатывает. Логика:

```
publish_state(L):  luastate.push_back(L) + pumpLive.insert(L) + active_pumps++
                   + lua_state_stamp(L)   [эпоха = текущая]
pump_owner(...):   помп-цикл; пока !lua_state_obsolete(L) и статус жив (не ошибка);
                   при ошибке (LUA_ERRRUN от StopHook) — ВЫХОД ПО СТАТУСУ;
                   по окончании:
                     obsolete(L) == true  → owner_selfclose(L)  [разбирает СВОЁ]
                     иначе                → drop_owner(L)       [остаётся сиротой]
owner_selfclose(L): onScriptTerminate() → destroy(L) → luastate.remove
                   + pumpLive.erase + active_pumps-- + lua_state_unstamp(L)
teardown_all(restart):
   если reload_busy уже true → пропуск (другая разборка идёт)
   teardown_active=true  [рвёт долгие C-API: модель/координаты/аудио]
   star_coroutine=false  [запрет 2-х потоков] + сброс флага миссии
   stop_mission_watch()
   g_lua_epoch++                            → ВСЕ существующие состояния УСТАРЕЛИ
   ЖДЁТ active_pumps==0 (порциями по 10мс, страховка 5с)   [join владельцев]
   свип сирот (в luastate, но НЕ в pumpLive) →
       onScriptTerminate → destroy → luastate.remove → unstamp
    reload_busy=false                        → новый Ctrl можно сразу
    если restart → g_scripts_teared_down.store(true)          [НЕ запускаем скрипты тут!]
```

**ВАЖНО (24.09): teardown НЕ запускает скрипты сам.** Раньше тут стояло
`std::thread(start_lualoder).detach()`, и это плодило ВИСЯЧИЕ потоки: `start_lualoder`
после `search_scripts()` уходит в `while(true)` ожидания страницы меню 8/10 (загрузка/
новая игра); в игре страница 32, поэтому цикл НИКОГДА не завершался. Каждый Ctrl
оставлял вечновисящий loader-поток, а при последующей загрузке сейвы все они разом
звали `final_scripts()` → каскад teardown'ов → вылет (см. §7.1). Теперь teardown
только поднимает флаг — перезапуск делает gameProcessEvent (§3.1).

`reload()` = `teardown_all(true)`, `final_scripts()` = `teardown_all(false)`,
`HandleClearFlush()` зовёт `teardown_all(false)` ПОСЛЕ поднятия флага.

## 3.1. Soft Restart — флаг `g_scripts_teared_down` (главное изменение 24.09)

**Цикл:** «скрипты убились → teardown поднял флаг → игра на следующем кадре
перезапустила их снова».

```
teardown_all(true):        ... разборка ... → g_scripts_teared_down.store(true)

gameProcessEvent (ИГРОВОЙ поток, plugin.cpp):
    if (g_scripts_teared_down.exchange(false)) {
        star_thread::set(s);                     // скрипты снова разрешены
        std::thread(search_scripts).detach();    // перезапуск, и поток ВОЗВРАЩАЕТСЯ
    }
```

**Почему именно так (три причины):**

1. **Поток-висельник убран.** `search_scripts()` — это ровно та часть `start_lualoder`,
   которая перезапускает скрипты, БЕЗ меню-цикла. Поток отрабатывает и завершается.
2. **Старт с игрового потока.** Запуск скриптов из reload/teardown-потока = data race
   с игровым состоянием; gameProcessEvent — единственное место, которому можно
   spawn'ить потоки скриптов. Разборка ставит ТОЛЬКО флаг-запрос.
3. **Схлопывание дубликатов.** Несколько Ctrl подряд = один флаг = ОДИН рестарт,
   а не N параллельных loader'ов.

**Почему `star_thread` НЕ гасится при teardown:** если бы teardown делал
`star_thread::set(false)`, то одновременно с флагом сработал бы и нижний путь
gameProcessEvent (`number_save_slot==9 && !star_thread::get()`), и скрипты
стартовали бы ДВАЖДЫ. `star_thread` остаётся true весь сеанс; единственный
обработчик рестарта — флаг `g_scripts_teared_down`.

**Как старые скрипты сворачиваются (три пути, все безопасны):**

1. **clrfl:** `g_shouldStopAllScripts=true` → StopHook бросает `luaL_error` любому
   скрипту в пределах 1000 инструкций (включая busy-Lua-петлю `while true do end`
   БЕЗ `wait()`) → `lua_resume` возвращает `LUA_ERRRUN` → `pump_owner` видит
   не-в-порядке статус и выходит → владелец завершает поток.
2. **Ctrl/reload:** эпоха+1 → `wait()` делает `return lua_yield(L, 0)` →
   `lua_resume` возвращается, владелец видит устаревшую эпоху и разбирает СВОЁ.
3. **Пауза/долгий C-вызов:** `teardown_active` рвёт циклы ожидания в
   `load_model_before_avalible`, `getcord`, `expectations`, `play_voice` — они
   выходят из C-цикла, управление возвращается в Lua, дальше крюк StopHook/эпоха.

**lua_close НЕ вызывается нигде** (закрытие живого состояния из чужого/фонового
потока роняло игру). Состояние после destroy остаётся в памяти, но никому не мешает.
`drop_owner`-сироты закрываются след. teardown-свипом. `cleanstl()` при reload НЕ
зовётся: старые владельцы ещё живы и их destroy() требуют STL-хранилища; новые
скрипты стартуют с чистых хранилищ, старые объекты дочистят сами владельцы.

## 4. clrfl — полная остановка (HandleClearFlush, plugin.cpp)

По шагам — ПОЛНОСТЬЮ по схеме «флаг → join → сброс»:

```
static void HandleClearFlush() {
    g_shouldStopAllScripts.store(true);   // 1) флаг: StopHook рвёт каждый скрипт
    teardown_all(false);                  // 2) join: ждёт active_pumps==0, свип сирот
    g_shouldStopAllScripts.store(false);  // 3) сброс: новые скрипты стартуют чисто
}
```

- **Никаких `sleep_for`, ни `g_luaMutex`** в пути остановки. Остановку делает сам
  флаг + хук (мгновенно); teardown лишь ждёт фактического завершения потоков.
  (Раньше тут были `sleep_for(100мс)` + захват `g_luaMutex` — убраны: именно они
  в прошлых прогонах давали «зависание».)
- **C-функции с флагом**: `wait()` и `play_voice` при `g_shouldStopAllScripts`
  возвращают `return luaL_error(L, "SCRIPT_STOPPED_BY_CPP")` (НЕ yield) —
  скрипт завершается той же ошибкой, что и через хук. Helper-циклы без `L`
  (`getcord`, `expectations`, `load_model_before_avalible`) выходят из цикла
  (`return 0` / `break`) — управление возвращается в Lua, дальше добивает хук.
- Запускается на ОТДЕЛЬНОМ detached-потоке (`TriggerClearFlush`), чтобы не
  блокировать поток чтения клавиш на время teardown (до 5с).

## 5. startscipt (plugin.cpp)

Отдельный detached-поток на каждый `.lua`:
`state Lua` (luaL_newstate+openlibs, GC выкл) → пути/функции →
`luaL_loadfile` → `lua_sethook(L, hookFunc, LUA_MASKCOUNT, 1000)` →
`lua_pcall` (создать main) → если `main` функция:
`publish_state(L)` → `lua_resume(L, NULL, 0, &nres)` → L1 = `lua_newthread(L)` →
если нет второго потока — `drop_owner` + return; иначе `pump_owner(L, L1, args, false)`.

`create_newthread` (plugin.cpp): состояние L1 на собственный `luaL_newstate`;
тут тоже ставится StopHook (count=1000) — иначе этот скрипт не остановился бы
clrfl'ом. Публикация (`publish_state`) происходит ВНУТРИ создаваемого потока —
пока владелец не зарегистрирован, состояние свипу не видно (закрытие чужого
исключено по построению). Поток: `publish_state(L1); pump_owner(L1, nullptr, args, true);`.

## 6. Сторож миссии

`mission_watch_proc` на reload/final зовёт `stop_mission_watch()` (join + nullptr).
Он разрушает `mission_watch_L` через `destroy()` со СВОЕГО потока (в т.ч. при
смерти игрока) — пред-существующая гонка, вне рамок reload; `g_destroy_mutex`
сериализует concurrent-destroy. Порядок в `teardown_all`: стоп-вотч → флаг.

## 7. О чём МОЛЧИТ код (грабли/остаточные риски)

1. **Каскад teardown'ов при загрузке сейвы (исправлено 24.09).** До правки
   `teardown_all(true)` сам запускал `start_lualoder()`, чей `while(true)` ждёт
   страницу меню 8/10 — в игре (страница 32) он не выходит никогда. Каждый Ctrl
   оставлял висячий loader-поток; при загрузке сейвы все они разом звали
   `final_scripts()` → десятки вложенных teardown'ов → порча памяти и вылет
   (маркеры в трейсе: `teardown: вход` повторяется раз за разом, затем
   `CRASH ... ACCESS_VIOLATION READ @0x00000018`). Лечится флагом — см. §3.1.
2. `luastate`/`pumpLive` под мьютексами (публикация/удаление/snapshot). Сирот-свип
   строит SNAPSHOT под мьютексом, итерации по нему.
3. **Край:** состояние `create_newthread`, чей поток ещё не стартовал, при уже
   завершённом teardown — опубликуется с НОВОЙ эпохой и запустится НОРМАЛЬНО после
   разборки. Это не краш: скрипт просто переживает reload.
4. **Хук ставят в flow и из `startscipt`, и из `create_newthread`.** Момент между
   `luaL_newstate` и `lua_sethook` — хук на состоянии ещё не висит; на практике
   clrfl в этот миг не приходит (состояние не опубликовано), поэтому не страшно,
   но помнить: полностью «от хукозащищённости» преждевременного состояния нет.
5. **Непробиваемый C-блокер вне `wait()`** (непатченый долгий API без проверок
   флага) держит СВОЙ скрипт до конца вызова. Ctrl/clrfl это НЕ замораживает
   (teardown никого не ждёт, лимит 5с + свип), но скрипт «доживает» до возврата
   из C-вызова. Для перезагрузки это остаточный «долгоживущий мусор».
6. `pause_scripts` — заморозка (hook + флаг миссии), состояния НЕ закрывает.
7. `dellod()` чистит `lualoader/log.txt` перед КАЖДЫМ запуском скриптов —
   диагностику вести только по свежему логу после прогона.
8. Маркеры в `trace.txt`: `teardown: вход`, `owner_selfclose: …`,
   `teardown: сирота %p`, `teardown: разборка завершена`,
   `gameProcessEvent: флаг перезапуска`. Увидели «вход» и нет
   `owner_selfclose` дольше 5с → владельцы зависли в C-вызовах (не крашит).
   Увидели каскад `teardown: вход` без `gameProcessEvent: флаг перезапуска`
   → вернулась старая сборка (пересобери `./build.sh`).

## 8. Как написать скрипт, ЧТОБЫ reload его пережил корректно

1. `main()` слушает флаг миссии и возвращается (`while true == getflagmission()`).
   Тогда Ctrl-разборка проходит аккуратно (владелец закроет СВОЁ состояние).
2. Регистрирует ресурсы → объявить `function onScriptTerminate()` (снять хуки).
3. Глобальные переменные после reload обнулены — main должен стартовать с чистого листа.
4. Для диагностики — свежий `lualoader/log.txt` и хвост `trace.txt`.
5. Помнить: `wait()` при clrfl возвращает ОШИБКУ (не продолжает работу). Не
   вылавливать `pcall`'ом — скрипт должен умереть, а не «пережить» остановку.

## 9. Быстрые вопросы-ответы

- **Когда срабатывает reload?** Ctrl нажат и отпущен (две фазы в `reload()`).
- **Что происходит после Ctrl?** `teardown_all(true)` останавливает скрипты и
  поднимает флаг `g_scripts_teared_down`. На следующем кадре `gameProcessEvent`
  (игровой поток) видит флаг и перезапускает скрипты через `search_scripts()`.
  Без флага restart шёл бы из reload-потока = data race (§3.1).
- **Что делает clrfl?** Полная остановка ВСЕХ скриптов по флагу (хук-ошибка) +
  `teardown_all(false)`, без рестарта. Новые скрипты не запускаются.
- **Какие файлы?** Все `.lua`/`.LUA` рекурсивно в папке `lualoader/` игры.
- **Почему clrfl теперь мгновенный?** Остановку делает StopHook (флаг → ошибка в
  пределах 1000 инструкций) вместо прежнего «flag + sleep 100мс + mutex + wait()-safe-point».
- **C++-код меняется?** Нет: Ctrl перезагружает только Lua. Правки C++ — пересборка
  `./build.sh` (успех = `ГОТОВО: ../lualoader.asi`), затем рестарт игры.
- **Почему было «зависание» на Ctrl?** Ранняя версия teardown назначала reload-потоку
  блокирующее ожидание до 15с; плюс путь clrfl содержал sleep(100мс)+мьютекс. Теперь
  разборка асинхронная (эпоха+1 мгновенно, Ctrl ничего не блокирует), а саму
  остановку делает хук.
- **Почему при загрузке сейвы после Ctrl шёл вылет?** Старый `teardown_all(true)`
  сам спавнил `start_lualoder()`, который навсегда зависал в `while(true)` ожидания
  страницы меню 8/10 (в игре страница 32). Каждый Ctrl = +1 висячий поток; при
  загрузке сейвы все они одновременно звали `final_scripts()` → каскад разборок →
  вылет. Теперь teardown только поднимает флаг, а перезапуск идёт через
  `search_scripts()` с игрового потока — висячих потоков нет (§3.1, §7.1).
- **Почему «мгновенный выход после ПАУЗЫ»?** `lua_resume(..., NULL)` — 4-й арг был
  NULL, а `*nresults` пишется всегда → краш при возврате yield. Исправлено: везде
  валидный `int nres`.
