# Перезагрузка скриптов в lualoader — как это устроено (подробно)

**Файл:** `plugin.cpp` (ядро плагина, точка входа ASI) + `funcs.cpp` (функции).
**Версия документа:** 22.09.2026 (рефактор «Teardown по владельцу» + АСИНХРОННАЯ разборка по эпохам).
Описывает ТОЛЬКО фактическое состояние кода после правок этой версии.

ВАЖНО: это **свой** lualoader для GTA VC (встраивание Lua 5.4), НЕ MoonLoader.
Механика «Hot Reload» (детекция → teardown → пересоздание состояний) реализована
СВОИМИ руками. Модель исполнения: **каждый скрипт живёт в своём C++-потоке**
(в отличие от MoonLoader, где скрипты — корутины на главном потоке игры).

## 1. Триггер: Ctrl

`reload()` — наблюдатель, запускается ОДИН раз за сессию (static-guard
`background_started` в `search_scripts()`). Фаза 1 ждёт НАЖАТИЕ Ctrl (или
`!star_thread`), фаза 2 ждёт ОТПУСКАНИЕ, затем `teardown_all(true)` + рестарт.
`KeyPressed(VK_CONTROL)` = `plugin::KeyPressed` (высокий бит — «удерживается»).

---

## 2. Teardown «по владельцу» — асинхронно, ПО ЭПОХАМ

**Почему НЕ «ждать потоки»:** первые 2 версии teardown блокировали reload-поток
до 15с в ожидании `active_pumps==0` — а pump-потоки сидят ВНУТРИ `lua_resume`
(в wait/API-циклах) и не каждый вовремя видит флаг. Итог: при Ctrl игра
«зависала» (reload-поток ждал, скрипты заморожены), по таймауту разборка
ОТМЕНЯЛАСЬ. От этого отказались.

**Принцип модели:** состояние закрывает ТОЛЬКО его владелец (pump-поток).
Teardown никого НЕ ждёт: он переводит все существующие состояния в «устаревшее»
поколение одним инкрементом эпохи и немедленно рестартует; владельцы сами
закрывают свои состояния на ближайшем yield. Новые скрипты штампуются НОВОЙ
эпохой — их `wait()` не срабатывает. Логика:

```
publish_state(L):  luastate.push_back(L) + pumpLive.insert(L) + active_pumps++
                   + lua_state_stamp(L)   [эпоха = текущая]
pump_owner(...):   помп-цикл; пока !lua_state_obsolete(L); по окончании:
                     obsolete(L) == true  → owner_selfclose(L)  [разбирает СВОЁ]
                     иначе                → drop_owner(L)       [остаётся сиротой]
owner_selfclose(L): onScriptTerminate() → destroy(L) → luastate.remove
                   + pumpLive.erase + active_pumps-- + lua_state_unstamp(L)
teardown_all(restart):   [АСИНХРОННО, мгновенно]
   star_coroutine=false (запрет 2-х потоков) + флаг миссии false + stop_mission_watch()
   g_lua_epoch++                            → ВСЕ существующие состояния УСТАРЕЛИ
   на каждом состоянии: lua_sethook(MASKCOUNT,100) → выход даже из busy-Lua петли
   cвип сирот: состояния в luastate, которых НЕТ в pumpLive (владельцы мертвы)
               → onScriptTerminate → destroy → luastate.remove → unstamp
   reload_busy=false                        → новый Ctrl можно сразу
   если restart → 100мс → std::thread(start_lualoder).detach()
```

`reload()` = `teardown_all(true)`, `final_scripts()` = `teardown_all(false)`.

**Как старые скрипты сворачиваются:** `wait()` (funcs.cpp) дробит сон по 10мс,
а при `lua_state_obsolete(L)` делает `return lua_yield(L, 0)` — `lua_resume`
возвращается, владелец видит устаревшую эпоху и разбирает своё состояние сам.
Busy-Lua петлю (хук был 0) ломает form-хук MASKCOUNT=100, выставленный из teardown.

**lua_close НЕ вызывается нигде** (закрытие живого состояния из чужого/фонового
потока роняло игру). Состояние после destroy остаётся в памяти, но никому не мешает.
`drop_owner`-сироты закрываются след. reload-свипом. `cleanstl()` при reload НЕ
зовётся: старые владельцы ещё живы и их destroy() требуют STL-хранилища; новые
скрипты стартуют с чистых хранилищ, старые объекты дочистят сами владельцы.

## 3. startscipt (plugin.cpp)

Отдельный detached-поток на каждый `.lua`:
`state Lua` (luaL_newstate+openlibs, GC выкл) → пути/функции →
`luaL_loadfile` → `lua_pcall` (создать main) → если `main` функция:
`publish_state(L)` → `lua_resume` → L1 = `lua_newthread(L)` →
если нет второго потока — `drop_owner` + return; иначе `pump_owner(L, L1, args, false)`.

`create_newthread` (plugin.cpp): состояние L1 на собственный `luaL_newstate`;
публикация (`publish_state`) происходит ВНУТРИ создаваемого потока — пока владелец
не зарегистрирован, состояние свипу не видно (закрытие чужого исключено по построению).
Поток: `publish_state(L1); pump_owner(L1, nullptr, args, true);`.

## 4. Сторож миссии

`mission_watch_proc` на reload/final зовёт `stop_mission_watch()` (join + nullptr).
Он разрушает `mission_watch_L` через `destroy()` со СВОЕГО потока (в т.ч. при
смерти игрока) — пред-существующая гонка, вне рамок reload; destroy-мутекс
сериализует concurrent-destroy. Порядок в `teardown_all`: стоп-вотч → флаг.

## 5. О чём МОЛЧИТ код (грабли/остаточные риски)

1. `luastate` теперь под `luastate_mx` (публикация/удаление/snapshot-итерации).
   Сирот-свип строит SNAPSHOT под мьютексом, итерации по нему.
2. **Край:** состояние `create_newthread`, чей поток ещё не стартовал, при уже
   завершённом teardown — опубликуется с НОВОЙ эпохой и запустится НОРМАЛЬНО
   после разборки (старым поколением не считается). Это не краш: скрипт просто
   переживает reload.
3. **Форс-хук (MASKCOUNT=100) ставится из чужого потока** на состояние, чей поток
   крутит `lua_resume` — та же техника, что в старой модели. Работает для
   busy-Lua петель. Непробиваемый C-блокер вне wait (не патченый API) держит СВОЙ
   скрипт до конца вызова — Ctrl это НЕ замораживает (teardown никого не ждёт),
   остаётся остаточным «долгоживущим мусором» до завершения вызова/флага миссии.
4. `pause_scripts` — заморозка (hook + флаг миссии), состояния НЕ закрывает.
5. `dellod()` чистит `lualoader/log.txt` перед КАЖДЫМ запуском скриптов —
   диагностику вести только по свежему логу после прогона.
6. Маркеры в `trace.txt`: `teardown: вход`, `owner_selfclose: …`,
   `teardown: сирота %p`, `teardown: разборка запущена` (НОВАЯ асинхронная
   разборка печатает «запущена», а НЕ «завершена» — завершение доводит каждый
   владелец), `destroy: ВХОД/ВЫХОД` (в destroy-мутексе). Увидели «вход» без
   «разборка запущена» → краш в teardown. Увидели «запущена» и НИ ОДНОЙ
   `owner_selfclose` → владельцы зависли в непробиваемых C-вызовах (скрипты
   сворачиваются при флаге миссии; не крашит).

## 6. Как написать скрипт, ЧТОБЫ reload его пережил корректно

1. `main()` слушает флаг миссии и возвращается (`while true == getflagmission()`).
   Тогда wait()-yield сработает и владелец аккуратно разберёт состояние.
2. Регистрирует ресурсы → объявить `function onScriptTerminate()` (снять хуки).
3. Глобальные переменные после reload обнулены — main должен стартовать с чистого листа.
4. Для диагностики — свежий `lualoader/log.txt` и хвост `trace.txt`.

## 7. Быстрые вопросы-ответы

- **Когда срабатывает reload?** Ctrl нажат и отпущен (две фазы в reload()).
- **Какие файлы?** Все `.lua`/`.LUA` рекурсивно в папке `lualoader/` игры.
- **C++-код меняется?** Нет: Ctrl перезагружает только Lua. Правки C++ — пересборка
  `./build.sh` (успех = `ГОТОВО: ../lualoader.asi`), затем рестарт игры.
- **Игра падает при reload?** Смотреть: свежий log.txt → хвост trace.txt
  (дошёл ли до «teardown: разборка запущена» и появились ли `owner_selfclose`).
- **Почему было «зависание» на Ctrl?** Ранняя версия teardown назначала
  reload-потоку блокирующее ожидание до 15с (active_pumps==0) — reload-поток
  ждал «застрявшие» pump-потоки, скрипты были заморожены. Теперь разборка
  асинхронная: эпоха+1 мгновенно, Ctrl ничего не блокирует.
